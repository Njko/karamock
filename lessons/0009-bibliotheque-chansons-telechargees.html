Leçon 9 · Architecture en couches (4/N)

L'onglet Bibliothèque affiche les chansons téléchargées

Boucle bouclée : la Leçon 7 a donné un sens à DownloadedSongsRepository, mais rien ne le lisait encore. On branche enfin LibraryView — stub vide depuis la Leçon 1 — dessus.

Pourquoi cette leçon : jusqu'ici, le Repository de la Leçon 7 n'était écrit que d'un seul côté (DownloadSongUseCase y ajoute des chansons). Un repository qu'on ne lit jamais n'a aucune valeur observable — cette leçon ferme la boucle en lisant réellement les chansons stockées et en les affichant. Et comme la Leçon 8 vient de le rappeler, un ViewModel ne doit jamais dépendre directement d'un Repository : la lecture passe donc, elle aussi, par un UseCase dédié plutôt que par un appel direct à downloadedSongsRepository.songs(). C'est aussi la première vue de la mission qui consomme un acteur asynchrone plutôt qu'un simple @State local.

Un second UseCase, symétrique du premier

DownloadSongUseCase (Leçon 7) écrit dans le Repository. Il lui manque un pendant pour la lecture — sans lui, LibraryViewModel n'aurait d'autre choix que d'appeler downloadedSongsRepository.songs() directement, exactement la violation de la Dependency Rule que la Leçon 8 vient de corriger côté téléchargement.

struct FetchDownloadedSongsUseCase: Sendable {
    let repository: DownloadedSongsRepository

    init(repository: DownloadedSongsRepository) {
        self.repository = repository
    }

    func callAsFunction() async -> [Song] {
        await repository.songs()
    }
}

Même convention callAsFunction qu'en Leçon 7, même absence de valeur par défaut pour repository — ce paramètre doit obligatoirement pointer vers l'instance partagée par toute l'app. À eux deux, DownloadSongUseCase (écriture) et FetchDownloadedSongsUseCase (lecture) sont désormais les seules portes d'entrée vers DownloadedSongsRepository : aucun ViewModel n'a besoin — ni le droit — d'y accéder autrement.

Struct, class ou actor ? Comment choisir

La question à se poser en premier : ce type a-t-il un état mutable qui doit être partagé par référence ? Si non, une struct suffit (immuable ou copiée sans conséquence, sans identité) — Sendable y est alors quasiment gratuit : le compilateur le vérifie automatiquement dès que toutes les propriétés stockées le sont déjà, comme pour Song ou les deux UseCase de cette leçon. Si oui, il reste à choisir où vit cet état mutable :

État mutableChoixExemple
UI, lu/modifié uniquement depuis le main thread@MainActor final classSongDownloadViewModel, LibraryViewModel
Partagé, accédé depuis plusieurs contextes async concurrentsactorInMemoryDownloadedSongsRepository (Leçon 7)
Immuable, aucune référence partagée nécessairestruct: SendableSong, FetchDownloadedSongsUseCase

Le piège à éviter : ne jamais forcer Sendable sur une classe à état mutable avec @unchecked Sendable pour faire taire le compilateur — ça reporte sur toi une garantie de thread-safety que plus rien ne vérifie. @MainActor pour l'UI et actor pour les types partagés couvrent tous les cas rencontrés dans cette mission.

Un ViewModel volontairement mince

SongDownloadViewModel (Leçon 6) gérait une vraie machine à états (notDownloaded → downloading → downloaded/failed). LibraryViewModel n'a presque aucune logique — et c'est très bien ainsi : son seul travail est de faire le pont asynchrone entre le UseCase de lecture et l'affichage synchrone qu'attend SwiftUI.

@MainActor
@Observable
final class LibraryViewModel {
    private(set) var songs: [Song] = []

    private let fetchDownloadedSongs: FetchDownloadedSongsUseCase

    init(fetchDownloadedSongs: FetchDownloadedSongsUseCase) {
        self.fetchDownloadedSongs = fetchDownloadedSongs
    }

    func refresh() async {
        songs = await fetchDownloadedSongs()
    }
}

Toujours pas de valeur par défaut — ni pour repository dans le UseCase, ni pour fetchDownloadedSongs dans le ViewModel : même règle qu'en Leçon 7 et 8, chaque maillon de la chaîne doit obligatoirement pointer vers l'instance partagée par toute l'app, jamais vers une instance isolée créée par accident.

LibraryView : charger, afficher, rafraîchir

struct LibraryView: View {
    @Environment(\.downloadedSongsRepository) private var downloadedSongsRepository
    @State private var viewModel: LibraryViewModel?
    @State private var selectedSong: Song?

    var body: some View {
        NavigationStack {
            Group {
                if let viewModel, !viewModel.songs.isEmpty {
                    List(viewModel.songs) { song in
                        Button {
                            selectedSong = song
                        } label: {
                            SongRow(song: song)
                        }
                        .buttonStyle(.plain)
                    }
                    .listStyle(.plain)
                } else {
                    ContentUnavailableView(
                        "Aucune chanson téléchargée",
                        systemImage: "arrow.down.circle",
                        description: Text("Télécharge une chanson depuis sa fiche pour la retrouver ici.")
                    )
                }
            }
            .navigationTitle("Bibliothèque")
        }
        .task {
            if viewModel == nil {
                viewModel = LibraryViewModel(
                    fetchDownloadedSongs: FetchDownloadedSongsUseCase(repository: downloadedSongsRepository)
                )
            }
            await viewModel?.refresh()
        }
        .refreshable {
            await viewModel?.refresh()
        }
        .sheet(item: $selectedSong) { song in
            SongOptionsSheet(song: song)
        }
    }
}

Taper une chanson dans la Bibliothèque rouvre SongOptionsSheet via .sheet(item:) — exactement le mécanisme de la Leçon 3 dans PlaylistDetailView. Rien de neuf à écrire : c'est le même selectedSong: Song? optionnel comme source de vérité, appliqué à un deuxième écran.

Pourquoi .task suffit à rafraîchir la liste sans .onAppear séparé

.task ne se contente pas de démarrer une fois "pour toujours" : son bloc se relance à chaque réapparition de la vue à laquelle il est attaché, et s'annule à chaque disparition. Changer d'onglet puis revenir sur Bibliothèque fait donc réapparaître LibraryView, ce qui relance .task — viewModel existe déjà (la condition if viewModel == nil saute), mais await viewModel?.refresh() s'exécute quand même à chaque fois. C'est ce qui garde la liste à jour après un téléchargement fait depuis l'onglet Découvrir, sans mécanisme de notification explicite entre les deux écrans.

Pourquoi le Preview de cette vue ne plante pas sans injection explicite

Contrairement à la mésaventure de la Leçon 4 (@Environment(Type.self), qui exige un ancêtre explicite sous peine de crash), @Environment(\.downloadedSongsRepository) passe par @Entry, qui porte toujours une valeur par défaut (InMemoryDownloadedSongsRepository(), vide). Une Preview de LibraryView sans .environment(\.downloadedSongsRepository, …) explicite affichera donc simplement l'état vide (ContentUnavailableView) plutôt que de planter — un des avantages concrets d'avoir adopté la forme par keypath partout dans ce projet.
