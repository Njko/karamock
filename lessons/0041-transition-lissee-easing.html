Leçon 41 · Moteur de paroles en C++ (5/N)

Lisser la transition entre deux lignes, sans état supplémentaire

Depuis la Leçon 40, currentTime avance réellement et la ligne active de LyricsPage change seule — mais elle saute encore net d'une position à l'autre, sans transition. Cette leçon lisse ce mouvement, en dérivant tout de currentTime plutôt qu'en faisant mémoriser à LyricsPage ce qui se passait à l'appel précédent. Symétrie avec la leçon précédente : après une leçon entièrement Swift, celle-ci est entièrement C++ — un seul fichier change, LyricsPage.cpp, et sa signature publique ne bouge pas d'un caractère. Toujours pas branché à un vrai flux audio ; ça reste la vue de preuve, avec trois lignes de test.

Le saut net, précisément

Depuis la Leçon 39, LyricsPage::render place chaque ligne à une position figée, fonction uniquement de l'index actif :

// État avant cette leçon
drawCentered(target, font, renderer, lyrics.textAt(active), centerY, activeHeight, activeColor);
if (active > 0) {
    drawCentered(target, font, renderer, lyrics.textAt(active - 1), centerY - lineAdvance, sideHeight, sideColor);
}

À l'instant précis où indexAtTime bascule d'une ligne à la suivante (Leçon 39), ces positions changent d'un coup, entre deux ticks de la Leçon 40 : une ligne encore "suivante" l'instant d'avant (à centerY + lineAdvance, petite, en retrait) devient "active" l'instant d'après (à centerY, grande, mise en avant) sans aucune position intermédiaire affichée.

Une transition sans mémoire d'un appel à l'autre

Tentation naturelle pour animer ce changement : faire retenir à LyricsPage l'index actif du dernier appel et l'instant où il a changé, dans un membre mutable. Ça marcherait, mais ça romprait une propriété que LyricsPage::render a depuis la Leçon 39 : c'est une fonction pure, son résultat ne dépend que de ses paramètres, jamais d'un appel précédent. Or l'information nécessaire existe déjà, sans rien mémoriser : lyrics.timeAt(active) donne l'instant exact où la ligne active a commencé — currentTime - lyrics.timeAt(active) donne donc directement "depuis combien de temps cette ligne est active", qu'il y ait eu un appel à render() une milliseconde plus tôt ou une minute plus tôt.

// NOUVEAU — dans render(), après avoir trouvé active
const double elapsedSinceActive = currentTime - lyrics.timeAt(active);

Ce n'est jamais négatif : indexAtTime ne renvoie active que si currentTime >= lyrics.timeAt(active) (Leçon 39), par construction.

L'easing : la fonction qui donne le fondu

Une interpolation linéaire (vitesse constante du début à la fin) donnerait un mouvement mécanique, perceptible comme artificiel. La pratique établie pour un mouvement d'interface qui "se pose" plutôt que de s'arrêter net — popularisée par les équations d'easing de Robert Penner, aujourd'hui un standard de fait en animation d'interface — est une fonction qui démarre vite et ralentit en approchant sa cible :

// NOUVEAU — dans l'espace de noms anonyme de LyricsPage.cpp
float clamp01(float t) {
    if (t < 0.0f) return 0.0f;
    if (t > 1.0f) return 1.0f;
    return t;
}

float easeOutCubic(float t) {
    const float u = 1.0f - t;
    return 1.0f - u * u * u;
}

clamp01 avant l'easing n'est pas une précaution superflue : elapsedSinceActive dépasse largement transitionDuration la plupart du temps qu'une ligne reste active (la transition ne dure qu'une fraction de seconde, la ligne reste active plusieurs secondes) — sans ce plafond à 1.0, t dépasserait 1, easeOutCubic donnerait un résultat supérieur à 1, et l'offset calculé plus bas deviendrait négatif : les lignes dépasseraient leur position finale au lieu de s'y arrêter.

Le calcul de l'offset : un seul décalage, appliqué aux trois lignes

// CORRECTION — Engine/LyricsPage.cpp (fonction render)
void LyricsPage::render(PixelBuffer& target, const Font& font, TextRenderer& renderer,
                         const LyricsStore& lyrics, double currentTime) const {
    const std::size_t active = lyrics.indexAtTime(currentTime);
    if (active == LyricsStore::npos) {
        return;
    }

    constexpr float activeHeight = 56.0f;
    constexpr float sideHeight = 32.0f;
    constexpr double transitionDuration = 0.5;   // NOUVEAU — secondes

    const Color activeColor{240, 240, 245};
    const Color sideColor = dim(activeColor);

    int ascent = 0, descent = 0, lineGap = 0;
    font.verticalMetrics(&ascent, &descent, &lineGap);
    const float lineAdvance = (ascent - descent + lineGap) * font.scaleForPixelsHeight(activeHeight);

    const double elapsedSinceActive = currentTime - lyrics.timeAt(active);   // NOUVEAU
    const float progress = easeOutCubic(clamp01(static_cast<float>(elapsedSinceActive / transitionDuration)));   // NOUVEAU
    const float offset = (1.0f - progress) * lineAdvance;   // NOUVEAU

    const int centerY = target.height() / 2;
    drawCentered(target, font, renderer, lyrics.textAt(active),
                 centerY + static_cast<int>(offset), activeHeight, activeColor);

    if (active > 0) {
        drawCentered(target, font, renderer, lyrics.textAt(active - 1),
                     centerY - static_cast<int>(lineAdvance) + static_cast<int>(offset), sideHeight, sideColor);
    }
    if (active + 1 < lyrics.lineCount()) {
        drawCentered(target, font, renderer, lyrics.textAt(active + 1),
                     centerY + static_cast<int>(lineAdvance) + static_cast<int>(offset), sideHeight, sideColor);
    }
}

Le même offset s'ajoute aux trois lignes — pas un décalage différent calculé pour chacune. C'est précisément ce qui garantit la continuité au moment du changement de ligne active : juste avant que active ne change (offset revenu à 0, ancienne transition terminée), la future ligne active était affichée en position "suivante", à centerY + lineAdvance. Juste après le changement (progress = 0, offset = lineAdvance), le calcul la replace à centerY + lineAdvance — exactement la même position, avant de la faire remonter vers centerY à mesure que progress avance vers 1. Aucun saut au moment de la bascule, sans que la fonction n'ait eu besoin de savoir qu'une bascule venait d'avoir lieu.

Ce que cette leçon ne fait délibérément pas : activeColor, sideColor, activeHeight et sideHeight restent assignés net selon le rôle final de chaque ligne, sans fondu. Une ligne qui devient active change de couleur et de taille instantanément au moment de la bascule ; seule sa position est lissée. Un fondu de couleur et de taille est un raffinement possible, distinct de ce que résout elapsedSinceActive, volontairement laissé de côté plutôt que traité en passant ici.

Aucun autre fichier ne change. La signature publique de LyricsPage::render est identique à la Leçon 39 — EngineProofView.swift et le bridging header n'ont rien à recompiler d'autre que LyricsPage.cpp lui-même.

État réel de l'implémentation (comparé le 9 août 2026) : conforme dans l'ensemble — clamp01, easeOutCubic et le calcul d'offset correspondent exactement à ce qu'enseigne cette leçon. Un seul écart, corrigé ci-dessus : transitionDuration vaut 0.5 dans le code réel, pas 0.3 — la leçon citait une valeur plausible mais non vérifiée avant la publication du vrai fichier.
Scénario de vérification, étape par étape :
  1. Build (⌘B) sur un simulateur iPhone et un simulateur Apple TV — aucun fichier Swift ni bridging header n'a changé, seule la recompilation C++ est attendue.
  2. Ouvre l'écran Découvrir : chaque changement de ligne active doit maintenant glisser verticalement au lieu de sauter net, sur environ 0,5 seconde.
  3. Observe particulièrement le début de chaque transition : la ligne qui devient active ne doit démarrer ni plus haut ni plus bas que sa position "suivante" affichée l'instant d'avant — aucun micro-saut visible au moment précis de la bascule.
  4. Vérifie que la couleur et la taille, elles, changent bien net au moment de la bascule — pas de fondu progressif attendu sur ces deux propriétés à ce stade.
  5. Change temporairement transitionDuration à 2.0 (bien plus long que l'écart de deux secondes entre les lignes de test) : observe que le mouvement ne se stabilise jamais complètement avant la bascule suivante — puis remets 0.5.
  6. Retire temporairement l'appel à clamp01 (passe directement elapsedSinceActive / transitionDuration à easeOutCubic) : observe le dépassement de position après la fin de chaque transition, puis remets clamp01.

Vérifie ta compréhension

1. Pourquoi le lissage n'exige-t-il aucun état mutable supplémentaire dans LyricsPage (pas de "dernier index actif" mémorisé entre deux appels) ?

2. Pourquoi clamp01 est-il nécessaire avant d'appeler easeOutCubic, alors qu'elapsedSinceActive ne peut jamais être négatif ?

3. Pourquoi le même offset est-il ajouté aux trois lignes (active, précédente, suivante), plutôt qu'un décalage calculé séparément pour chacune ?

4. Pourquoi la couleur et la taille de chaque ligne changent-elles encore net au moment de la bascule, alors que la position est désormais lissée ?

5. Pourquoi choisir une fonction d'ease-out (easeOutCubic) plutôt qu'une interpolation linéaire pour cette transition ?

6. Pourquoi LyricsPage::render reste-t-elle une méthode const, sans aucun membre mutable ajouté pour implémenter ce lissage ?

7. Que se passerait-il visuellement si transitionDuration était fixée à 2.0 secondes, avec des lignes de test espacées d'environ deux secondes (comme dans EngineProofView) ?

La transition se lisse bien mais un léger tremblement apparaît sur la position finale, comme si les lignes n'arrivaient jamais parfaitement immobiles ? Vérifie d'abord que offset atteint bien exactement 0 une fois progress à 1 (et non une valeur résiduelle due à l'arrondi static_cast<int>) avant de creuser plus loin — pose la question avec la valeur observée de offset en fin de transition si le tremblement persiste après cette vérification.
