ViewModel et Service : télécharger une chanson

Premier maillon d'un chantier qui va s'étaler sur plusieurs leçons : sortir la logique métier des vues. On commence par le cas le plus simple à isoler — télécharger une chanson pour l'écoute hors-ligne — sans encore introduire de couche Domain/UseCase.

Étape 0 — trois dossiers plutôt qu'un

Dans Xcode, à côté de Views/, crée deux nouveaux groupes : ViewModels/ et Services/. On n'ajoute pas encore de Domain/ — une couche Domain/UseCase qui ne fait qu'appeler un Service sans ajouter de règle métier est de la abstraction gratuite. On l'introduira dans une prochaine leçon, quand une vraie règle (ex. "interdire deux téléchargements simultanés à l'échelle de l'app") le justifiera.

Le Service : la seule couche qui "sait" comment télécharger

Un protocole d'abord, une implémentation mockée ensuite — c'est l'inversion de dépendance que tu appliquais déjà avec des protocoles côté Alamofire/réseau en UIKit. Le ViewModel dépendra du protocole, jamais de l'implémentation concrète.

protocol SongDownloading: Sendable {
    func download(_ song: Song) -> AsyncStream<Double>
}

struct MockSongDownloadService: SongDownloading {
    func download(_ song: Song) -> AsyncStream<Double> {
        AsyncStream { continuation in
            Task {
                for step in 1...10 {
                    try? await Task.sleep(for: .milliseconds(200))
                    continuation.yield(Double(step) / 10)
                }
                continuation.finish()
            }
        }
    }
}

AsyncStream<Double> émet une valeur de progression toutes les 200ms puis se termine — le consommateur la parcourt avec for await, comme un Observable<Double> RxSwift qu'on subscriberait, sans DisposeBag à tenir. Sendable sur le protocole documente que n'importe quelle implémentation doit être sûre à partager entre contextes de concurrence — ici MockSongDownloadService n'a aucun état stocké, donc rien à vérifier de plus.

Pourquoi pas un simple callback onProgress: (Double) -> Void ?

Une closure @escaping passée à une fonction async doit être @Sendable pour satisfaire la vérification stricte de concurrence de Swift 6 dès qu'elle traverse une frontière d'acteur — une source d'erreurs de compilation frustrantes pour un gain nul ici. AsyncStream est le mécanisme pensé pour exactement ce cas (une séquence de valeurs dans le temps) et évite le problème à la racine.

Le ViewModel : état observable, jamais de vue à l'intérieur

enum DownloadState: Equatable {
    case notDownloaded
    case downloading(progress: Double)
    case downloaded
    case failed
}

@MainActor
@Observable
final class SongDownloadViewModel {
    private(set) var state: DownloadState = .notDownloaded

    private let song: Song
    private let service: SongDownloading

    init(song: Song, service: SongDownloading = MockSongDownloadService()) {
        self.song = song
        self.service = service
    }

    func startDownload() {
        guard state == .notDownloaded || state == .failed else { return }
        state = .downloading(progress: 0)
        Task {
            for await progress in service.download(song) {
                state = .downloading(progress: progress)
            }
            state = .downloaded
        }
    }
}

@MainActor sur la classe entière garantit que toute mutation de state se fait sur le thread principal — nécessaire puisque ce state pilote directement de l'UI. private(set) empêche la vue d'écrire state directement : elle ne peut que le lire et appeler startDownload(), qui seul décide des transitions. service: SongDownloading (le protocole, pas MockSongDownloadService) avec une valeur par défaut — c'est ce qui rendra ce ViewModel testable avec un faux service plus tard, sans toucher à son code.

Brancher dans SongOptionsSheet

Le ViewModel est créé paresseusement dans .task, pas dans l'init de la vue — ça évite toute question sur le contexte d'acteur au moment de la construction de la vue, .task s'exécutant déjà sur le contexte principal :

struct SongOptionsSheet: View {
    let song: Song
    @State private var downloadViewModel: SongDownloadViewModel?
    // ... @State existants inchangés (mode, singerName, adjustVolumes, pitch, tempo)

    var body: some View {
        ScrollView {
            VStack(alignment: .leading, spacing: 20) {
                SongHeader(song: song)

                if let downloadViewModel {
                    DownloadButton(viewModel: downloadViewModel)
                }

                // ... ModeCard, TextField, Toggle, Sliders, boutons inchangés
            }
            .padding()
        }
        .task {
            if downloadViewModel == nil {
                downloadViewModel = SongDownloadViewModel(song: song)
            }
        }
    }
}

struct DownloadButton: View {
    let viewModel: SongDownloadViewModel

    var body: some View {
        switch viewModel.state {
        case .notDownloaded:
            Button("Télécharger", systemImage: "arrow.down.circle") {
                viewModel.startDownload()
            }
        case .downloading(let progress):
            HStack {
                ProgressView(value: progress)
                Text("\(Int(progress * 100)) %")
                    .font(.caption)
                    .monospacedDigit()
            }
        case .downloaded:
            Label("Téléchargée", systemImage: "checkmark.circle.fill")
                .foregroundStyle(.green)
        case .failed:
            Button("Réessayer", systemImage: "exclamationmark.triangle") {
                viewModel.startDownload()
            }
        }
    }
}
Pourquoi let viewModel: SongDownloadViewModel suffit dans DownloadButton, sans @ObservedObject ?

Avec l'ancien ObservableObject, oublier @ObservedObject sur une propriété stockant l'objet dans une vue enfant était un piège classique : sans lui, la vue ne se redessinait pas quand une propriété @Published changeait. Le framework Observation supprime ce piège : une classe @Observable lue dans body (ici via viewModel.state) est automatiquement suivie, qu'elle soit stockée avec let, passée en paramètre simple, ou récupérée via @Environment — plus de wrapper spécial à retenir pour la simple lecture.
