Leçon 4 · État partagé et présentation plein écran

Le lecteur plein écran et le mini-lecteur persistant

Le bouton "Jouer maintenant" de la Leçon 2 ne fait toujours rien. On le branche enfin — et pour ça, on a besoin d'un état partagé entre des vues qui n'ont aucun lien de parenté direct : @Observable + @Environment, en situation réelle cette fois.

Pourquoi cette leçon : tu connais @Observable en théorie, mais jamais appliqué à un vrai problème de câblage SwiftUI. Ici le problème est concret : SongOptionsSheet (Leçon 2) est enterré à trois niveaux de profondeur — RootTabView → DiscoverView → PlaylistDetailView → feuille modale — et il doit pourtant déclencher un mini-lecteur qui vit tout en haut, au niveau de RootTabView. C'est exactement le genre de câblage qu'on retrouve dans toute app SwiftUI avec un état partagé entre écrans distants.

Le problème : un état qui doit traverser des vues qui ne se connaissent pas

Taper "Jouer maintenant" dans SongOptionsSheet doit faire deux choses que SongOptionsSheet ne peut pas faire toute seule : afficher un mini-lecteur ancré au-dessus de la tab bar (propriété de RootTabView), et permettre d'ouvrir un lecteur plein écran depuis n'importe où. Passer un @Binding à travers chaque vue intermédiaire (DiscoverView, PlaylistDetailView…) marcherait, mais chacune devrait déclarer et retransmettre une propriété qu'elle n'utilise pas elle-même — ce qu'on appelle le prop drilling. La solution : un objet @Observable partagé, injecté une seule fois dans l'environnement.

@Observable
final class PlayerState {
    var currentSong: Song?
    var isPlaying = false
    var isExpanded = false
}

N'importe quelle vue descendante peut lire et muter cet objet via @Environment, sans qu'aucune vue intermédiaire n'ait besoin de le connaître ou de le retransmettre explicitement.

C'est la version moderne de quoi, exactement ?

Avant iOS 17, ce même besoin passait par ObservableObject + @Published, injecté via .environmentObject(_:) et lu via @EnvironmentObject. Le principe est identique — un objet de référence partagé, observé automatiquement — mais la macro @Observable (framework Observation, iOS 17+) suit les propriétés individuellement lues par chaque vue plutôt que d'invalider toute vue qui observe l'objet entier : une vue qui ne lit que currentSong ne se redessine pas quand seul isPlaying change.

Injecter et lire : .environment(_:) et @Environment(Type.self)

RootTabView (Leçon 1) possède l'unique instance de PlayerState et l'injecte au niveau du TabView :

struct RootTabView: View {
    @State private var player = PlayerState()

    var body: some View {
        TabView {
            DiscoverView()
                .tabItem {
                    Label("Découvrir", systemImage: "book.closed.fill")
                }

            LibraryView()
                .tabItem {
                    Label("Bibliothèque", systemImage: "music.note.list")
                }
        }
        .environment(player)
        .overlay(alignment: .bottom) {
            if let song = player.currentSong, !player.isExpanded {
                MiniPlayerBar(song: song)
                    .padding(.bottom, 49)
            }
        }
        .fullScreenCover(isPresented: $player.isExpanded) {
            if let song = player.currentSong {
                FullScreenPlayerView(song: song)
            }
        }
    }
}

N'importe quelle vue à l'intérieur du TabView — même trois niveaux plus bas — récupère la même instance avec :

@Environment(PlayerState.self) private var player

Comme PlayerState est une classe, cette propriété n'a pas besoin d'être mutable pour que tu puisses modifier ce qu'elle référence : player.currentSong = song fonctionne directement, et toute vue qui lit currentSong ailleurs se met à jour.

⚠️ Deux mécanismes @Environment différents — ne pas les mélanger

@Environment recouvre en réalité deux mécanismes distincts qui partagent juste le nom du property wrapper, avec des clés de stockage totalement séparées dans EnvironmentValues :

  • @Environment(\keypath) — la forme historique (iOS 13+), utilisée par \.dismiss, \.colorScheme, \.locale. Elle lit une valeur à une clé précise, définie via une EnvironmentKey (avec une defaultValue obligatoire) et une propriété calculée sur EnvironmentValues. On peut définir ses propres clés ainsi — c'est ce que montre le tutoriel de Fatbobman — mais ça reste du boilerplate à écrire pour chaque type.
  • @Environment(Type.self) — la forme moderne (iOS 17+, framework Observation), utilisée dans cette leçon pour PlayerState. Elle lit directement par type, sans keypath ni EnvironmentKey à déclarer : injection avec .environment(instance), lecture avec @Environment(SonType.self).

Le point critique : ces deux mécanismes ne communiquent pas entre eux. .environment(player) (utilisé dans RootTabView plus haut) alimente exclusivement le slot par-type de PlayerState. Si un écran consommateur lit avec @Environment(\.player) (le slot par-keypath d'une clé personnalisée), il ne trouvera jamais cette valeur-là — il retombe systématiquement sur la defaultValue de la clé, déconnectée de l'instance réelle de RootTabView. C'est exactement la cause du crash : injection par type, lecture par keypath, deux tiroirs différents.

Le correctif : dans SongOptionsSheet, FullScreenPlayerView et MiniPlayerBar, remplace toute occurrence de @Environment(\.player) (et supprime la PlayerState-EnvironmentKey personnalisée si tu l'as ajoutée) par la syntaxe par type déjà utilisée dans cette leçon :

@Environment(PlayerState.self) private var player

Comme PlayerState est @Observable, la forme par type est strictement suffisante : aucune EnvironmentKey à écrire, aucune defaultValue à choisir. Garde le mécanisme par keypath réservé aux valeurs système (\.dismiss) ou aux cas où le type transporté n'est pas @Observable.

Câbler enfin le bouton de la Leçon 2

SongOptionsSheet lit player depuis l'environnement et dismiss depuis le contexte de présentation modale, pour fermer la feuille après avoir lancé la lecture :

struct SongOptionsSheet: View {
    @Environment(PlayerState.self) private var player
    @Environment(\.dismiss) private var dismiss
    let song: Song
    // ... @State existants inchangés (mode, singerName, adjustVolumes, pitch, tempo)

    var body: some View {
        ScrollView {
            VStack(alignment: .leading, spacing: 20) {
                // ... SongHeader, ModeCard, TextField, Toggle, Sliders inchangés

                Button("Ajouter à la file d'attente") { }
                    .buttonStyle(.borderedProminent)
                    .tint(.pink)
                    .frame(maxWidth: .infinity)

                Button("Jouer maintenant") {
                    player.currentSong = song
                    player.isExpanded = true
                    dismiss()
                }
                .buttonStyle(.bordered)
                .frame(maxWidth: .infinity)
            }
            .padding()
        }
    }
}

Trois lignes suffisent : on pose la chanson courante, on demande l'ouverture plein écran, on referme la feuille du dessous.

⚠️ Ça va planter au tap : réinjecter l'environnement à la frontière de la .sheet

DiscoverView n'a effectivement rien à changer — mais PlaylistDetailView (Leçon 3), si. En théorie, l'environnement posé sur le TabView de RootTabView devrait redescendre jusque dans SongOptionsSheet sans rien faire de plus : DiscoverView → NavigationStack → PlaylistDetailView (poussée via navigationDestination(for:)) → SongOptionsSheet (présentée via .sheet(item:)). En pratique, les présentations modales (.sheet, .fullScreenCover, .popover) déclenchées depuis une vue elle-même poussée par navigationDestination(for:) ont un angle mort connu : l'héritage implicite de l'environnement via @Environment(Type.self) ne traverse pas toujours cette double frontière (push + présentation modale) de façon fiable. C'est très probablement l'exact crash que tu observes.

Le correctif robuste — et une bonne pratique générale, pas juste un contournement ponctuel — consiste à réinjecter explicitement l'environnement au moment de la présentation, plutôt que de compter sur sa propagation implicite à travers une frontière modale :

struct PlaylistDetailView: View {
    let playlist: Playlist
    @Environment(PlayerState.self) private var player
    @State private var selectedSong: Song?

    var body: some View {
        VStack(spacing: 0) {
            PlaylistCoverHeader(playlist: playlist)

            List(playlist.songs) { song in
                Button {
                    selectedSong = song
                } label: {
                    SongRow(song: song)
                }
                .buttonStyle(.plain)
            }
            .listStyle(.plain)
        }
        .navigationTitle(playlist.title)
        .navigationBarTitleDisplayMode(.inline)
        .sheet(item: $selectedSong) { song in
            SongOptionsSheet(song: song)
                .environment(player)     // ← réinjection explicite, à ajouter
        }
    }
}

PlaylistDetailView lit d'abord player depuis son propre environnement (ça, ça marche : c'est la frontière de push, pas de présentation modale, qui n'est pas concernée par cet angle mort), puis le repasse explicitement à SongOptionsSheet avec .environment(player) sur le contenu de la feuille. Résultat : plus aucune dépendance à l'héritage implicite pour franchir la frontière .sheet.

Faut-il faire pareil pour .fullScreenCover dans RootTabView ?

Non, et c'est justement ce qui confirme le diagnostic : dans RootTabView, .environment(player) et .fullScreenCover(isPresented:) sont posés sur la même vue (le TabView), au même niveau — il n'y a ni push via navigationDestination, ni frontière intermédiaire à franchir avant la présentation modale. L'angle mort ne concerne que le cas précis d'une présentation modale déclenchée depuis une vue elle-même poussée par navigation.

Autre piège séparé : la Preview de la Leçon 2 n'a personne pour lui fournir l'environnement

SongOptionsSheet lit désormais @Environment(PlayerState.self) — et même une fois le correctif ci-dessus en place dans l'app réelle, la #Preview écrite en Leçon 2 reste cassée, pour une raison différente : elle l'instancie seule, sans passer par RootTabView ni par PlaylistDetailView :

#Preview {
    SongOptionsSheet(song: .init(
        title: "You Give Love a Bad Name",
        artist: "Bon Jovi",
        year: 1986,
        duration: "03:35",
        key: "Cm"
    ))
}

Une #Preview place la vue qu'on lui donne à la racine de son propre arbre, sans passer ni par RootTabView ni par le correctif de PlaylistDetailView ci-dessus — il n'existe aucun ancêtre pour fournir player. Résultat : @Environment(PlayerState.self) ne trouve rien, et SwiftUI arrête l'exécution avec la même erreur Fatal error: No Observable object of type PlayerState found. A View.environment(_:) for PlayerState may be missing as an ancestor of this view. — mais cette fois dans le canvas, pas dans l'app. Les deux crashs se ressemblent parce que c'est le même mécanisme (@Environment(Type.self) sans ancêtre pour le fournir), à deux endroits différents de l'arbre de vues.

Le correctif : injecter une instance fraîche de PlayerState directement dans la Preview, exactement comme RootTabView le fait pour l'app réelle :

#Preview {
    SongOptionsSheet(song: .init(
        title: "You Give Love a Bad Name",
        artist: "Bon Jovi",
        year: 1986,
        duration: "03:35",
        key: "Cm"
    ))
    .environment(PlayerState())
}
Règle générale : toute Preview d'une vue qui lit @Environment(MonType.self) doit l'injecter elle-même

Une #Preview ne fait jamais partie de la hiérarchie de vues de l'app — elle en construit une nouvelle, minimale, juste pour la vue prévisualisée. Ça vaut pour n'importe quel type lu via @Environment(Type.self) : dès qu'une vue en dépend, sa Preview doit lui fournir sa propre instance avec .environment(...), sinon le canvas plante immédiatement à l'ouverture — même si l'app tournant dans le simulateur, elle, fonctionne parfaitement (parce que là, RootTabView fournit bien l'environnement). C'est un piège fréquent : un crash en Preview ne veut pas toujours dire que l'app réelle est cassée.

.fullScreenCover — la variante plein écran de .sheet

Le lecteur doit couvrir tout l'écran, tab bar comprise — pas une feuille qui laisse dépasser le haut de l'écran précédent. .fullScreenCover(isPresented:) est le pendant exact de .sheet(isPresented:), avec une présentation modale plein écran plutôt qu'une carte :

struct FullScreenPlayerView: View {
    @Environment(PlayerState.self) private var player
    @Environment(\.dismiss) private var dismiss
    let song: Song

    var body: some View {
        VStack(spacing: 32) {
            Button {
                dismiss()
            } label: {
                Image(systemName: "chevron.down")
                    .font(.title3)
            }
            .frame(maxWidth: .infinity, alignment: .leading)

            RoundedRectangle(cornerRadius: 16)
                .fill(.quaternary)
                .frame(width: 260, height: 260)

            VStack(spacing: 4) {
                Text(song.title).font(.title2.bold())
                Text(song.artist).foregroundStyle(.secondary)
            }

            VStack(spacing: 8) {
                Slider(value: .constant(0.35))
                HStack {
                    Text("01:15")
                    Spacer()
                    Text("-" + song.duration)
                }
                .font(.caption)
                .foregroundStyle(.secondary)
            }

            HStack(spacing: 48) {
                Button { } label: {
                    Image(systemName: "backward.fill").font(.title)
                }
                Button {
                    player.isPlaying.toggle()
                } label: {
                    Image(systemName: player.isPlaying ? "pause.circle.fill" : "play.circle.fill")
                        .font(.system(size: 64))
                }
                Button { } label: {
                    Image(systemName: "forward.fill").font(.title)
                }
            }

            Spacer()
        }
        .padding()
    }
}

#Preview {
    FullScreenPlayerView(song: .init(
        title: "You Give Love a Bad Name",
        artist: "Bon Jovi",
        year: 1986,
        duration: "03:35",
        key: "Cm"
    ))
    .environment(PlayerState())
}

Le réflexe pris juste au-dessus s'applique dès l'écriture de cette Preview : comme FullScreenPlayerView lit aussi @Environment(PlayerState.self), on lui injecte tout de suite sa propre instance plutôt que d'attendre le crash.

Taper la flèche referme le plein écran (dismiss()) sans vider player.currentSong ni repasser isExpanded à true — isExpanded redevient false automatiquement puisque c'est justement ce booléen que dismiss() fait basculer côté .fullScreenCover(isPresented:). La chanson reste "en cours", donc le mini-lecteur réapparaît immédiatement.

Pourquoi le slider de progression est-il figé (.constant(0.35)) ?

Rappel du cadrage de la mission (MISSION.md) : pas de vrai moteur audio ici, uniquement l'UI. .constant(_:) crée un Binding en lecture seule qui affiche une valeur fixe sans jamais la faire varier — utile pour maquetter un contrôle sans lui brancher de vraie logique derrière. Le jour où un vrai lecteur audio existera, ce sera Binding<Double> vers sa position de lecture réelle, sans changer le reste de la vue.

Le mini-lecteur : une barre persistante au-dessus de la tab bar

Le mini-lecteur est un overlay posé sur le TabView lui-même (voir RootTabView plus haut), pas sur un onglet en particulier — c'est ce qui le fait rester visible même quand tu changes d'onglet, exactement comme le mini-lecteur d'Apple Musique.

struct MiniPlayerBar: View {
    @Environment(PlayerState.self) private var player
    let song: Song

    var body: some View {
        HStack(spacing: 12) {
            RoundedRectangle(cornerRadius: 6)
                .fill(.quaternary)
                .frame(width: 40, height: 40)

            VStack(alignment: .leading, spacing: 2) {
                Text(song.title).font(.subheadline.bold())
                Text(song.artist).font(.caption).foregroundStyle(.secondary)
            }

            Spacer()

            Button {
                player.isPlaying.toggle()
            } label: {
                Image(systemName: player.isPlaying ? "pause.fill" : "play.fill")
                    .font(.title3)
            }
            .buttonStyle(.plain)
        }
        .padding(10)
        .background(.regularMaterial)
        .clipShape(RoundedRectangle(cornerRadius: 10))
        .padding(.horizontal, 8)
        .contentShape(Rectangle())
        .onTapGesture {
            player.isExpanded = true
        }
    }
}

.contentShape(Rectangle()) étend la zone cliquable à tout le rectangle de la barre, y compris les espaces vides entre les Text — sans lui, .onTapGesture ne réagirait que sur les zones réellement dessinées (le texte, l'image), un piège fréquent avec les HStack contenant des Spacer().
