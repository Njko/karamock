Leçon 32 · Multi-plateforme (2/N)

tvOS gagne ses propres contrôles : remplacer, pas seulement retirer

La Leçon 31 a fait compiler Karamock pour tvOS en désactivant cinq éléments avec #if os(iOS). Cette leçon reprend chacun des cinq, un par un, et cherche une vraie réponse tvOS — vérifiée avant d'être écrite, jamais devinée. Parfois cette réponse est "rien à faire, vérifié" ; deux fois, c'est un composant dédié tvOS, entièrement nouveau.

Pourquoi cette leçon : désactiver une fonctionnalité avec #if os(iOS) est la partie facile. La vraie compétence Tech Lead est de décider, plateforme par plateforme, quand construire un vrai équivalent, quand accepter une différence d'expérience assumée, et quand il n'y a tout simplement rien à construire — sans jamais confondre les trois par flemme ou par intuition non vérifiée.

Cinq restrictions, cinq réponses — pas cinq composants

Ordre du plus simple au plus complexe. Chaque section cite la doc Apple vérifiée avant tout code.

1. Titre de navigation — PlaylistDetailView.swift — aucune alternative n'existe, vérifié

La .navigationBarTitleDisplayMode(_:) retirée en Leçon 31 n'a pas d'équivalent tvOS. Recherche faite spécifiquement pour cette leçon : aucun modificateur tvOS-spécifique de contrôle d'affichage de titre n'existe dans la documentation SwiftUI. .navigationTitle(_:) lui-même est bien disponible sur tvOS (14.0+) et continue de fonctionner tel quel — mais sa page de documentation ne décrit un comportement spécifique que pour iOS/iPadOS/macOS/watchOS, pas pour tvOS. Absence de preuve n'est pas preuve d'absence en général, mais ici c'est le résultat le plus solide qu'on puisse obtenir : pas de mécanisme documenté à activer, donc rien à ajouter. Le code de la Leçon 31 reste inchangé :

.ignoresSafeArea(edges: .top)
#if os(iOS)
.navigationBarTitleDisplayMode(.inline)
#endif
.navigationTitle(playlist.title)

2. Style de champ texte — SongOptionsForm.swift — un défaut rendu explicite

.roundedBorder est confirmé absent de tvOS (Leçon 31). La documentation de .automatic (DefaultTextFieldStyle) confirme sa disponibilité tvOS 13.0+, décrite comme "le style recommandé pour la plateforme actuelle". Techniquement, omettre le modificateur produit déjà ce même résultat sur tvOS — la Leçon 31 aurait pu s'arrêter là. Mais un style implicite par omission est une information invisible dans le code ; l'écrire noir sur blanc documente que le choix a été fait consciemment, pas oublié :

TextField("Chanteur", text: $viewModel.singerName)
#if os(iOS)
    .textFieldStyle(.roundedBorder)
#else
    .textFieldStyle(.automatic)
#endif

3. Fond de carte — ModeCard.swift — Material, pas Color

Color(.secondarySystemBackground) échoue sur tvOS (Leçon 31, coupable identifié : UIColor.secondarySystemBackground). La .regularMaterial (type Material) est en revanche confirmée disponible tvOS 15.0+ — un vrai remplacement, pas une improvisation. Différence structurelle à gérer : Material est un effet de flou/vibrance, pas une couleur avec opacité réglable comme Color.purple.opacity(0.15) ; il ne peut donc pas à lui seul distinguer visuellement l'état sélectionné. Solution retenue : le Material reste constant, une bordure violette apparaît seulement quand isSelected est vrai (mécanisme SwiftUI standard, sans dépendance de plateforme) :

.padding()
#if os(iOS)
.background(isSelected ? Color.purple.opacity(0.15) : Color(.secondarySystemBackground))
#else
.background(.regularMaterial)
.overlay(
    RoundedRectangle(cornerRadius: 12)
        .stroke(.purple, lineWidth: isSelected ? 3 : 0)
)
#endif
.foregroundStyle(.primary)
.clipShape(RoundedRectangle(cornerRadius: 12))

4. Réglages par pas — tonalité, tempo, progression — FocusStepperTV, nouveau composant partagé

Slider n'existe sur aucune version de tvOS (Leçon 31), et ni lui ni Stepper n'ont d'équivalent natif. Avant de construire quoi que ce soit, trois faits vérifiés séparément :

  • Un Button SwiftUI ordinaire gère seul le focus et l'activation télécommande sur tvOS — sa documentation officielle l'affirme explicitement : "In tvOS, the user presses 'select' on an external remote, like the Siri Remote, while focusing on the button." Aucun .focusable() ni @FocusState nécessaire pour un simple bouton — ces deux mécanismes sont réservés à des vues personnalisées non-Button qui doivent gérer le focus elles-mêmes (confirmé par la doc de .focusable(_:)).
  • CardButtonStyle (.card), le style le plus "tvOS" qui existe (tvOS 14.0+ exclusivement, absent de toutes les autres plateformes), ne convient pas ici : sa documentation le décrit comme appliquant "a motion effect when a button has focus" — pensé pour des cartes de contenu à parcourir (posters, vignettes), pas pour un petit bouton icône +/-. .plain (tvOS 13.0+), déjà la convention du projet pour les boutons icône (voir MiniPlayerBar.swift), reste le bon choix ici aussi.
  • Aucun mécanisme officiellement documenté n'a été trouvé pour l'appui long/accélération (presser-maintenir pour aller plus vite) sur un contrôle SwiftUI tvOS. Décision explicite : chaque clic = un pas, rien de plus. Pas d'invention d'un geste non documenté.
// NOUVEAU — Views/Common/FocusStepperTV.swift
struct FocusStepperTV: View {
    let onDecrement: () -> Void
    let onIncrement: () -> Void
    var decrementDisabled = false
    var incrementDisabled = false

    var body: some View {
        HStack(spacing: 24) {
            Button(action: onDecrement) {
                Image(systemName: "minus.circle.fill")
            }
            .disabled(decrementDisabled)
            .accessibilityLabel("Diminuer")

            Button(action: onIncrement) {
                Image(systemName: "plus.circle.fill")
            }
            .disabled(incrementDisabled)
            .accessibilityLabel("Augmenter")
        }
        .font(.title2)
        .buttonStyle(.plain)
    }
}

Utilisation pour la tonalité (même geste pour le tempo, bornes -50...50, pas de 5) :

// SongOptionsForm.swift
HStack {
    Text("Tonalité")
    Spacer()
    Text("\(Int(viewModel.pitch))")
}
#if os(iOS)
Slider(value: $viewModel.pitch, in: -12...12, step: 1)
#else
FocusStepperTV(
    onDecrement: { viewModel.pitch = max(-12, viewModel.pitch - 1) },
    onIncrement: { viewModel.pitch = min(12, viewModel.pitch + 1) },
    decrementDisabled: viewModel.pitch <= -12,
    incrementDisabled: viewModel.pitch >= 12
)
#endif

Et pour la progression du lecteur plein écran, par pas de 10 secondes :

// FullScreenPlayerView.swift
VStack(spacing: 8) {
    #if os(iOS)
    Slider(value: $progress, in: 0...song.durationInSeconds)
    #else
    FocusStepperTV(
        onDecrement: { progress = max(0, progress - 10) },
        onIncrement: { progress = min(song.durationInSeconds, progress + 10) },
        decrementDisabled: progress <= 0,
        incrementDisabled: progress >= song.durationInSeconds
    )
    #endif
    HStack {
        Text("0:00")
        Spacer()
        Text("-" + song.duration)
    }
    .font(.caption)
    .foregroundStyle(.secondary)
}

Le Text("\(Int(viewModel.pitch))") existant au-dessus reste la seule source d'affichage de la valeur — FocusStepperTV ne duplique rien, il se contente d'incrémenter/décrémenter.

Écart relevé dans l'implémentation réelle : le pas du tempo

Comparé le 2026-08-02 avec l'implémentation réelle de Nicolas : le geste pour le tempo utilise viewModel.tempo - 1 / + 1 au lieu de -5/+5 — vraisemblablement un copier-coller du bloc tonalité sans ajuster le pas. Conséquence : sur tvOS, le tempo (plage -50...50) avance par pas de 1, dix fois plus fin qu'sur iOS où Slider(value: $viewModel.tempo, in: -50...50, step: 5) avançait par 5. Pas corrigé ici — juste signalé, pour que Nicolas ajuste onDecrement/onIncrement du tempo à des pas de 5 s'il veut retrouver la granularité d'origine (plus de clics nécessaires pour parcourir toute la plage, sinon).

5. Mini-lecteur — RootTabView.swift — MiniPlayerBarTV, nouveau composant dédié

.tabViewBottomAccessory n'a pas d'équivalent tvOS (Leçon 31). La leçon aurait pu réutiliser MiniPlayerBar tel quel — mais ce composant iOS repose sur un .onTapGesture posé sur toute la zone (pas un vrai Button) plus un Button imbriqué à l'intérieur pour play/pause. Or la doc Button citée au point 4 est claire : sur tvOS, l'interaction documentée passe par le focus + select sur un Button, pas par un onTapGesture générique. Et imbriquer deux Button l'un dans l'autre pose un problème indépendant du langage : le Focus Engine ne peut donner le focus qu'à un seul élément activable à la fois, donc le bouton interne imbriqué n'a de toute façon aucune garantie d'être atteignable séparément.

Décision de conception (un choix, pas une règle Apple citée) : MiniPlayerBarTV ne fait qu'une seule chose — focus + select ouvre le lecteur plein écran. Le vrai bouton play/pause reste exclusivement dans FullScreenPlayerView, qui l'a déjà.

// NOUVEAU — Views/Player/MiniPlayerBar/MiniPlayerBarTV.swift
struct MiniPlayerBarTV: View {
    @Injected(\.player) private var player
    let song: Song

    var body: some View {
        Button {
            player.isExpanded = true
        } label: {
            HStack(spacing: 16) {
                RoundedRectangle(cornerRadius: 6)
                    .fill(.quaternary)
                    .frame(width: 48, height: 48)
                    .accessibilityHidden(true)

                VStack(alignment: .leading, spacing: 2) {
                    Text(song.title).font(.headline)
                    Text(song.artist).font(.subheadline).foregroundStyle(.secondary)
                }

                Spacer()

                Image(systemName: player.isPlaying ? "pause.fill" : "play.fill")
                    .font(.title2)
            }
            .padding(20)
            .background(.regularMaterial)
            .clipShape(RoundedRectangle(cornerRadius: 16))
        }
        .buttonStyle(.plain)
        .accessibilityLabel("\(song.title), \(song.artist), \(player.isPlaying ? "en lecture" : "en pause")")
        .accessibilityHint("Ouvrir le lecteur plein écran")
    }
}

Branché via un .overlay manuel, puisqu'aucune API SwiftUI équivalente à l'accessoire iOS n'existe sur tvOS :

// RootTabView.swift

    }
}
Pourquoi pas de presser-maintenir pour accélérer le réglage ?

Vérifié spécifiquement pour cette leçon, via sous-agent spécialiste : aucune page de documentation Apple ne décrit de mécanisme officiel SwiftUI pour "maintenir le bouton select enfoncé pour accélérer" un contrôle par pas sur tvOS. Des discussions communautaires mentionnent UILongPressGestureRecognizer côté UIKit ou le comportement d'auto-répétition de MPRemoteCommandCenter pour le seek média — mais ce sont des sources secondaires, pas une API SwiftUI documentée pour ce cas précis. Plutôt que d'improviser un geste non vérifié, FocusStepperTV reste volontairement au clic simple. À réévaluer si Nicolas trouve un besoin réel une fois testé à la télécommande.

Scénario de vérification, étape par étape :
  1. Build (⌘B) sur le simulateur Apple TV : doit réussir sans erreur, comme à la fin de la Leçon 31, et le build iOS doit rester identique (aucune régression).
  2. Ouvre une fiche chanson : ModeCard affiche un fond flouté (Material) constant, avec une bordure violette uniquement sur la carte actuellement sélectionnée.
  3. Le champ "Chanteur" reste utilisable normalement (ouverture du clavier à distance standard de tvOS).
  4. Tonalité et tempo affichent chacun deux boutons +/- au lieu du Slider retiré ; navigue au focus dessus et clique "select" plusieurs fois : la valeur change par pas, les boutons se désactivent visuellement aux bornes (-12/12 et -50/50).
  5. Lance "Jouer maintenant" : une barre MiniPlayerBarTV apparaît en bas de l'écran Découvrir/Bibliothèque pendant la navigation, focus + select l'ouvre en plein écran.
  6. Dans le lecteur plein écran : les mêmes boutons +/- pilotent la progression par pas de 10 secondes, à la place du Slider retiré. Le bouton play/pause du lecteur plein écran continue de fonctionner comme avant — c'est le seul endroit où il existe sur tvOS.
  7. Ouvre le titre d'une playlist : aucun changement visuel attendu par rapport à avant cette leçon — confirme que l'absence d'alternative pour navigationBarTitleDisplayMode ne casse rien.
