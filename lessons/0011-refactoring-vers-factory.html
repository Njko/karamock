Leçon 11 · Architecture en couches (6/N)

Refactoring vers Factory : une librairie de DI compile-time safe

La Leçon 10 a construit un composition root à la main, avec seulement du SwiftUI. Cette leçon reprend exactement le même graphe de dépendances — player, downloadedSongsRepository, les deux UseCases — et le fait migrer vers Factory, pour voir concrètement ce qu'une librairie dédiée change, sur un exemple qu'on connaît déjà par cœur.

Pourquoi cette leçon : le composition root manuel de la Leçon 10 fonctionne très bien à l'échelle de ce projet (2 dépendances partagées). Mais reconnaître et manipuler une librairie de DI container-based fait partie du bagage attendu pour du Swift/Apple Platforms sur le marché actuel. Factory est la référence pour un projet SwiftUI neuf en 2026 : compile-time safe, pensée pour @Observable/@Environment, et explicitement alignée avec la concurrence stricte de Swift 6.

Installer Factory

Dans Xcode : File → Add Package Dependencies…, puis colle https://github.com/hmlongco/Factory.git. Sélectionne le produit FactoryKit pour la cible de l'app (le nom du produit n'est pas Factory tout court — la librairie l'a renommé pour éviter un conflit avec son propre type Factory<T>). Si tu ajoutes des tests plus tard, la cible de test aura aussi besoin du produit FactoryTesting.

Le Container remplace KaramockApp comme composition root

Chez Factory, chaque dépendance est une propriété calculée sur une extension de Container, qui retourne un Factory<Type> :

import FactoryKit

extension Container {
    var player: Factory<PlayerState> {
        self { PlayerState() }
            .singleton
    }

    var downloadedSongsRepository: Factory<DownloadedSongsRepository> {
        self { InMemoryDownloadedSongsRepository() }
            .singleton
    }

    var downloadSong: Factory<DownloadSongUseCase> {
        self { DownloadSongUseCase(repository: self.downloadedSongsRepository()) }
    }

    var fetchDownloadedSongs: Factory<FetchDownloadedSongsUseCase> {
        self { FetchDownloadedSongsUseCase(repository: self.downloadedSongsRepository()) }
    }
}

player et downloadedSongsRepository portent .singleton : une seule instance, partagée par toute l'app — c'est le rôle que jouait @State dans KaramockApp à la Leçon 10. Les deux UseCases, eux, restent au scope par défaut (.unique) : une nouvelle instance à chaque résolution. C'est exactement le même raisonnement qu'en Leçon 10 — des struct sans état, bon marché à reconstruire — seule la façon dont cette reconstruction est déclenchée change : avant, un appel explicite au point d'usage ; maintenant, une résolution via le container.

KaramockApp redevient minimal

@main
struct KaramockApp: App {
    var body: some Scene {
        WindowGroup {
            RootTabView()
        }
    }
}

Le composition root n'a pas disparu : il a déménagé. Ce n'était pas une propriété intrinsèque de KaramockApp — c'était le seul endroit du projet où InMemoryDownloadedSongsRepository() apparaissait. Maintenant c'est l'extension de Container qui joue ce rôle. Le point à retenir : le composition root est une responsabilité, pas un fichier précis — elle peut se déplacer quand l'outillage change.

Chaque vue déclare ce dont elle a besoin, directement

RootTabView — même correction qu'en Leçon 10, @Injected ne donnant pas plus de projection $ que @Environment : la ligne @Bindable var player = player reste nécessaire en tout premier dans body :

import FactoryKit

struct RootTabView: View {
    @Injected(\.player) private var player

    var body: some View {
        @Bindable var player = player  // doit être la première ligne de body

        TabView {
            DiscoveryView()
                .tabItem {
                    Label("Découvrir", systemImage: "book.closed.fill")
                }
            LibraryView()
                .tabItem {
                    Label("Bibliothèque", systemImage: "music.note.list")
                }
        }
        .overlay(alignment: .bottom) {
            if let song = player.currentSong, !player.isExpanded {
                MiniPlayerBar(song: song)
                    .padding(.bottom, 49)
            }
        }
        .fullScreenCover(isPresented: $player.isExpanded) {
            if let song = player.currentSong {
                FullScreenPlayerView(song: song)
            }
        }
    }
}

Remarque ce qui a disparu : plus aucun .environment(\.player, player). Avec @Environment, chaque vue ancêtre devait explicitement réinjecter la valeur pour que ses enfants la reçoivent. Avec @Injected, chaque vue résout directement depuis le Container partagé, où qu'elle se trouve dans la hiérarchie — plus besoin de propager manuellement à travers les vues intermédiaires.

SongOptionsSheet — c'est ici que le gain est le plus visible :

import FactoryKit

struct SongOptionsSheet: View {
    @Injected(\.player) private var player
    @Environment(\.dismiss) private var dismiss
    @Injected(\.downloadSong) private var downloadSong

    let song: Song
    @State private var downloadViewModel: SongDownloadViewModel?
    // … le reste de l'état du formulaire, inchangé

    var body: some View {
        // … inchangé
        .task {
            if downloadViewModel == nil {
                downloadViewModel = SongDownloadViewModel(song: song, downloadSong: downloadSong)
            }
        }
    }
}

Avant, SongOptionsSheet lisait downloadedSongsRepository depuis l'environnement puis construisait elle-même DownloadSongUseCase(repository: downloadedSongsRepository) — la vue devait donc savoir que ce UseCase a besoin d'un repository. Maintenant elle injecte directement downloadSong, déjà assemblé : la vue ne sait même plus que DownloadedSongsRepository existe. Le câblage a fini de migrer entièrement vers le Container.

LibraryView suit exactement le même principe avec fetchDownloadedSongs — je ne la réécris pas en entier, seule la ligne d'injection change : @Injected(\.fetchDownloadedSongs) private var fetchDownloadedSongs, puis LibraryViewModel(fetchDownloadedSongs: fetchDownloadedSongs) dans le .task.

Ce que "compile-time safe" veut dire concrètement

Si tu supprimes la propriété downloadSong de l'extension Container mais que SongOptionsSheet continue d'écrire @Injected(\.downloadSong), le projet ne compile plus : \.downloadSong n'existe pas sur Container, erreur immédiate. C'est très différent d'un container résolu au runtime par réflexion, où une dépendance non enregistrée compile sans problème et ne crashe qu'au moment précis où le code tente de la résoudre — potentiellement bien après le déploiement. Le README de Factory revendique explicitement cette propriété : "a factory for a given type must exist or the code simply will not compile". Factory 3.0 annonce aussi être conçu "under Strict Concurrency guidelines" — cohérent avec toute la rigueur Swift 6 déjà en place dans ce projet depuis la Leçon 7.

Previews et tests : remplacer une dépendance sans toucher au Container

Le Container partagé reste modifiable ponctuellement — utile pour un Preview ou un test qui veut éviter le comportement par défaut :

#Preview {
    Container.shared.fetchDownloadedSongs { MockFetchDownloadedSongsUseCase() }
    LibraryView()
}

Cette ligne remplace la fabrique par défaut juste pour ce Preview, sans modifier l'extension Container elle-même. C'est le même mécanisme qui rendra les tests de la prochaine leçon simples à écrire : chaque test peut substituer exactement la dépendance qu'il veut observer, sans reconstruire tout le graphe à la main.
