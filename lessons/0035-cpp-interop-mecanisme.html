Leçon 35 · Interop Swift/C++ (1/N)

Ajouter du C++ à Karamock : le mécanisme, avant le moteur

L'axe tvOS est clos (Leçons 31 à 34, trois correctifs mineurs mis de côté). Nouvel axe : un mini moteur de paroles en C++, intégré via l'interop Swift/C++. Cette leçon ne touche à aucune logique métier — pas encore à LyricsMapper.swift — elle prouve seulement que le mécanisme fonctionne : un appel C++ minimal qui compile et s'exécute depuis Swift, dans la target existante. Le vrai portage du timing simulé est la Leçon 36.

Le mécanisme : C++ Interoperability Mode, pas un pont Objective-C++ à l'ancienne

Karamock est aujourd'hui 100% Swift : aucun fichier .cpp/.mm, aucun bridging header. Le mode moderne pour mélanger Swift et C++ dans un même projet — C++ Interoperability Mode — est distinct de l'ancien pont via Objective-C++ : pas de fichier .mm intermédiaire à écrire, Swift peut appeler du C++ (presque) directement. Introduit avec Swift 5.9 / Xcode 15, largement en dessous du plancher actuel du projet (SWIFT_VERSION = 6.0, Xcode 26).

Dans Xcode : sélectionne le projet → la target Karamock → onglet Build Settings → recherche "interoperability" → réglage "C++ and Objective-C Interoperability" → passe de "Objective-C" (valeur par défaut) à "C++/Objective-C++". C'est la même bascule que documente la documentation officielle Swift.org pour ce mécanisme.

Un détail du projet qui prête à confusion : gnu++20 est déjà là

project.pbxproj contient déjà CLANG_CXX_LANGUAGE_STANDARD = "gnu++20", dans les deux configurations de build — avant même cette leçon. Ce n'est PAS un signe que l'interop C++ est déjà activée : c'est juste le dialecte C++ que le compilateur utiliserait si du C++ était compilé, un réglage par défaut du template Xcode, présent que le projet contienne du C++ ou non. Le vrai interrupteur est "C++ and Objective-C Interoperability" (SWIFT_OBJC_INTEROP_MODE), absent du projet avant cette leçon — confirmé en cherchant dans project.pbxproj.

Ajouter les fichiers C++

Convention utilisée dans le guide de démarrage officiel de swiftlang : une paire .hpp (déclaration) / .cpp (implémentation). Dans Xcode : clic droit sur le groupe Engine (nouveau, à créer) → Add Files to "Karamock"... → sélectionne les deux fichiers. Xcode détecte automatiquement le .cpp et l'ajoute à Build Phases → Compile Sources — aucune configuration manuelle supplémentaire à ce niveau.

// Engine/LyricsTimingCheck.hpp
int lyricsTimingCheck(int value);
// Engine/LyricsTimingCheck.cpp
#include "LyricsTimingCheck.hpp"

int lyricsTimingCheck(int value) {
    return value + 1;
}

Volontairement trivial — une fonction pure sur un entier, sans std::string ni std::vector. La Leçon 36 s'attaquera au vrai signal ambigu (bridging de String/std::string) ; ici, l'objectif est uniquement de prouver que le compilateur accepte le C++ dans la target et que Swift peut l'appeler.

Le pont vers Swift : pourquoi une target App a besoin d'un bridging header

Point vérifié précisément, parce que la doc officielle distingue deux cas très différents :

"App targets must use a bridging header to make the target's C++ types and functions available to Swift code in the same App target."

Une target Framework importe automatiquement le C++ déclaré dans ses headers publics — pas de bridging header nécessaire. Karamock est une target App (pas un framework), donc ce raccourci ne s'applique pas : il faut le même mécanisme qu'utilisait déjà le pont Objective-C historique, un bridging header, sauf qu'ici il pointe vers un header C++ au lieu d'un header Objective-C.

// Karamock-Bridging-Header.h
#include "Engine/LyricsTimingCheck.hpp"

Puis dans Xcode : Build Settings → "Objective-C Bridging Header" → chemin vers Karamock-Bridging-Header.h. Ce réglage (SWIFT_OBJC_BRIDGING_HEADER) existe depuis l'interop Objective-C classique — la Leçon 35 est la première fois que Karamock en a besoin, mais le mécanisme lui-même n'est pas nouveau.

Preuve minimale : un appel qui compile et s'exécute

Périmètre décidé pour cette leçon : un seul appel, temporaire, juste pour observer que ça fonctionne — pas une intégration dans l'UI définitive de Karamock.

// DiscoveryView.swift — ligne temporaire, à retirer une fois vérifié
VStack(alignment: .leading, spacing: 24) {
    Text("C++ check: \(lyricsTimingCheck(41))")
    PlaylistSection(playlists: mockPlaylist)
}

Si le mécanisme fonctionne, l'app affiche "C++ check: 42" au lancement — 41 passé à une fonction C++ réelle, compilée dans la target, le résultat revenant intact côté Swift. Cette ligne n'a aucune vocation à rester : elle disparaît dès que la Leçon 36 remplace LyricsTimingCheck par le vrai portage de LyricsMapper.

FactoryKit (SPM) va-t-il casser avec l'interop C++ activé ?

Recherche menée avant d'écrire cette leçon : la documentation officielle mentionne une règle de propagation pour les targets de Swift Package — activer l'interop C++ sur un target de package oblige les targets qui en dépendent à l'activer aussi, et c'est un changement cassant pour un package. Cette règle concerne des packages qui dépendent d'autres targets de packages, pas le cas de Karamock : ici, c'est l'app qui consomme FactoryKit (un simple import), pas l'inverse. Aucun conflit documenté trouvé pour ce sens de dépendance précis — mais c'est une inférence raisonnée à partir de la règle documentée, pas une garantie noir sur blanc d'Apple. Point à surveiller concrètement à la première compilation après activation : si FactoryKit ou un autre package SPM échoue à résoudre, ce sera un fait nouveau, pas une supposition de cette leçon.

Scénario de vérification, étape par étape :
  1. Dans Xcode : target Karamock → Build Settings → "C++ and Objective-C Interoperability" → C++/Objective-C++.
  2. Crée le groupe Engine, ajoute LyricsTimingCheck.hpp et LyricsTimingCheck.cpp ci-dessus.
  3. Crée Karamock-Bridging-Header.h à la racine du projet Swift, avec le #include ci-dessus.
  4. Renseigne Build Settings → "Objective-C Bridging Header" → chemin vers ce fichier.
  5. Build (⌘B) sur un simulateur iPhone et un simulateur Apple TV : les deux doivent réussir — ce mécanisme ne dépend d'aucune plateforme, contrairement à tout l'axe A.
  6. Ajoute temporairement la ligne Text("C++ check: \(lyricsTimingCheck(41))") dans DiscoveryView.swift, lance l'app : "C++ check: 42" doit s'afficher en haut de l'écran Découvrir, sur les deux plateformes.
  7. Vérifie qu'aucune dépendance SPM existante (FactoryKit) ne signale d'erreur de résolution après l'activation — point non garanti par la doc, signalé plus haut.
  8. Retire la ligne de Text temporaire une fois la preuve faite ; garde le reste (réglages, fichiers C++, bridging header) pour la Leçon 36.
