Le header extensible de la fiche playlist

En testant la Leçon 17 sur un vrai appareil, tu as repéré deux problèmes en un : le header de PlaylistDetailView n'était ni dans le scroll, ni sous la barre de statut. Cette leçon va plus loin que le simple correctif structurel — elle reproduit l'effet "extensible" (stretchy header) qu'on voit sur tes captures de référence (02-playlist-detail) : l'image grandit quand on tire l'écran vers le bas, puis défile normalement.

Pourquoi cette leçon : ce n'est pas une leçon théorique choisie à l'avance — elle existe parce que tu as testé l'app sur un vrai appareil et jugé le rendu "particulièrement moche". C'est exactement le genre d'écart entre "ça compile et ça a l'air correct dans le code" et "ça se sent bien en main" que seul un vrai test découvre, et que la mission demande de reproduire fidèlement (captures de référence dans reference/screenshots/).

Le point de départ : structurer le scroll

PlaylistDetailView aujourd'hui sépare le header (fixe) de la liste (son propre scroll) :

var body: some View {
    VStack(spacing: 0) {
        PlaylistCoverHeader(playlist: playlist)

        List(playlist.songs) { song in
            Button { selectedSong = song } label: { SongRow(song: song) }
                .buttonStyle(.plain)
        }
        .listStyle(.plain)
    }
    .navigationTitle(playlist.title)
    .navigationBarTitleDisplayMode(.inline)
    // …
}

List est remplacé par un ScrollView + VStack classique — rien ici n'utilise de fonctionnalité propre à List (sections, swipe actions) — pour que le header et les chansons ne fassent plus qu'un seul contenu défilant :

var body: some View {
    ScrollView {
        VStack(spacing: 0) {
            PlaylistCoverHeader(playlist: playlist)

            ForEach(playlist.songs) { song in
                Button { selectedSong = song } label: { SongRow(song: song).padding(.horizontal) }
                    .buttonStyle(.plain)
            }
        }
    }
    .ignoresSafeArea(edges: .top)
    .navigationBarTitleDisplayMode(.inline)
    // …
}

.ignoresSafeArea(edges: .top) se pose sur le ScrollView lui-même, pas sur le header : comme PlaylistCoverHeader est le tout premier élément du contenu défilant, c'est lui qui vient occuper l'espace ainsi libéré sous la barre de statut — rien d'autre dans la liste n'est affecté, puisque le header reste avant eux dans l'ordre du VStack.

L'effet extensible

Un modificateur réutilisable, à part — Views/Common/View+Stretchy.swift :

extension View {
    func stretchy() -> some View {
        visualEffect { effect, geometry in
            let currentHeight = geometry.size.height
            let scrollOffset = geometry.frame(in: .scrollView).minY
            let positiveOffset = max(0, scrollOffset)

            let newHeight = currentHeight + positiveOffset
            let scaleFactor = newHeight / currentHeight

            return effect.scaleEffect(
                x: scaleFactor, y: scaleFactor,
                anchor: .bottom
            )
        }
    }
}

visualEffect donne accès à la géométrie de la vue à chaque frame, sans passer par un GeometryReader qui casserait la mise en page environnante. geometry.frame(in: .scrollView).minY lit la position de la vue par rapport au ScrollView parent — .scrollView est un espace de coordonnées intégré à SwiftUI, pensé précisément pour ce cas. Tant que l'utilisateur scrolle normalement vers le bas, minY devient négatif ou nul : max(0, scrollOffset) ramène ça à zéro, donc scaleFactor reste à 1 — aucun effet. C'est seulement pendant un overscroll en haut (l'utilisateur tire l'écran vers le bas, au-delà de sa position de repos) que minY devient positif, et que la vue s'agrandit en proportion.

Appliqué à PlaylistCoverHeader :

struct PlaylistCoverHeader: View {
    let playlist: Playlist

    var body: some View {
        ZStack {
            LinearGradient(colors: playlist.gradientColors, startPoint: .topLeading, endPoint: .bottomTrailing)
                .frame(minHeight: 220)

            Text(playlist.title)
                .font(.title2.bold())
                .foregroundStyle(.white)
                .multilineTextAlignment(.center)
                .padding()
        }
        .stretchy()
    }
}

.stretchy() est posé sur le ZStack entier, pas seulement sur le dégradé — dégradé et titre grandissent ensemble pendant l'overscroll, exactement comme sur les captures de référence. Le ZStack conserve tout ce qui a été construit en Leçon 17 (la correction Dynamic Type) sans aucune modification : .stretchy() n'agit qu'au moment du geste de traction, un problème entièrement différent de la taille de police.

Pourquoi anchor: .bottom plutôt que .center ou .top

scaleEffect(anchor:) détermine le point fixe autour duquel la vue grandit. Avec .bottom, le bas du header reste exactement à sa place (juste au-dessus du premier SongRow) et toute la croissance se fait vers le haut — cohérent avec le fait que le header est ancré en haut de l'écran et que c'est la zone sous la barre de statut qui doit s'étendre. Avec .center ou .top, le bas du header se déplacerait aussi, et le premier SongRow sauterait visiblement à chaque geste de traction.

Ce qu'on laisse de côté pour l'instant

Tes captures de référence montrent aussi une barre de navigation transparente au repos, qui devient opaque seulement une fois le header scrollé hors de vue — le même genre d'effet que Spotify ou Apple Music. C'est un mécanisme séparé (suivre la position de scroll avec onScrollGeometryChange, piloter .toolbarBackground en conséquence), pas un prolongement direct de l'effet extensible. Volontairement laissé pour une prochaine leçon plutôt que d'alourdir celle-ci.
