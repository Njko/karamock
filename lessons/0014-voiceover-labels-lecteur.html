Leçon 14 · Accessibilité (1/N)

VoiceOver : nommer les boutons icône-seule du lecteur

Après l'architecture (Leçons 6 à 12) et les tests (Leçon 13), un nouvel axe : l'accessibilité. Premier point d'entrée, concret : MiniPlayerBar et FullScreenPlayerView ont quatre boutons qui ne sont composés que d'une icône — et VoiceOver n'a aujourd'hui aucun moyen de dire à l'utilisateur ce qu'ils font.

Pourquoi cette leçon : l'accessibilité était un axe confirmé pour la suite dès que l'architecture et les tests seraient posés (voir learning-records/0003-...). Ce n'est pas un sujet réservé aux développeurs : designers, product, QA — toute l'équipe partage la responsabilité de ne pas exclure une partie des utilisateurs. Mais ça suppose que le sujet soit discutable par tous, pas caché derrière une checklist de conformité que seuls les devs consultent. Savoir pointer un vrai écran, dire précisément ce que VoiceOver annonce aujourd'hui, et expliquer un correctif en une phrase simple — c'est ce qui rend un manquement d'accessibilité visible et discutable en équipe, pas seulement réparable en silence.

Ce que VoiceOver annonce aujourd'hui

Le bouton play/pause de MiniPlayerBar, tel qu'il existe sur ta machine :

Button {
    player.isPlaying.toggle()
} label: {
    Image(systemName: player.isPlaying ? "pause.fill" : "play.fill")
        .font(.title3)
}
.buttonStyle(.plain)

Ce n'est pas silencieux : les SF Symbols portent une étiquette d'accessibilité intégrée par le système, dérivée du nom du symbole. Mais cette étiquette décrit l'icône, pas l'action — et elle arrive dans la langue système de l'appareil, généralement en anglais. Résultat concret ici : un utilisateur VoiceOver sur un iPhone en français entendrait une description d'icône en anglais, au milieu d'une app entièrement rédigée en français ("Chanté par", "Ajouter à la file d'attente", etc.). Le même problème existe pour le bouton de fermeture (chevron.down) et les boutons piste précédente/suivante de FullScreenPlayerView.

Nommer par l'action, pas par l'icône

MiniPlayerBar — l'étiquette doit changer avec l'état, exactement comme l'icône :

Button {
    player.isPlaying.toggle()
} label: {
    Image(systemName: player.isPlaying ? "pause.fill" : "play.fill")
        .font(.title3)
}
.buttonStyle(.plain)
.accessibilityLabel(player.isPlaying ? "Mettre en pause" : "Lire")

FullScreenPlayerView — les quatre boutons du bas et le bouton de fermeture :

Button {
    dismiss()
} label: {
    Image(systemName: "chevron.down")
        .font(.title3)
}
.accessibilityLabel("Fermer")

// …

Button { } label: {
    Image(systemName: "backward.fill").font(.title)
}
.accessibilityLabel("Piste précédente")

Button {
    player.isPlaying.toggle()
} label: {
    Image(systemName: player.isPlaying ? "pause.circle.fill" : "play.circle.fill")
        .font(.system(size: 64))
}
.accessibilityLabel(player.isPlaying ? "Mettre en pause" : "Lire")

Button { } label: {
    Image(systemName: "forward.fill").font(.title)
}
.accessibilityLabel("Piste suivante")

Les boutons piste précédente/suivante n'ont pas encore d'action câblée (hors périmètre de la mission, Leçon 5) — ça n'empêche pas de leur donner un nom correct dès maintenant : un utilisateur VoiceOver qui explore l'écran au doigt doit pouvoir identifier chaque contrôle visible, que son action soit branchée ou non.

Vérifier sans attendre la prochaine leçon

Deux façons rapides de constater le changement : dans Xcode, Open Developer Tool → Accessibility Inspector, pointer un élément du Simulateur et lire le champ "Label". Ou directement sur le Simulateur/l'appareil : Réglages → Accessibilité → VoiceOver, puis naviguer l'écran au doigt — chaque bouton doit maintenant s'annoncer par son action ("Lire, bouton", "Fermer, bouton") plutôt que par le nom brut de l'icône.

Piège repéré, pas encore corrigé : le .onTapGesture de MiniPlayerBar

MiniPlayerBar tout entier réagit à .onTapGesture { player.isExpanded = true } pour ouvrir le lecteur plein écran — mais ce n'est pas un Button. Un .onTapGesture posé sur une HStack quelconque ne donne pas automatiquement le trait .isButton à l'élément : VoiceOver peut l'annoncer comme du simple contenu statique, sans indiquer qu'il est activable. Le correctif — .accessibilityAddTraits(.isButton), ou remplacer le geste par un vrai Button — est volontairement laissé pour une prochaine leçon, pour garder celle-ci concentrée sur un seul sujet : nommer ce qui est déjà un bouton.

Vérifie ta compréhension

1. Pourquoi le bouton play/pause de MiniPlayerBar n'est-il pas totalement silencieux pour VoiceOver, même sans accessibilityLabel ?

2. Pourquoi l'étiquette système d'un SF Symbol ne suffit-elle pas dans Karamock spécifiquement ?

3. Pourquoi .accessibilityLabel(player.isPlaying ? "Mettre en pause" : "Lire") plutôt qu'un texte fixe comme "Lecture" ?

4. Pourquoi donner un accessibilityLabel aux boutons piste précédente/suivante alors qu'ils n'ont pas encore d'action câblée ?
