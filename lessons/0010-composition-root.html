Leçon 10 · Architecture en couches (5/N)

Composition Root : un seul endroit pour construire les dépendances

Les Leçons 7 à 9 ont bâti la couche Domain (DownloadSongUseCase, FetchDownloadedSongsUseCase, DownloadedSongsRepository). Mais une question reste sans réponse claire : qui a le droit de construire l'implémentation concrète, InMemoryDownloadedSongsRepository() — et où ?

Pourquoi cette leçon : aujourd'hui, c'est RootTabView — une View — qui écrit @State private var downloadedSongsRepository = InMemoryDownloadedSongsRepository(). Une vue de la couche UI connaît donc le nom d'un type concret de la couche Data. C'est exactement le genre de fuite que la Dependency Rule interdit (mêmes principes qu'en Leçon 8, appliqués cette fois à la construction plutôt qu'à l'utilisation). Cette leçon identifie le composition root du projet : l'unique endroit autorisé à écrire le nom d'un type concret.

Deux mécanismes déjà en place, une question encore ouverte

Le projet utilise déjà deux formes d'injection de dépendances, et les deux sont correctes :

  • Injection par constructeur — DownloadSongUseCase(repository:), SongDownloadViewModel(song:downloadSong:) : chaque type reçoit ses dépendances explicitement, sans valeur par défaut cachée pour ce qui doit être partagé.
  • Injection par environnement — @Entry + @Environment(\.downloadedSongsRepository) : les vues profondément imbriquées (SongOptionsSheet, LibraryView) récupèrent l'instance partagée sans qu'on la fasse transiter manuellement à travers chaque initialiseur de vue intermédiaire.

Aucun des deux ne répond à une question pourtant essentielle : où, la toute première fois, l'instance concrète est-elle créée ? Actuellement, la réponse est RootTabView :

struct RootTabView: View {
    @State var player = PlayerState()
    @State var downloadedSongsRepository = InMemoryDownloadedSongsRepository()  // ⚠️ type concret, dans une View

    var body: some View {
        TabView { … }
            .environment(\.player, player)
            .environment(\.downloadedSongsRepository, downloadedSongsRepository)
            …
    }
}

RootTabView joue ici deux rôles à la fois : assembler les écrans de l'app et décider quelle implémentation du Repository utiliser. Le second rôle ne devrait pas appartenir à une View.

Le composition root : la seule porte d'entrée vers les types concrets

Un composition root est « l'endroit précis de l'application où les modules sont composés, c'est-à-dire instanciés et injectés avec toutes leurs dépendances » — un point unique, pas une notion diffuse répartie dans plusieurs fichiers. Dans une app SwiftUI, ce point unique existe déjà et n'a pas besoin d'être inventé : c'est le @main App, qui s'exécute une fois, avant qu'aucune vue n'existe.

@main
struct KaramockApp: App {
    @State private var player = PlayerState()
    @State private var downloadedSongsRepository: DownloadedSongsRepository = InMemoryDownloadedSongsRepository()

    var body: some Scene {
        WindowGroup {
            RootTabView()
                .environment(\.player, player)
                .environment(\.downloadedSongsRepository, downloadedSongsRepository)
        }
    }
}

RootTabView redevient une simple vue d'assemblage, sans plus aucune connaissance d'un type concret de la couche Data :

struct RootTabView: View {
    @Environment(\.player) private var player

    var body: some View {
        @Bindable var player = player  // doit être la première ligne de body

        TabView {
            DiscoveryView()
                .tabItem {
                    Label("Découvrir", systemImage: "book.closed.fill")
                }
            LibraryView()
                .tabItem {
                    Label("Bibliothèque", systemImage: "music.note.list")
                }
        }
        .overlay(alignment: .bottom) {
            if let song = player.currentSong, !player.isExpanded {
                MiniPlayerBar(song: song)
                    .padding(.bottom, 49)
            }
        }
        .fullScreenCover(isPresented: $player.isExpanded) {
            if let song = player.currentSong {
                FullScreenPlayerView(song: song)
            }
        }
    }
}
Pourquoi une ligne @Bindable var player = player au sommet de body

$player.isExpanded fonctionnait avant parce que player était un @State — seuls @State et @Bindable exposent une projection $. @Environment n'en a jamais eu : il donne seulement une valeur en lecture. La solution documentée pour obtenir malgré tout un Binding<Bool> vers player.isExpanded à partir d'une instance @Observable lue dans l'environnement est de la "ré-envelopper" localement avec @Bindable var player = player au tout début de body — cette ligne masque volontairement la propriété player d'origine par une version qui expose $player. Point d'attention réel : cette déclaration doit rester la toute première ligne de body, pas nichée dans un VStack ou un autre builder — la placer plus profondément provoque une erreur de link (Undefined symbol: unsafeMutableAddressor).

Le type de la propriété a aussi changé : downloadedSongsRepository: DownloadedSongsRepository (le protocole), pas InMemoryDownloadedSongsRepository (le type concret). Le composition root est le seul endroit où le nom concret apparaît une fois, à la construction — partout ailleurs, seul le protocole circule.

Pourquoi SongOptionsSheet et LibraryView continuent-ils de construire leurs UseCases eux-mêmes ?

On pourrait pousser le raisonnement jusqu'au bout et pré-construire aussi DownloadSongUseCase et FetchDownloadedSongsUseCase dans le composition root, dans un conteneur genre AppDependencies. Ce n'est pas fait ici, volontairement : ces UseCases sont des struct sans état, sans coût de construction, qui ne font qu'assembler une dépendance déjà partagée (le Repository récupéré via l'environnement). Les reconstruire au point d'usage ne duplique aucune donnée ni aucune logique — seule la ligne de câblage (DownloadSongUseCase(repository:)) est répétée deux fois, ce qui reste lisible avec seulement deux UseCases. Ajouter un conteneur AppDependencies maintenant serait de l'abstraction prématurée. Si le graphe de dépendances grossit significativement (plus de UseCases, des dépendances qui ne viennent pas toutes de l'environnement), ce calcul coût/bénéfice changera — mais ce n'est pas encore le cas.

Le piège de la valeur par défaut de @Entry

@Entry var downloadedSongsRepository: DownloadedSongsRepository = InMemoryDownloadedSongsRepository() a toujours une valeur par défaut — c'est ce qui protège les Previews de LibraryView du crash (Leçon 9). Le revers : si le composition root oubliait d'appeler .environment(\.downloadedSongsRepository, downloadedSongsRepository), l'app ne planterait pas non plus — elle utiliserait silencieusement une instance vide et déconnectée, jamais alimentée par les téléchargements réels. Contrairement à la forme par type (@Environment(Type.self), abandonnée en Leçon 4 précisément parce qu'elle plante sans ancêtre explicite), @Entry ne peut pas te protéger de cet oubli par un crash. La seule garde-fou ici, c'est la discipline : puisqu'il n'existe maintenant qu'un seul composition root, il n'y a qu'un seul endroit à vérifier — KaramockApp doit toujours injecter explicitement, jamais compter sur le défaut de @Entry en dehors des Previews et des tests.

Source primaire recommandée
Mastering Dependency Injection in iOS: Implementing a Composition Root (Azizbek Asadov) pour la définition et les bénéfices du composition root ; Managing Dependencies in the Age of SwiftUI (Lucas van Dongen) pour la confirmation que @main App est un point d'entrée valide pour ce rôle en SwiftUI.

Pourquoi apprendre le composition root "à la main" avant une librairie de DI : ce qu'on vient de construire — KaramockApp qui assemble deux dépendances partagées et les injecte via @Environment — n'est pas un brouillon jetable. C'est une stratégie de DI à part entière, suffisante tant que le graphe de dépendances reste petit (ici : 2 instances partagées, 2 UseCases construits au point d'usage). Aucune app SwiftUI n'a besoin d'un SDK pour ça.

Le calcul change à plus grande échelle : des dizaines d'écrans, de UseCases, de Repository à câbler à la main deviennent vite un fardeau répétitif, et c'est là que les équipes Swift adoptent des bibliothèques dédiées. Pour un projet SwiftUI neuf comme celui-ci, la référence actuelle est Factory — un Container dans lequel chaque dépendance est une propriété calculée (var myService: Factory<MyServiceType>), résolue via le property wrapper @Injected. Contrairement à des solutions plus anciennes basées sur la réflexion et la résolution au runtime, Factory est vérifié à la compilation : une dépendance sans fabrique enregistrée empêche le code de compiler, exactement dans l'esprit de rigueur que Swift 6 nous a fait adopter depuis la Leçon 7 (Sendable, isolation d'acteur).

La Leçon 11 reprend exactement le graphe construit ici (player, downloadedSongsRepository, les deux UseCases) et le fait migrer vers un Container Factory — tu pourras comparer les deux stratégies sur le même exemple plutôt que sur un projet jouet différent.
