Leçon 42 · Moteur de paroles en C++ (6/N)

Sortir de la vue de preuve : le moteur dans le vrai lecteur

Depuis la Leçon 37, EngineProofView a rempli son rôle — prouver, étape par étape, que le moteur C++ sait recevoir des paroles, dessiner du texte, avancer dans le temps et lisser une transition. Elle vivait dans l'écran Découvrir, avec trois lignes de test et sa propre horloge fabriquée de toutes pièces. Cette leçon la fait sortir de là : le rendu C++ s'installe dans FullScreenPlayerView, l'écran de destination réel, alimenté par les vraies paroles récupérées par FullScreenPlayerViewModel et par la progression de lecture qui existe déjà dans cet écran depuis bien avant l'arrivée du moteur C++. Aucun changement côté C++ cette leçon — uniquement du réarrangement et du branchement Swift.

Ce qui existe déjà côté écran réel, sans lien avec le moteur C++

FullScreenPlayerView affiche des paroles depuis la Leçon 5, bien avant que le moteur C++ n'existe — avec sa propre LyricsView SwiftUI (défilement de Text) et sa propre notion du temps qui passe :

// État avant cette leçon — FullScreenPlayerView.swift
@State private var progress: TimeInterval = 0
private let timer = Timer.publish(every: 0.5, on: .main, in: .common).autoconnect()
...
LyricsView(lyrics: viewModel?.lyrics ?? placeholderLyrics, currentTime: progress)
    .frame(height:160)
...
.onReceive(timer) { _ in
    guard player.isPlaying, progress < song.durationInSeconds else { return }
    progress += 0.5
}

progress avance déjà, toutes les 0,5 seconde, tant que la lecture est active — une horloge de lecture simulée, pas encore reliée à un vrai flux audio, mais bien réelle du point de vue de l'écran. C'est précisément ce qui change la donne pour cette leçon : contrairement à EngineProofView, qui n'avait aucune source de temps externe et devait donc fabriquer la sienne (TimelineView, Leçon 40), FullScreenPlayerView a déjà tout ce qu'il faut.

LyricsEngineView : la vue de preuve généralisée, pas réécrite

EngineProofView devient LyricsEngineView — déplacée de Views/Discovery/ vers Views/Player/FullScreenPlayer/, et généralisée : lyricsStore et currentTime deviennent des paramètres fournis par l'appelant, plus jamais fabriqués en interne.

// CORRECTION — Views/Discovery/EngineProofView.swift → Views/Player/FullScreenPlayer/LyricsEngineView.swift
struct LyricsEngineView: View {
    let lyricsStore: karamock.LyricsStore   // NOUVEAU — fourni par l'appelant, plus de testLines
    let currentTime: TimeInterval           // NOUVEAU — fourni par l'appelant, plus de startDate

    @Environment(\.displayScale) private var displayScale
    @State private var fontData: Data?
    @State private var size: CGSize = .zero   // NOUVEAU

    var body: some View {
        content
            .frame(maxWidth: .infinity, maxHeight: .infinity)
            .onGeometryChange(for: CGSize.self) { proxy in
                proxy.size
            } action: { newValue in
                size = newValue
            }
            .task {
                guard fontData == nil else { return }
                guard let fontURL = Bundle.main.url(forResource: "NotoSans-Regular", withExtension: "ttf")
                else { return }
                fontData = try? Data(contentsOf: fontURL)
            }
    }

    @ViewBuilder
    private var content: some View {
        if let fontData, size.width > 0, size.height > 0,
           let image = Self.render(pointSize: size, scale: displayScale, fontData: fontData,
                                    lyricsStore: lyricsStore, currentTime: currentTime) {
            Image(decorative: image, scale: displayScale)
                .interpolation(.none)
        } else {
            ProgressView()
        }
    }

    private static func render(pointSize: CGSize, scale: CGFloat, fontData: Data,
                                lyricsStore: karamock.LyricsStore, currentTime: TimeInterval) -> CGImage? {
        let pixelWidth  = Int((pointSize.width  * scale).rounded())
        let pixelHeight = Int((pointSize.height * scale).rounded())
        guard pixelWidth > 0, pixelHeight > 0 else { return nil }   // NOUVEAU

        var font = karamock.Font()
        guard loadFont(from: fontData, into: &font) else { return nil }

        var buffer = karamock.PixelBuffer()
        buffer.resize(Int32(pixelWidth), Int32(pixelHeight))
        buffer.fill(20, 20, 30)

        var renderer = karamock.TextRenderer()
        let page = karamock.LyricsPage()
        page.render(&buffer, font, &renderer, lyricsStore, currentTime)

        guard let base = buffer.__dataUnsafe() else { return nil }
        let pixels = Data(bytes: base, count: buffer.sizeInBytes())

        guard let provider = CGDataProvider(data: pixels as CFData),
              let colorSpace = CGColorSpace(name: CGColorSpace.sRGB)
        else { return nil }

        let bitmapInfo = CGBitmapInfo(
            rawValue: CGImageAlphaInfo.premultipliedLast.rawValue
                    | CGImageByteOrderInfo.order32Big.rawValue
        )

        return CGImage(
            width: pixelWidth, height: pixelHeight,
            bitsPerComponent: 8, bitsPerPixel: 32, bytesPerRow: Int(buffer.bytesPerRow()),
            space: colorSpace, bitmapInfo: bitmapInfo, provider: provider,
            decode: nil, shouldInterpolate: false, intent: .defaultIntent
        )
    }

    private static func loadFont(from data: Data, into font: inout karamock.Font) -> Bool {
        data.withUnsafeBytes { rawBuffer in
            guard let baseAddress = rawBuffer.bindMemory(to: UInt8.self).baseAddress else {
                return false
            }
            return font.loadFromMemory(baseAddress, rawBuffer.count)
        }
    }
}

Pourquoi TimelineView disparaît, pas seulement se déplace

Ce n'est pas un oubli : LyricsEngineView n'a plus de TimelineView ni de startDate du tout, contrairement à ce qu'on pourrait attendre en généralisant la Leçon 40. Une vue SwiftUI réévalue naturellement son body chaque fois qu'une de ses propriétés change — currentTime est désormais un let fourni par FullScreenPlayerView, qui change déjà lui-même toutes les 0,5 seconde via son propre Timer.publish établi bien avant cette leçon. Réintroduire une horloge indépendante dans LyricsEngineView ne ferait pas qu'être redondant : ça donnerait à l'écran deux notions du temps qui passe, sans aucune garantie qu'elles restent synchronisées. Généraliser une vue de preuve, ici, veut dire retirer une machinerie devenue inutile, pas seulement ajouter des paramètres.

Mesurer l'espace réel : onGeometryChange, et l'ordre qui compte

EngineProofView utilisait un pointSize fixe (320×200, Leçon 37) — une taille choisie pour la démonstration, sans rapport avec un vrai écran. Dans FullScreenPlayerView, la zone de paroles ne contraint que la hauteur (.frame(height: 160)) ; la largeur doit remplir l'espace réellement disponible, qui varie selon l'appareil. PixelBuffer::resize a besoin de dimensions concrètes en pixels — il faut donc les mesurer, pas les inventer.

.onGeometryChange(for: CGSize.self) { proxy in
    proxy.size
} action: { newValue in
    size = newValue
}

onGeometryChange, pas GeometryReader : GeometryReader s'insère comme une vue à part entière qui s'étend pour occuper tout l'espace qu'on lui propose, ce qui complique la disposition des vues autour de lui — un défaut assez répandu pour être documenté comme tel dans la communauté SwiftUI. onGeometryChange se contente d'observer la géométrie sans influencer le layout, et rapporte sa valeur dès l'apparition de la vue — pas seulement lors d'un changement ultérieur, contrairement à .onChange(of:) qui a besoin de initial: true pour ce même comportement.

Détail qui casse tout si l'ordre est inversé : .frame(maxWidth: .infinity, maxHeight: .infinity) est appliqué à content avant .onGeometryChange, jamais après.

// Ordre qui compte
content
    .frame(maxWidth: .infinity, maxHeight: .infinity)   // 1. content s'étend d'abord
    .onGeometryChange(for: CGSize.self) { ... }          // 2. puis on mesure l'espace occupé

Sans cette expansion préalable, onGeometryChange mesurerait la taille naturelle de content à cet instant précis — celle, minuscule et centrée, d'un ProgressView() tant qu'aucune image n'existe encore — plutôt que l'espace réellement offert par le parent. Le résultat serait un PixelBuffer redimensionné à la taille d'un indicateur de chargement, pas à celle de la zone de paroles. L'ordre des modifiers détermine ce qui est mesuré, pas seulement ce qui s'affiche à l'écran.

Brancher les vraies données

lyricsStore existe déjà dans FullScreenPlayerViewModel depuis la Leçon 36, mais reste privé — rien à côté de lui ne peut le lire :

// CORRECTION — ViewModels/FullScreenPlayerViewModel.swift
private(set) var lyricsStore = karamock.LyricsStore()   // était : private var lyricsStore

Même principe déjà appliqué à lyrics (private(set) var lyrics, Leçon 36) : la lecture s'ouvre à l'extérieur, mais seule sendLyricsToEngine() — restée private — a le droit de le modifier, garantissant que son contenu reste synchronisé avec lyrics.

// CORRECTION — Views/Player/FullScreenPlayer/FullScreenPlayerView.swift
LyricsEngineView(lyricsStore: viewModel?.lyricsStore ?? karamock.LyricsStore(), currentTime: progress)
    .frame(height: 160)

viewModel?.lyricsStore ?? karamock.LyricsStore() reprend exactement le principe de secours déjà utilisé pour viewModel?.lyrics ?? placeholderLyrics avant cette leçon — sauf qu'ici, le repli est un LyricsStore vide plutôt qu'un jeu de paroles de démonstration. Une différence de comportement réelle, à ne pas laisser filer sans l'expliquer : voir plus bas.

Ce que cette intégration change, honnêtement

viewModel est assigné avant que loadLyrics() n'ait fini (self.viewModel = viewModel; await viewModel.loadLyrics(), établi bien avant cette leçon) — pendant cette fenêtre, lyricsStore est un LyricsStore tout juste construit, vide. LyricsPage::render (Leçon 39) interroge indexAtTime sur un store vide, reçoit npos, et ne dessine rien : le canvas reste uniment coloré, sans texte, le temps que loadLyrics() se termine. Avant cette leçon, LyricsView affichait immédiatement placeholderLyrics ("Chaque ligne a son propre horodatage"...) dans ce même intervalle — un vrai contenu visible, pas un canvas vide.

Cette régression reste étroite, pas permanente : sendLyricsToEngine() (Leçon 36) s'exécute après loadLyrics(), succès ou échec confondus — même les lignes de repli en cas d'erreur ("Connexion impossible. Réessayez", établies en amont de cette série de leçons) sont poussées dans lyricsStore comme n'importe quelle ligne réelle. Seule la fenêtre de chargement elle-même reste un canvas vide ; une fois loadLyrics() terminée, il y a toujours au moins une ligne à afficher, erreur ou pas. Ce trou de chargement est un gap réel, volontairement non comblé dans cette leçon — candidat naturel pour une leçon future, pas traité en passant ici.

Deux vues devenues inutiles

EngineProofView a été conçue comme une vue de preuve temporaire depuis sa toute première apparition (Leçon 37) — sa fonction, démontrer que le moteur fonctionne, est maintenant remplie par l'intégration réelle ci-dessus. La garder à côté dans DiscoveryView dupliquerait la même logique de rendu que LyricsEngineView, avec le risque bien réel qu'elles divergent silencieusement au fil des prochaines leçons :

// CORRECTION — Views/Discovery/DiscoveryView.swift

    ScrollView {
        VStack(alignment: .leading, spacing: 24) {
            PlaylistSection(playlists: mockPlaylist)   // EngineProofView() retirée
        }
        .padding(.top)

Views/Player/FullScreenPlayer/LyricsView.swift (le défilement Text de la Leçon 5) devient, lui aussi, du code mort : plus aucun appelant depuis que FullScreenPlayerView utilise LyricsEngineView. À supprimer plutôt qu'à laisser traîner — le garder entretiendrait une ambiguïté sur lequel des deux rendus de paroles fait réellement autorité dans l'app.

État réel de l'implémentation (comparé le 9 août 2026) : conforme exactement à ce qu'enseigne cette leçon — LyricsEngineView (structure, ordre .frame(maxWidth:maxHeight:.infinity) puis .onGeometryChange, garde pixelWidth > 0, pixelHeight > 0), le branchement dans FullScreenPlayerView, le retrait d'EngineProofView() de DiscoveryView, private(set) var lyricsStore, et la suppression de LyricsView.swift correspondent tous au vrai code. Aucun écart à corriger.
Scénario de vérification, étape par étape :
  1. Build (⌘B) sur un simulateur iPhone et un simulateur Apple TV.
  2. Ouvre l'écran Découvrir : plus aucune trace du moteur de paroles — seule la section playlists doit rester.
  3. Ouvre une chanson jusqu'au lecteur plein écran : la zone de paroles doit maintenant afficher le rendu C++ (fond sombre, texte rastérisé), pas le défilement Text d'avant.
  4. Lance la lecture : la ligne active doit changer et glisser au rythme de progress, exactement comme le faisait LyricsView avant cette leçon — mais rendu par le moteur C++.
  5. Fais pivoter l'appareil ou teste sur un iPad en largeur différente : la zone de paroles doit occuper toute la largeur disponible, pas une bande de 320 points fixe.
  6. Observe l'instant précis où l'écran s'ouvre, avant que les paroles ne soient chargées : le canvas doit rester vide un court instant, sans crash — le trou de chargement documenté plus haut, pas un bug à corriger ici.
