Tester LibraryViewModel avec Swift Testing

Six leçons (6 à 12) ont découplé les Vues des UseCases, des Repositories et maintenant des ViewModels eux-mêmes, via Container. Le bénéfice concret arrive ici : LibraryViewModel peut être testé sans lancer l'app, sans simulateur, en remplaçant juste ce qu'il faut dans le graphe de dépendances.

Pourquoi cette leçon : l'architecture en couches n'a de valeur que si elle rend le code plus facile à vérifier, pas seulement plus joli à lire. Cette leçon en fait la preuve : un seul test, une dizaine de lignes, aucune dépendance à un vrai Repository ou à SwiftUI pour valider que LibraryViewModel.refresh() fait ce qu'on attend de lui.

Créer la cible de tests

Dans Xcode : File → New → Target…, choisis Unit Testing Bundle, nomme-la KaramockTests. Depuis Xcode 16, Swift Testing est le framework sélectionné par défaut pour une nouvelle cible de tests (l'ancien XCTest reste disponible si besoin, mais on utilise Swift Testing ici).

Ajoute ensuite FactoryTesting aux dépendances de la cible KaramockTests (Project → KaramockTests → General → Frameworks and Libraries). Un point important, documenté par Factory lui-même : n'ajoute pas FactoryKit une seconde fois à la cible de tests — seul FactoryTesting y va, FactoryKit vient déjà avec la cible Karamock importée via @testable import Karamock. L'ajouter deux fois peut créer des fabriques dupliquées et un comportement indéterminé.

Un Repository factice pour les tests

DownloadedSongsRepository est un protocole — exactement ce qu'il faut pour lui substituer une implémentation de test, sur le même principe que MockSongDownloading (Leçon 6). Comme InMemoryDownloadedSongsRepository en production, on garde un actor : c'est un état partagé, potentiellement lu et modifié depuis plusieurs tests exécutés en parallèle (voir plus bas) — le raisonnement de la Leçon 9 sur struct/class/actor s'applique à l'identique ici.

@testable import Karamock

actor MockDownloadedSongsRepository: DownloadedSongsRepository {
    private var storage: [Song]

    init(songs: [Song] = []) {
        self.storage = songs
    }

    func songs() async -> [Song] {
        storage
    }

    func add(_ song: Song) async {
        storage.append(song)
    }
}

Ce fichier vit dans la cible de tests, pas dans Karamock — un mock n'a rien à faire dans le code livré à l'utilisateur. @testable import Karamock est ce qui donne accès à Song et DownloadedSongsRepository, deux types internal du module Karamock, sans avoir à faire vivre ce fichier dans ce module.

Piège Xcode : un fichier de test qui finit dans l'app livrée

Sans cet import, Xcode propose une solution qui compile aussi : ajouter MockDownloadedSongsRepository.swift à l'appartenance de cible (Target Membership) de Karamock en plus de KaramockTests. Ça compile, parce que le fichier fait alors littéralement partie du même module que Song — mais ça veut dire que ce mock se retrouve dans le binaire de l'app livrée à l'utilisateur, alors qu'il n'a de sens que pour les tests. Le bon réflexe : @testable import Karamock depuis la cible de tests, jamais une double appartenance de cible. Dans l'inspecteur de fichier Xcode, seule la case KaramockTests doit être cochée.

Le test

Le README de Factory le dit explicitement : "the mocking concept can also be used when writing unit tests" — remplacer une fabrique juste pour un test suit exactement le même mécanisme que pour un Preview (Leçon 11).

import Testing
import FactoryKit
import FactoryTesting
@testable import Karamock

@Suite(.container) // conteneur isolé, un par test
struct LibraryViewModelTests {

    @Test
    @MainActor
    func refreshLoadsDownloadedSongs() async {
        let song = Song(title: "Year of the Cat", artist: "Cat Stevens", year: 1976, duration: "6:38", key: "Bm")
        Container.shared.fetchDownloadedSongs {
            FetchDownloadedSongsUseCase(repository: MockDownloadedSongsRepository(songs: [song]))
        }

        let viewModel = Container.shared.libraryViewModel()
        await viewModel.refresh()

        #expect(viewModel.songs == [song])
    }

    @Test
    @MainActor
    func refreshWithNoDownloadedSongsLeavesLibraryEmpty() async {
        Container.shared.fetchDownloadedSongs {
            FetchDownloadedSongsUseCase(repository: MockDownloadedSongsRepository())
        }

        let viewModel = Container.shared.libraryViewModel()
        await viewModel.refresh()

        #expect(viewModel.songs.isEmpty)
    }
}

Deux ajustements par rapport à une intuition SwiftUI classique. D'abord, import FactoryKit est nécessaire en plus de FactoryTesting : ce dernier fournit le trait .container, mais Container et Factory eux-mêmes viennent de FactoryKit. Ensuite, chaque @Test porte @MainActor : libraryViewModel est une fabrique @MainActor dans KaramockContainer (Leçon 12), parce que LibraryViewModel l'est aussi — un test qui la résout doit donc lui-même être isolé sur le MainActor, sous peine d'erreur de compilation Swift 6. C'est la même règle de cohérence d'isolation qu'en Leçon 12, appliquée cette fois au code de test plutôt qu'à une Vue.

Aucun des deux tests ne construit LibraryViewModel à la main : chacun redéfinit fetchDownloadedSongs dans le Container, puis résout libraryViewModel — Factory assemble le reste (LibraryViewModel(fetchDownloadedSongs:)) exactement comme il le ferait dans l'app. C'est la même déclaration que dans KaramockContainer, juste avec la fabrique fetchDownloadedSongs temporairement remplacée pour ce test précis.

Pourquoi @Suite(.container) plutôt que rien du tout

Container.shared est partagé par défaut — sans .container, les deux tests ci-dessus se disputeraient la même instance de Container, et Swift Testing exécute les tests en parallèle par défaut. Le résultat serait indéterministe : selon l'ordre d'exécution, un test pourrait lire la fabrique fetchDownloadedSongs enregistrée par l'autre. .container, fourni par FactoryTesting, donne une instance de Container fraîche et isolée à chaque test — c'est ce qui permet de garder les tests parallèles plutôt que de les forcer en série.

Piège : Song et l'égalité par id

Une façon a priori tout aussi naturelle d'écrire l'assertion aurait été de reconstruire un Song identique directement dans le #expect, plutôt que de réutiliser la variable song déclarée plus haut :

#expect(viewModel.songs == [
    Song(title: "Year of the Cat", artist: "Cat Stevens", year: 1976, duration: "6:38", key: "Bm")
])

Ce test échouerait à tous les coups, pour une mauvaise raison. Song génère un UUID() aléatoire à chaque construction (Leçon 1), et le Hashable synthétisé compare aussi id. Deux Song construits séparément avec des champs identiques ne sont donc jamais égaux — même titre, même artiste, mais deux id différents. C'est précisément pour éviter ce piège que le test déclare song une seule fois et le réutilise des deux côtés : MockDownloadedSongsRepository(songs: [song]) pour peupler le mock, puis #expect(viewModel.songs == [song]) pour l'assertion — la même instance, jamais reconstruite.

Pourquoi ne pas plutôt réutiliser mockPlaylist ?

Le projet a déjà des données factices toutes prêtes : mockPlaylist, la constante définie dans Playlist.swift et utilisée par DiscoveryView. Il aurait été tentant d'écrire MockDownloadedSongsRepository(songs: [mockPlaylist[0].songs[0]]) plutôt que de construire un Song de toutes pièces dans le test.

C'est exactement ce que Gerard Meszaros appelle un Mystery Guest dans xUnit Test Patterns : un test qui dépend d'une donnée définie ailleurs, hors de sa propre portée. Le lecteur du test ne voit plus le lien de cause à effet entre la donnée et l'assertion — il doit aller lire Playlist.swift pour comprendre ce qui est vérifié. Pire : si quelqu'un modifie mockPlaylist plus tard pour une raison qui n'a rien à voir avec ce test (changer un titre affiché dans DiscoveryView, par exemple), le test peut se mettre à échouer — ou pire, à passer pour de mauvaises raisons — sans qu'aucune ligne du test elle-même n'ait changé.

L'alternative que Meszaros recommande s'appelle une Fresh Fixture : "each test method creates a test fixture for its own private use". C'est exactement ce que fait let song = Song(title: "Year of the Cat", …) dans ce test — une valeur locale, jetable, qui ne doit rien à personne d'autre dans le projet. Une donnée de production qui change ne doit jamais casser un test sans rapport ; une donnée de test qui change ne doit jamais casser autre chose que ce test.
