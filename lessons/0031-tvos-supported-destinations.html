Leçon 31 · Multi-plateforme (1/N)

Ajouter tvOS au projet : une cible, plusieurs destinations

Le cycle Nettoyage architecture est bouclé (Leçons 24 à 30). Nouvel axe : faire tourner Karamock sur Apple TV, tel quel, sans réinventer l'UI pour la télécommande. Cette leçon couvre le mécanisme d'ajout de plateforme et les erreurs de compilation réelles qu'il révèle sur l'existant — cinq, dans cinq fichiers différents, pas une seule ni deux.

Le mécanisme : Supported Destinations, pas une nouvelle cible

Karamock est une cible unique, créée avant Xcode 14, et uniquement destinée à iOS (IPHONEOS_DEPLOYMENT_TARGET = 26.5, SDKROOT = iphoneos). Le réflexe le plus intuitif — créer une seconde cible tvOS à côté, dupliquer les fichiers — est précisément ce que Xcode 14 a rendu inutile. Documentation officielle Apple, "Configuring a multiplatform app target" :

"To add a destination to a target, click the Add button (+) under Supported Destinations, and then select the destination from the pop-up menu... iOS, iPadOS, macOS, tvOS, and visionOS apps can share a single target."

Et confirmé dans les notes de version Xcode 14 : "Xcode 14 enables a single target to support multiple platforms and conditionally include dependencies, code, resources, and build settings for specific platforms." La documentation précise explicitement que ce mécanisme fonctionne aussi en partant d'une cible mono-plateforme déjà existante, pas seulement depuis le template "Multiplatform App" utilisé à la création d'un nouveau projet — exactement le cas de Karamock.

Dans Xcode : sélectionne le projet → la cible Karamock → onglet General → section Supported Destinations → bouton + → tvOS. Aucune nouvelle cible n'apparaît ; c'est la même cible qui gagne une destination supplémentaire.

Ce qui change concrètement dans les réglages de build

Une fois tvOS ajouté, certains réglages qui n'avaient qu'une seule valeur (comme le deployment target) deviennent conditionnels par plateforme — Xcode ajoute une ligne supplémentaire dans l'onglet Build Settings, sélectionnable via le menu déroulant "Any SDK" à côté de chaque réglage concerné. C'est l'effet documenté par Apple ; la forme exacte que ça prend dans project.pbxproj une fois enregistré n'est pas précisément documentée par Apple lui-même — pas la peine de la deviner, Xcode s'en charge à l'enregistrement. Pour un fichier entier spécifique à une plateforme (pas notre cas ici, mais bon à savoir), Apple recommande de le filtrer dans Build Phases → Compile Sources, colonne Filters, plutôt que du code conditionnel à l'intérieur du fichier.

Cinq erreurs de compilation, dans cinq fichiers différents

Ajouter la destination ne suffit pas à faire compiler l'app pour tvOS. Cinq endroits du code utilisent des API qui n'existent tout simplement pas sur cette plateforme — vérifiées une par une via la documentation Apple, pas supposées. Elles se regroupent en cinq causes distinctes, sur sept lignes au total (une seule cause, Slider, revient trois fois dans deux fichiers).

1. RootTabView.swift — .tabViewBottomAccessory :

TabView {
    DiscoveryView().tabItem { Label("Découvrir", systemImage: "book.closed.fill") }
    LibraryView().tabItem { Label("Bibliothèque", systemImage: "music.note.list") }
}
.tabBarMinimizeBehavior(.onScrollDown)
.tabViewBottomAccessory(isEnabled: player.currentSong != nil && !player.isExpanded) {
    if let song = player.currentSong, !player.isExpanded {
        MiniPlayerBar(song: song)
    }
}
.fullScreenCover(isPresented: $player.isExpanded) {
    if let song = player.currentSong { FullScreenPlayerView(song: song) }
}

La documentation officielle de tabViewBottomAccessory(isEnabled:content:) liste ses plateformes disponibles : iOS 26.1, iPadOS 26.1, Mac Catalyst 26.1 — aucune entrée tvOS. Ce n'est pas une limitation de version à rattraper plus tard : cette API n'existe pas du tout sur tvOS, quelle que soit la version.

.tabBarMinimizeBehavior(.onScrollDown), juste à côté, compile en revanche sans problème — sa documentation liste tvOS 26.0 parmi ses plateformes, ce qui surprend, puisque ce comportement concerne un concept de barre d'onglets en bas d'écran, absent sur tvOS (qui affiche ses onglets en haut). Ce n'est donc pas une vraie erreur de compilation. Dans l'implémentation réelle de Nicolas, elle est malgré tout regroupée sous le même #if os(iOS) que .tabViewBottomAccessory — un choix de simplicité (un seul bloc plutôt que deux), pas une nécessité technique. À retenir : ce regroupement est un choix de lisibilité, pas la conséquence d'une indisponibilité de l'API.

2. Discovery/PlaylistDetail/PlaylistDetailView.swift — .navigationBarTitleDisplayMode(.inline) :

La documentation officielle liste iOS 14.0, iPadOS 14.0, Mac Catalyst 14.0, visionOS 1.0, watchOS 8.0 — ni tvOS, ni même macOS. Le nom de l'API le trahit : c'est un concept de navigation bar UIKit qui n'a pas d'équivalent sur tvOS, où la navigation ne repose pas sur une barre en haut d'écran de ce type.

3. Discovery/PlaylistDetail/SongOptionSheet/ModeCard.swift — Color(.secondarySystemBackground) :

.background(isSelected ? Color.purple.opacity(0.15) : Color(.secondarySystemBackground))

Point à ne pas survoler : le coupable précis n'est pas l'initialiseur Color(uiColor:) lui-même — sa documentation le liste bien disponible sur tvOS (15.0, comme iOS/iPadOS/Mac Catalyst/watchOS). Le vrai blocage est l'argument : UIColor.secondarySystemBackground, dont la documentation ne liste qu'iOS/iPadOS 13.0, Mac Catalyst 13.1 et visionOS 1.0 — absent de tvOS. Le symbole qui échoue à compiler, ce n'est donc pas Color(uiColor:), c'est la couleur système passée en argument.

4. Discovery/PlaylistDetail/SongOptionSheet/SongOptionsForm.swift — .textFieldStyle(.roundedBorder) et deux Slider :

TextField("Chanteur", text: $viewModel.singerName)
    .textFieldStyle(.roundedBorder)
// ...
Slider(value: $viewModel.pitch, in: -12...12, step: 1)
// ...
Slider(value: $viewModel.tempo, in: -50...50, step: 5)

La .roundedBorder (RoundedBorderTextFieldStyle) liste iOS/iPadOS/Mac Catalyst 13.0, macOS 10.15, visionOS 1.0 — encore une fois pas de tvOS. Détail à part, sans lien avec tvOS mais bon à savoir : cette même documentation la marque obsolète depuis iOS 27.0, même sur les plateformes qui la supportent (remplacée par .bordered + textInputBorderShape(.roundedRectangle)) — hors périmètre de cette leçon, mais à surveiller pour une future leçon iOS.

La documentation officielle de Slider liste iOS, iPadOS, Mac Catalyst, macOS, visionOS, watchOS — tvOS n'apparaît jamais, à aucune version. Point à ne pas deviner à moitié : le réflexe naturel serait de remplacer Slider par Stepper sur tvOS, mais la documentation de Stepper ne liste pas non plus tvOS. Aucun contrôle natif SwiftUI de saisie numérique par plage n'existe sur tvOS — un vrai vide, pas une méconnaissance : il existe même des bibliothèques tierces dédiées (par ex. zattoo/TvOSSlider, une réimplémentation fondée sur le Focus Engine) précisément pour combler ce manque.

5. Player/FullScreenPlayer/FullScreenPlayerView.swift — un troisième Slider :

Slider(value: $progress, in: 0...song.durationInSeconds)

Exactement la même cause qu'au point 4 : la barre de progression du lecteur plein écran utilise elle aussi Slider, dans un fichier séparé. Trois lignes, deux fichiers, une seule cause documentée — pas la peine de la revérifier une troisième fois, mais on peut facilement passer à côté si on ne relit pas tout le module Player en cherchant spécifiquement ce symbole.

Et FactoryKit (@Injected) ?

Rien à faire de ce côté : le Package.swift de FactoryKit déclare explicitement .tvOS(.v13) dans ses platforms, à côté d'iOS/macOS/watchOS/visionOS/Mac Catalyst. Le graphe de dépendances (Container, @Injected) fonctionne sur tvOS sans aucun changement. Même chose pour @Observable/@Bindable (Observation framework, tvOS 17+), NavigationStack (tvOS 16+), sheet/fullScreenCover/ScrollViewReader/@ScaledMetric (tvOS 13-14+) : tous déjà compatibles avec la cible tvOS 13+ minimale qu'implique l'ajout de la destination. Les cinq points de friction réels sont ceux ci-dessus, pas une longue liste cachée.

Les correctifs — #if os(iOS)

Périmètre décidé pour cette leçon : faire tourner l'existant tel quel sur tvOS, pas construire une vraie interaction télécommande pour le mini-lecteur ou les réglages de tonalité/tempo. La correction la plus honnête est donc de conditionner ce qui n'existe pas sur tvOS, et de documenter ce qui reste à faire — pas de l'inventer maintenant.

// CORRECTION — RootTabView.swift
TabView {
    DiscoveryView().tabItem { Label("Découvrir", systemImage: "book.closed.fill") }
    LibraryView().tabItem { Label("Bibliothèque", systemImage: "music.note.list") }
}
#if os(iOS)
.tabBarMinimizeBehavior(.onScrollDown)
.tabViewBottomAccessory(isEnabled: player.currentSong != nil && !player.isExpanded) {
    if let song = player.currentSong, !player.isExpanded {
        MiniPlayerBar(song: song)
    }
}
#endif
.fullScreenCover(isPresented: $player.isExpanded) {
    if let song = player.currentSong { FullScreenPlayerView(song: song) }
}

Les deux modificateurs sont regroupés sous le même #if os(iOS), alors que seul .tabViewBottomAccessory l'exige réellement — .tabBarMinimizeBehavior compilerait tout seul sur tvOS (voir plus haut). Sur tvOS, aucun mini-lecteur persistant n'apparaît pendant la navigation — pas une régression, une limite assumée. Lire une chanson depuis "Jouer maintenant" ouvre quand même FullScreenPlayerView en plein écran normalement : ce chemin passe par fullScreenCover(isPresented: $player.isExpanded), complètement indépendant de l'accessoire retiré.

// CORRECTION — PlaylistDetailView.swift
.ignoresSafeArea(edges: .top)
#if os(iOS)
.navigationBarTitleDisplayMode(.inline)
#endif
.navigationTitle(playlist.title)
// CORRECTION — ModeCard.swift
.padding()
#if os(iOS)
.background(isSelected ? Color.purple.opacity(0.15) : Color(.secondarySystemBackground))
#endif
.foregroundStyle(.primary)

Sur tvOS, la carte de mode perd son fond coloré/gris conditionnel — un détail purement visuel, sans effet sur la logique de sélection (isSelected continue de piloter l'icône checkmark.circle.fill/circle juste au-dessus, elle-même indépendante de la plateforme).

// CORRECTION — SongOptionsForm.swift
TextField("Chanteur", text: $viewModel.singerName)
#if os(iOS)
    .textFieldStyle(.roundedBorder)
#endif
// ...
HStack {
    Text("Tonalité")
    Spacer()
    Text("\(Int(viewModel.pitch))")
}
#if os(iOS)
Slider(value: $viewModel.pitch, in: -12...12, step: 1)
#endif

Même geste pour le tempo. Pas de repli en Text "indisponible" ajouté ici : la valeur reste déjà lisible sur tvOS via le Text("\(Int(viewModel.pitch))") existant juste au-dessus (inchangé, ne dépend d'aucune plateforme) — seul le Slider disparaît, sans message de remplacement. Un vrai contrôle adapté à la télécommande (basé sur le Focus Engine, hors périmètre décidé pour cet axe) resterait à construire dans une leçon dédiée si Nicolas le demande plus tard.

// CORRECTION — FullScreenPlayerView.swift
VStack(spacing: 8) {
    #if os(iOS)
    Slider(value: $progress, in: 0...song.durationInSeconds)
    #endif
    HStack {
        Text("0:00")
        // ...
    }
}
Scénario de vérification, étape par étape :
  1. Dans Xcode : Projet → cible Karamock → General → Supported Destinations → + → tvOS.
  2. Sélectionne un schéma/simulateur Apple TV, build (⌘B) avant tout correctif : Xcode doit signaler des erreurs dans cinq fichiers — RootTabView.swift (.tabViewBottomAccessory), PlaylistDetailView.swift (.navigationBarTitleDisplayMode), ModeCard.swift (Color(.secondarySystemBackground)), SongOptionsForm.swift (.textFieldStyle(.roundedBorder) + deux Slider) et FullScreenPlayerView.swift (un troisième Slider) — les cinq causes distinctes annoncées plus haut, sept lignes au total.
  3. Applique les cinq correctifs #if os(iOS) ci-dessus.
  4. Build (⌘B) sur le simulateur Apple TV : doit réussir sans erreur, et le build iOS existant doit rester identique (aucune régression pour iPhone/iPad).
  5. Lance l'app sur le simulateur Apple TV : les onglets Découvrir/Bibliothèque s'affichent en haut d'écran (style tvOS natif de TabView, pas de code à changer pour ça).
  6. Ouvre une fiche chanson, appuie sur "Jouer maintenant" : le lecteur plein écran s'ouvre normalement, malgré l'absence de mini-lecteur et de barre de progression.
  7. Ouvre les options d'une chanson : vérifie que tonalité/tempo n'affichent plus de Slider — seule la valeur numérique déjà présente au-dessus reste visible, sans message de remplacement.
  8. Étape facultative : si tu sors .tabBarMinimizeBehavior(.onScrollDown) du bloc #if os(iOS), regarde si elle produit un effet visible en scrollant Découvrir sur tvOS — la documentation Apple ne précise pas ce point. Telle qu'elle est écrite aujourd'hui (regroupée avec .tabViewBottomAccessory), elle reste désactivée sur tvOS, donc rien à observer sans ce changement.
