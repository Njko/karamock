Leçon 27 · Nettoyage architecture (4/N)

Le service de téléchargement devient réel : throwing, container, annulation propre

La Leçon 26 a rendu l'annulation d'un téléchargement fiable de bout en bout. Il reste trois trous dans le même service : SongDownloading ne peut techniquement jamais échouer (DownloadState.failed est du code mort), MockSongDownloading est construit directement dans le container sans jamais être déclaré comme dépendance, et le mock étouffe silencieusement les annulations avec un try?. Cette leçon ferme les trois.

Ce que l'audit a trouvé

Trois lignes distinctes dans l'audit, toutes sur le même service :

  • "Aucune vraie implémentation de SongDownloading n'existe. SongDownloading n'est pas enregistré dans le container → non-swappable." (point #5)
  • "État .failed jamais atteint (SongDownloading non-throwing)" (section 3, point 5)
  • "try? avale CancellationError → boucle non stoppable" (section 3, point 3)

Une précision de périmètre avant de commencer : l'audit suggère aussi de "créer URLSessionSongDownloading" — une vraie implémentation réseau. Karamock n'a pas de véritable backend de téléchargement de chansons à interroger ; inventer une adresse d'API fictive n'apporterait rien et introduirait une API imaginaire dans le code. "Le service devient réel" dans cette leçon veut dire : toute la mécanique interne (déclaration, gestion des erreurs, annulation) devient celle d'un vrai service de production — pas qu'on simule un réseau qui n'existe pas.

1. Enregistrer SongDownloading dans le container

KaramockContainer.swift construit MockSongDownloading() directement à l'intérieur de la Factory de DownloadSongUseCase — le service n'existe nulle part en tant que dépendance déclarée :

// KaramockContainer.swift — ACTUEL
var downloadSong: Factory<DownloadSongUseCase> {
    self { DownloadSongUseCase(service: MockSongDownloading(), repository: self.downloadedSongsRepository()) }
}

Compare avec lyricsFetching, juste au-dessus dans le même fichier, qui suit déjà le bon pattern :

var lyricsFetching: Factory<LyricsFetching> {
    self { URLSessionLyricsFetching() }
}

SongDownloading doit recevoir exactement le même traitement — sa propre Factory, référencée via self.songDownloading() plutôt que construite en dur à l'intérieur d'une autre :

// CORRECTION — KaramockContainer.swift
var songDownloading: Factory<SongDownloading> {
    self { MockSongDownloading() }
}

var downloadSong: Factory<DownloadSongUseCase> {
    self { DownloadSongUseCase(service: self.songDownloading(), repository: self.downloadedSongsRepository()) }
}

Le comportement de l'app ne change pas d'un iota — MockSongDownloading() reste ce qui tourne en production, puisqu'il n'existe rien d'autre à mettre à sa place. Ce qui change, c'est que la dépendance est désormais nommée et remplaçable : un test, un futur service réel, ou une preview peuvent l'injecter par Container.shared.songDownloading.register { ... } sans toucher à downloadSong.

2. Rendre SongDownloading.download() throwing

AsyncStream<Double> ne peut, par construction, rien signaler d'autre qu'une valeur ou une fin — aucune erreur ne peut transiter par ce type. C'est pour ça que DownloadState.failed, déjà défini, ne peut jamais être atteint : rien dans la chaîne ne peut produire cet état.

// Domain/Interfaces/Services/SongDownloading.swift — ACTUEL
nonisolated protocol SongDownloading: Sendable {
    func download(_ song: Song) -> AsyncStream<Double>
}

Le type qui permet de signaler un échec dans un flux existe dans la bibliothèque standard : AsyncThrowingStream. Une nuance à connaître avant de l'utiliser — ce type est paramétré par son type d'erreur (AsyncThrowingStream<Element, Failure>), mais tous ses initialiseurs publics imposent Failure == Error : il n'est aujourd'hui pas possible d'écrire AsyncThrowingStream<Double, DownloadError> avec un type d'erreur concret, contrairement aux erreurs typées (throws(LyricsError), qui déclarent précisément quel type d'erreur peut sortir) déjà utilisées ailleurs dans ce projet pour fetchLyrics. Ce n'est pas un choix de style ici, c'est une limitation actuelle de la bibliothèque standard — une évolution est réclamée depuis 2024, toujours pas livrée.

// CORRECTION — Domain/Interfaces/Services/SongDownloading.swift
nonisolated protocol SongDownloading: Sendable {
    func download(_ song: Song) -> AsyncThrowingStream<Double, Error>
}

DownloadSongUseCase doit suivre exactement le même changement de type, et laisser l'erreur traverser sans traitement particulier : elle est simplement retransmise au consommateur :

// Domain/Use Case/DownloadSongUseCase.swift — CORRECTION
func callAsFunction(_ song: Song) -> AsyncThrowingStream<Double, Error> {
    AsyncThrowingStream { continuation in
        let task = Task {
            do {
                for try await progress in service.download(song) {
                    guard !Task.isCancelled else { break }
                    continuation.yield(progress)
                }
                guard !Task.isCancelled else { return }
                await repository.add(song)
                continuation.finish()
            } catch {
                continuation.finish(throwing: error)
            }
        }
        continuation.onTermination = { _ in task.cancel() }
    }
}

Le point à ne pas manquer : si service.download(song) lève une erreur, l'exécution saute directement au catch — repository.add(song) n'est alors jamais atteint, sans qu'un guard supplémentaire soit nécessaire pour ce cas. Le guard !Task.isCancelled, lui, reste nécessaire pour une raison différente et plus subtile, expliquée juste en dessous.

L'annulation d'un AsyncThrowingStream ne lève PAS d'erreur dans le catch

Piège à connaître avant d'aller plus loin : quand la Task qui itère un AsyncThrowingStream via for try await est annulée, l'itération ne lève pas de CancellationError dans un catch englobant. Franz Busch, de l'équipe Swift, l'explique noir sur blanc sur le forum Swift : "Returning nil on cancellation is a totally valid thing for AsyncSequences to do. In fact it is the only thing for AsyncThrowingStream to do since the stream's Failure type might be a specific error so it can't just throw a CancellationError." En clair : renvoyer nil à l'annulation est un comportement légitime, et c'est même le seul possible pour AsyncThrowingStream puisque son type d'erreur pourrait être trop spécifique pour accueillir une CancellationError générique. Concrètement : l'annulation fait sortir la boucle for try await silencieusement, exactement comme une fin normale du flux — sans passer par un catch. C'est pour cette raison précise que les deux guard !Task.isCancelled (dans la boucle et juste après) restent indispensables, même avec un flux devenu throwing : eux seuls distinguent "le flux s'est terminé normalement" de "l'itération a été abandonnée par annulation" — le langage ne fait pas cette distinction à ta place.

3. Le ViewModel distingue enfin succès, annulation et échec

// ViewModels/SongDownloadViewModel.swift — CORRECTION
func startDownload() {
    guard state == .notDownloaded || state == .failed else { return }
    state = .downloading(progress: 0)
    downloadTask = Task {
        do {
            for try await progress in downloadSong(song) {
                guard !Task.isCancelled else { return }
                state = .downloading(progress: progress)
            }
            guard !Task.isCancelled else { return }
            state = .downloaded
            downloadTask = nil
        } catch {
            state = .failed
            downloadTask = nil
        }
    }
}

Trois dénouements, désormais tous représentés : la boucle se termine normalement → .downloaded ; la Task est annulée → sortie silencieuse, les deux guard empêchent toute mise à jour d'état (ni .downloaded, ni .failed — cancelDownload() a déjà mis .notDownloaded) ; le service lève une erreur → catch, .failed. cancelDownload() n'a besoin d'aucun changement, il ne fait que déclencher le deuxième cas.

4. Corriger le try? qui avale l'annulation dans le mock

MockSongDownloading doit à la fois adopter le nouveau type de retour et cesser d'ignorer silencieusement l'annulation :

// Services/MockSongDownloading.swift — ACTUEL
struct MockSongDownloading: SongDownloading {
    func download(_ song: Song) -> AsyncStream<Double> {
        AsyncStream { continuation in
            Task {
                for step in 1...10 {
                    try? await Task.sleep(for: .milliseconds(200))   // avale CancellationError
                    continuation.yield(Double(step) / 10)
                }
                continuation.finish()
            }
        }
    }
}

try? transforme toute erreur — y compris une CancellationError légitime — en nil silencieux : la boucle continue d'itérer et de yield comme si de rien n'était, même après une demande d'annulation. Le correctif distingue explicitement une annulation propre (on arrête, sans que ce soit un échec) d'une éventuelle vraie erreur (on la fait remonter) :

// CORRECTION — Services/MockSongDownloading.swift
struct MockSongDownloading: SongDownloading {
    var shouldFail = false

    func download(_ song: Song) -> AsyncThrowingStream<Double, Error> {
        AsyncThrowingStream { continuation in
            Task {
                do {
                    for step in 1...10 {
                        try await Task.sleep(for: .milliseconds(200))
                        if shouldFail, step == 5 {
                            throw SimulatedDownloadFailure()
                        }
                        continuation.yield(Double(step) / 10)
                    }
                    continuation.finish()
                } catch is CancellationError {
                    continuation.finish()
                } catch {
                    continuation.finish(throwing: error)
                }
            }
        }
    }
}

private struct SimulatedDownloadFailure: Error {}

try await Task.sleep(...) (sans ?) laisse l'erreur remonter jusqu'au do/catch qui l'entoure. Deux cas de sortie distincts : catch is CancellationError reconnaît une annulation propre et termine le flux normalement (continuation.finish(), sans erreur — une annulation n'est pas un échec métier) ; le catch générique restant couvre toute autre erreur, réelle celle-ci, et la fait remonter via continuation.finish(throwing:).

shouldFail (nouveau, false par défaut) ne change rien au comportement de production — MockSongDownloading(), tel qu'enregistré dans le container, continue de toujours réussir. C'est un levier qui permet de déclencher .failed à volonté pour le vérifier (scénario ci-dessous), et pour l'écrire en test à la Leçon 30 : sans lui, rien dans le mock actuel ne peut jamais réellement déclencher .failed, et l'affirmation "l'état est atteignable" resterait une affirmation sur le papier, jamais vérifiée.

Pourquoi ce code compile avec la concurrence stricte de Swift 6

Deux questions valent la peine d'être posées avant d'accepter ce code : AsyncThrowingStream<Double, Error> est-il bien Sendable, comme l'exige le protocole SongDownloading: Sendable ? Et une erreur quelconque (any Error) peut-elle traverser une frontière d'acteur sans problème ? Réponse aux deux, vérifiée dans le code source de la bibliothèque standard : AsyncThrowingStream est conforme à Sendable dès que son Element l'est (extension AsyncThrowingStream: @unchecked Sendable where Element: Sendable) — Double l'est, donc c'est réglé sans condition sur Failure. Et la raison pour laquelle aucune condition sur Failure n'est nécessaire : le protocole Error lui-même hérite de Sendable dans sa déclaration (public protocol Error: Sendable) — tout type conforme à Error, et donc any Error, est Sendable par construction. Une erreur qui traverse une frontière d'acteur ne pose donc jamais de problème de concurrence en soi.

Scénario de vérification, étape par étape :
  1. Build du projet (⌘B) : doit réussir sans erreur.
  2. Dans Xcode, vérifie que Container.shared.songDownloading existe et que downloadSong l'utilise via self.songDownloading() plutôt que de construire MockSongDownloading() directement.
  3. Lance un téléchargement normal : il doit se comporter exactement comme avant (0% à 100%, puis .downloaded) — shouldFail vaut false par défaut.
  4. Modifie temporairement Container.shared.songDownloading.register { MockSongDownloading(shouldFail: true) } (par exemple dans le #Preview de SongOptionsSheet) : lance un téléchargement, il doit s'arrêter à 40% et passer à .failed plutôt qu'à .downloaded.
  5. Remets shouldFail: false (ou retire l'override) avant de continuer — c'était uniquement pour vérifier le chemin d'échec.
  6. Lance un téléchargement puis annule-le avant la fin (Leçon 26) : l'état doit revenir à .notDownloaded, jamais passer par .failed.
