Leçon 23 · Gestion des erreurs (1/N)

Un type d'erreur dédié, plutôt qu'un catch générique

La Leçon 22 a délibérément laissé la gestion d'erreur sommaire : un seul catch, un seul message, quelle que soit la cause. C'était honnête pour une leçon centrée sur URLSession — mais la Leçon 22 se terminait justement en annonçant que ce n'était "pas ce qu'on ferait dans une app industrielle". Voici pourquoi, et comment le corriger proprement sur FetchLyricsUseCase.

Pourquoi cette leçon : un poste Swift/Apple Platforms senior suppose de savoir modéliser les erreurs, pas seulement les attraper — distinguer ce qui est attendu (une chanson sans paroles) de ce qui ne l'est pas (une panne réseau, une réponse qu'on ne sait plus décoder), décider quoi montrer à l'utilisateur et quoi journaliser pour soi-même. C'est une compétence transversale à toute l'architecture déjà posée (Leçons 6-12) et à la Leçon 22 qui vient de l'exposer concrètement.

Aujourd'hui : un seul symptôme pour trois causes très différentes

Le code actuel de FullScreenPlayerViewModel.loadLyrics() (Leçon 22) :

func loadLyrics() async {
    do {
        lyrics = try await fetchLyrics(for: song)
    } catch {
        lyrics = [LyricsLine(time: 0, text: "Paroles indisponibles pour le moment.")]
    }
}

Trois situations bien distinctes finissent pourtant dans la même case catch, avec le même message :

  • La chanson n'a simplement pas de paroles sur lyrics.ovh (l'API répond 404) — attendu, pas un bug, rien à corriger côté app.
  • Le réseau est indisponible — transitoire, l'utilisateur pourrait réessayer dans quelques instants.
  • La réponse ne correspond plus à ce que le code attend (JSON malformé, URL invalide) — un vrai problème, potentiellement une régression de l'API ou un bug côté app, qui mérite d'être investigué.

Aplatir les trois dans un seul message générique coûte deux fois : l'utilisateur ne sait jamais si réessayer a un sens, et le développeur perd toute visibilité sur le troisième cas — celui qui, contrairement aux deux autres, signale vraiment quelque chose à corriger.

Modéliser l'erreur : un type dédié plutôt qu'Error générique

Swift 6 permet de déclarer précisément quel type d'erreur une fonction peut lancer, via les "typed throws" (SE-0413) : throws(MonType) au lieu de throws. La fonction ne peut alors lancer que des instances de ce type précis, et le catch qui la reçoit connaît déjà son type concret — sans as? ni caste.

enum LyricsError: Error, Sendable {
    case invalidURL
    case notFound
    case network
    case malformedResponse
}

Volontairement, aucun cas n'embarque l'erreur technique d'origine (URLError, DecodingError…) — ce type ne sert qu'à décider quoi montrer et quoi journaliser, pas à transporter un diagnostic complet à travers toutes les couches. Le détail technique est journalisé au plus près de sa source (section suivante), là où il est encore riche de sens — pas remonté artificiellement jusqu'au ViewModel. Ce type vit dans Services/LyricsError.swift : bien qu'utilisé par le Repository, le UseCase et le ViewModel aussi, c'est le Service qui en a la connaissance la plus intime (c'est lui qui interprète le contrat HTTP ci-dessous), donc c'est un choix de rangement défendable — pas une obligation.

Le service : interpréter le contrat HTTP, pas seulement décoder le JSON

Le code de la Leçon 22 ignorait le code HTTP retourné par lyrics.ovh — un 404 traversait URLSession.shared.data(from:) sans lever la moindre erreur, et ne finissait en échec qu'indirectement, au moment du décodage JSON (le corps {"error": "No lyrics found"} ne correspond pas à LyricsResponse). Ça fonctionnait par accident. Le Service est le seul endroit qui connaît le contrat exact de cette API — c'est donc lui qui doit l'interpréter explicitement :

import Foundation
import os

protocol LyricsFetching: Sendable {
    func fetchLyrics(artist: String, title: String) async throws(LyricsError) -> String
}

private let lyricsFetcherLogger = Logger(subsystem: "fr.nicolaslinard.karamock", category: "Lyrics")

struct URLSessionLyricsFetching: LyricsFetching {
    func fetchLyrics(artist: String, title: String) async throws(LyricsError) -> String {
        guard let url = lyricsURL(artist: artist, title: title) else {
            throw .invalidURL
        }

        let data: Data
        let response: URLResponse

        do {
            (data, response) = try await URLSession.shared.data(from: url)
        } catch {
            lyricsFetcherLogger.error("Echec reseau lyrics.ovh : \(error)")
            throw .network
        }

        guard let httpResponse = response as? HTTPURLResponse else {
            throw .malformedResponse
        }

        if httpResponse.statusCode == 404 {
            throw .notFound
        }

        guard (200...299).contains(httpResponse.statusCode) else {
            lyricsFetcherLogger.error("Statut HTTP inattendu de lyrics.ovh: \(httpResponse)")
            throw .network
        }

        do {
            return try JSONDecoder().decode(LyricsResponse.self, from: data).lyrics
        } catch {
            lyricsFetcherLogger.error("Reponse lyrics.ovh non decodable: \(error)")
            throw .malformedResponse
        }
    }
}

Le protocole lui-même déclare désormais throws(LyricsError), pas seulement l'implémentation. throw .invalidURL, throw .notFound : la syntaxe abrégée du throw fonctionne comme return .someCase, parce que le type attendu (LyricsError) est déjà connu de la signature de la fonction. Remarque au passage : les messages passés à Logger ci-dessus évitent les accents — un choix qui n'a rien d'obligatoire techniquement, mais que tu retrouveras si tu compares avec ton propre fichier.

Pourquoi journaliser ici, et pas plus haut dans le Repository ou le ViewModel ?

Au moment où l'erreur technique est capturée (URLError, code HTTP, DecodingError), on a le maximum de détail disponible. Une fois convertie en LyricsError.network ou .malformedResponse, cette information est perdue — remonter l'erreur d'origine à travers Repository/UseCase/ViewModel juste pour la journaliser plus tard reviendrait à complexifier tout le chemin pour un seul appel à logger.error. Journaliser au plus près de la source, puis ne remonter qu'un type d'erreur propre et minimal : c'est le compromis qui coûte le moins cher en couches traversées.

Pourquoi .notFound n'est jamais journalisé

Un 404 de lyrics.ovh, ici, ne signale pas une panne : il dit juste "cette chanson n'a pas de paroles chez nous", une réponse parfaitement normale de l'API. La journaliser produirait du bruit dans les logs pour un cas qui n'a jamais besoin d'être investigué. Une bonne règle générale : ne journaliser que ce qui, en le relisant plus tard, pourrait légitimement déclencher une action — pas tout ce qui n'est pas un succès.

Propager le type d'erreur : Repository et UseCase

Chaque couche qui relaie l'appel change sa signature de throws à throws(LyricsError), sans rien changer d'autre :

nonisolated protocol LyricsRepository: Sendable {
    func lyrics(for song: Song) async throws(LyricsError) -> [LyricsLine]
}

actor CachedLyricsRepository: LyricsRepository {
    private let service: LyricsFetching
    private var cache: [Song.ID: [LyricsLine]] = [:]

    init(service: LyricsFetching) {
        self.service = service
    }

    func lyrics(for song: Song) async throws(LyricsError) -> [LyricsLine] {
        if let cached = cache[song.id] { return cached }

        let rawText = try await service.fetchLyrics(artist: song.artist, title: song.title)
        let lines = rawText.split(separator: "\n", omittingEmptySubsequences: false).map(String.init)
        guard !lines.isEmpty else { return [] }
        let interval = song.durationInSeconds / Double(lines.count)
        let result = lines.enumerated().map { index, text in
            LyricsLine(time: Double(index) * interval, text: text)
        }

        cache[song.id] = result
        return result
    }
}

struct FetchLyricsUseCase: Sendable {
    let repository: LyricsRepository

    nonisolated init(repository: LyricsRepository) {
        self.repository = repository
    }

    func callAsFunction(for song: Song) async throws(LyricsError) -> [LyricsLine] {
        try await repository.lyrics(for: song)
    }
}

try await service.fetchLyrics(...) compile sans rien ajouter : le Repository déclare le même throws(LyricsError) que le Service qu'il appelle, donc l'erreur traverse la frontière sans conversion. Si un jour un second Service (une autre API de paroles, par exemple) lançait un type d'erreur différent, le compilateur le signalerait immédiatement à cet endroit précis — impossible de l'oublier silencieusement.

Le ViewModel : trois réponses différentes pour trois causes différentes

func loadLyrics() async {
    do throws(LyricsError) {
        lyrics = try await fetchLyrics(for: song)
    } catch {
        switch error {
        case .notFound:
            lyrics = [LyricsLine(time: 0, text: "Paroles indisponibles pour cette chanson.")]
        case .network:
            lyrics = [LyricsLine(time: 0, text: "Connexion impossible. Réessayez")]
        case .invalidURL, .malformedResponse:
            lyrics = [LyricsLine(time: 0, text: "Paroles indisponibles pour le moment.")]
        }
    }
}

Dans la case catch, error est déjà connu comme un LyricsError concret — le switch qui suit porte directement sur ses cas, sans caste. Trois messages désormais, pas un seul : un pour la chanson sans paroles (rien à faire), un pour l'échec réseau (un réessai a du sens), et un message générique de repli pour les deux cas vraiment inattendus. Si LyricsError gagne un jour un nouveau cas, ce switch ne compile plus tant qu'il n'a pas été mis à jour — le compilateur empêche qu'un nouveau mode d'échec passe inaperçu.

Le catch ci-dessus doit rester inconditionnel pour être exhaustif

D'après la proposition SE-0413 elle-même : seul un catch sans condition (comme celui-ci, qui capture tout LyricsError dans error) rend le do...catch exhaustif — un catch let error as LyricsError ne suffirait pas, même en couvrant tous les cas connus. C'est le switch à l'intérieur du catch, pas le catch lui-même, qui doit énumérer tous les cas de l'enum.

Scénario de vérification, étape par étape :
  1. Ouvre "Bohemian Rhapsody" de Queen (playlist "Best Of Rock") : toujours un succès identique à la Leçon 22, aucune régression.
  2. Ouvre une chanson dont l'association artiste/titre est peu probable sur lyrics.ovh : le message doit maintenant être "Paroles indisponibles pour cette chanson." — différent de celui d'avant.
  3. Coupe le Wi-Fi/les données, puis ouvre une chanson jamais mise en cache : le message doit être "Connexion impossible. Réessayez" — visiblement différent du précédent, alors que les deux affichaient exactement le même texte en Leçon 22.
