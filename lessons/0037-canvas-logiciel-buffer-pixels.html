Leçon 37 · Moteur de paroles en C++ (1/N)

Le canvas logiciel : du buffer C++ à l'écran

Une première version de cette leçon explorait Metal via metal-cpp. Elle est remplacée par celle-ci : l'objectif du moteur n'est pas seulement de tourner sur iOS/tvOS, mais d'imiter une vraie bibliothèque C++ portée sur desktop et Web — et Metal, comme toute API graphique Apple, casserait cet objectif dès la première ligne. La solution retenue est celle qu'utilisent les moteurs 2D réellement portés partout (Skia en est l'exemple le plus connu) : un cœur 100% C++ standard qui dessine dans un buffer de pixels en mémoire, sans dépendance de plateforme, et une coquille de présentation différente par plateforme. Cette leçon prouve le mécanisme de bout en bout — un motif de test, pas encore de vrai texte, pas encore de boucle d'animation.

Le buffer, côté C++ : rien d'Apple à l'intérieur

PixelBuffer ne connaît ni Metal, ni Objective-C, ni même Xcode — c'est la condition pour qu'il compile un jour ailleurs que sur Apple :

// NOUVEAU — Engine/PixelBuffer.hpp
#pragma once
#include <cstddef>
#include <cstdint>
#include <vector>

namespace karamock {

class PixelBuffer {
public:
    PixelBuffer() = default;

    void resize(int width, int height);
    void fillTestPattern();

    int width() const;
    int height() const;
    int bytesPerRow() const;               // largeur × 4 — calculé côté C++, jamais recalculé côté Swift
    std::size_t sizeInBytes() const;
    const std::uint8_t* data() const;

private:
    int width_ = 0;
    int height_ = 0;
    std::vector<std::uint8_t> pixels_;   // RGBA8, zéro dépendance Apple
};

} // namespace karamock
// NOUVEAU — Engine/PixelBuffer.cpp
#include "PixelBuffer.hpp"

namespace karamock {

void PixelBuffer::resize(int width, int height) {
    width_  = width  > 0 ? width  : 0;
    height_ = height > 0 ? height : 0;
    pixels_.assign(static_cast<std::size_t>(width_) * height_ * 4, 0);
}

void PixelBuffer::fillTestPattern() {
    const int lastX = width_  > 1 ? width_  - 1 : 1;
    const int lastY = height_ > 1 ? height_ - 1 : 1;

    for (int y = 0; y < height_; ++y) {
        for (int x = 0; x < width_; ++x) {
            const std::size_t i = (static_cast<std::size_t>(y) * width_ + x) * 4;
            const bool light = (((x / 32) + (y / 32)) % 2) == 0;

            pixels_[i + 0] = static_cast<std::uint8_t>(x * 255 / lastX);  // R : dégradé horizontal
            pixels_[i + 1] = static_cast<std::uint8_t>(y * 255 / lastY);  // G : dégradé vertical
            pixels_[i + 2] = light ? 200 : 40;                             // B : damier 32 px
            pixels_[i + 3] = 255;                                          // A : opaque
        }
    }
}

int         PixelBuffer::width()       const { return width_; }
int         PixelBuffer::height()      const { return height_; }
int         PixelBuffer::bytesPerRow() const { return width_ * 4; }
std::size_t PixelBuffer::sizeInBytes() const { return pixels_.size(); }
const std::uint8_t* PixelBuffer::data() const { return pixels_.data(); }

} // namespace karamock

Le motif n'est pas décoratif, il est diagnostique : le dégradé rouge/vert révèle immédiatement une inversion largeur/hauteur, le damier révèle un mauvais bytesPerRow (l'image partirait en diagonale), et le fait que le damier soit porté par le canal bleu seul révèle une inversion de l'ordre des canaux (il apparaîtrait rouge au lieu de bleu). Un simple aplat de couleur ne prouverait aucun de ces trois points.

Le piège du jour : Swift renomme les pointeurs qu'il juge dangereux

Point vérifié précisément avant d'écrire quoi que ce soit, parce que le symptôme est déroutant si on ne sait pas à quoi s'attendre : buffer.data(), tel quel, ne compile pas côté Swift — l'auto-complétion ne propose même pas ce nom. La documentation officielle explique pourquoi :

"Member functions that return references, pointers, or certain structures/classes that contain references or pointers often return a reference that points inside of this, the object used to call the function. Such member functions are considered to be unsafe in Swift […] Swift automatically renames such member functions in order to emphasize their unsafety. Their Swift name is prefixed with two underscores and suffixed with Unsafe."

const std::uint8_t* data() const pointe à l'intérieur du std::vector que possède l'objet PixelBuffer — si ce dernier est détruit ou redimensionné pendant que Swift tient encore ce pointeur, c'est un accès mémoire invalide. Swift ne peut pas le vérifier statiquement, donc il rend le danger visible dans le nom lui-même : côté Swift, la méthode s'appelle __dataUnsafe(), et retourne un UnsafePointer<UInt8>!.

La documentation swift.org donne directement la parade recommandée :

"The recommended approach to calling member functions that return a reference or a view type with a dependent lifetime is to wrap them in a Swift API that returns a copy of the referenced object."

Concrètement : appeler __dataUnsafe() et copier immédiatement son contenu dans un Data Swift, en une seule opération — après cette ligne, plus aucune dépendance au buffer C++ :

guard let base = buffer.__dataUnsafe() else { return nil }
let pixels = Data(bytes: base, count: buffer.sizeInBytes())
// à partir d'ici : `pixels` est autonome, `buffer` peut être redimensionné ou détruit sans risque

Construire le CGImage : chaque paramètre compte

guard let provider = CGDataProvider(data: pixels as CFData),
      let colorSpace = CGColorSpace(name: CGColorSpace.sRGB)
else { return nil }

let bitmapInfo = CGBitmapInfo(
    rawValue: CGImageAlphaInfo.premultipliedLast.rawValue
            | CGImageByteOrderInfo.order32Big.rawValue
)

let image = CGImage(
    width: Int(buffer.width()),
    height: Int(buffer.height()),
    bitsPerComponent: 8,
    bitsPerPixel: 32,
    bytesPerRow: Int(buffer.bytesPerRow()),
    space: colorSpace,
    bitmapInfo: bitmapInfo,
    provider: provider,
    decode: nil,
    shouldInterpolate: false,
    intent: .defaultIntent
)

Trois choix qui, mal faits, produisent silencieusement une image déformée ou aux couleurs fausses plutôt qu'un crash — donc invisibles sans savoir précisément quoi vérifier :

  • CGColorSpace.sRGB, pas CGColorSpaceCreateDeviceRGB() : Apple déconseille explicitement l'espace dépendant du périphérique — les couleurs y varient d'un écran à l'autre. sRGB est l'espace standard, stable.
  • bytesPerRow vient de buffer.bytesPerRow(), jamais recalculé côté Swift : c'est le C++ qui sait comment ses lignes sont organisées en mémoire. Le jour où le moteur ajoutera un alignement de ligne (fréquent pour de vraies bibliothèques graphiques), Swift n'aura rien à changer.
  • CGImageByteOrderInfo.order32Big, pas CGBitmapInfo.byteOrder32Big : les deux valent la même chose aujourd'hui, mais CGBitmapInfo.byteOrder32Big est déprécié depuis la version 27.0 de la documentation Apple (aucun avertissement à la compilation avec le SDK actuel du projet, mais autant utiliser directement la forme pérenne). Sans cet indicateur d'ordre d'octets du tout, on obtient le bug classique "rouge et bleu inversés" — ici, le damier apparaîtrait rouge au lieu de bleu, exactement le genre d'erreur que le motif de test est censé révéler.

L'échelle d'affichage : pixels, pas points

Le moteur doit recevoir une taille en pixels physiques, pas en points SwiftUI — sinon l'image est rendue à une résolution plus basse que l'écran et paraît floue une fois étirée. @Environment(\.displayScale) donne ce facteur, disponible en SwiftUI depuis toujours (iOS/tvOS 13.0+) :

@Environment(\.displayScale) private var displayScale
UIScreen.main.scale existe encore, mais vient d'être marqué obsolète

Vérifié dans la documentation Apple actuelle : UIScreen.main est déprécié depuis iOS 26.0/tvOS 26.0 — exactement la cible de ce projet, ce n'est donc pas une mise en garde théorique. Citation : "Apple discourages the use of this symbol. Use a UIScreen instance found through context instead." Pour un facteur d'échelle spécifiquement, la documentation redirige vers traitCollection.displayScale de la vue concernée — mais en SwiftUI pur, sans UIViewRepresentable, @Environment(\.displayScale) couvre déjà ce besoin sans avoir à passer par UIKit.

Afficher l'image, et la preuve temporaire

// NOUVEAU — Views/Discovery/EngineProofView.swift
import CoreGraphics
import Foundation
import SwiftUI

struct EngineProofView: View {
    @Environment(\.displayScale) private var displayScale
    @State private var image: CGImage?

    private let pointSize = CGSize(width: 240, height: 135)

    var body: some View {
        Group {
            if let image {
                Image(decorative: image, scale: displayScale)
                    .interpolation(.none)
            } else {
                ProgressView()
            }
        }
        .frame(width: pointSize.width, height: pointSize.height)
        .task(id: displayScale) {
            image = Self.render(pointSize: pointSize, scale: displayScale)
        }
    }

    private static func render(pointSize: CGSize, scale: CGFloat) -> CGImage? {
        let pixelWidth  = Int((pointSize.width  * scale).rounded())
        let pixelHeight = Int((pointSize.height * scale).rounded())

        var buffer = karamock.PixelBuffer()
        buffer.resize(Int32(pixelWidth), Int32(pixelHeight))
        buffer.fillTestPattern()

        guard let base = buffer.__dataUnsafe() else { return nil }
        let pixels = Data(bytes: base, count: buffer.sizeInBytes())

        guard let provider = CGDataProvider(data: pixels as CFData),
              let colorSpace = CGColorSpace(name: CGColorSpace.sRGB)
        else { return nil }

        let bitmapInfo = CGBitmapInfo(
            rawValue: CGImageAlphaInfo.premultipliedLast.rawValue
                    | CGImageByteOrderInfo.order32Big.rawValue
        )

        return CGImage(
            width: Int(buffer.width()),
            height: Int(buffer.height()),
            bitsPerComponent: 8,
            bitsPerPixel: 32,
            bytesPerRow: Int(buffer.bytesPerRow()),
            space: colorSpace,
            bitmapInfo: bitmapInfo,
            provider: provider,
            decode: nil,
            shouldInterpolate: false,
            intent: .defaultIntent
        )
    }
}

.interpolation(.none) garde le damier net — sans lui, SwiftUI lisse l'image à l'affichage et les bords du damier deviennent flous, masquant justement ce que le motif est censé révéler. .task(id: displayScale) plutôt que .task seul : si l'échelle change (l'app passe d'un écran à un autre, rare mais possible), l'image se régénère à la bonne résolution.

Scénario de vérification, étape par étape :
  1. Build (⌘B) sur un simulateur iPhone et un simulateur Apple TV : les deux doivent réussir — PixelBuffer ne dépend d'aucune plateforme.
  2. Ouvre l'écran Découvrir : un rectangle 240×135 apparaît, dégradé rouge (horizontal) vers vert (vertical), avec un damier bleu/gris visible en surimpression.
  3. Vérifie que le damier est net, pas flou (.interpolation(.none) a un effet visible si on le retire temporairement pour comparer).
  4. Vérifie que le damier n'apparaît pas en rouge ou en violet — un damier rouge indiquerait un ordre de canaux inversé (BGRA au lieu de RGBA), à corriger dans bitmapInfo avant de continuer.
  5. Vérifie qu'aucune ligne du rectangle ne part en diagonale — un décalage progressif indiquerait un bytesPerRow incorrect.
  6. Sur simulateur @2x et @3x (change de modèle d'iPhone simulé) : vérifie que le motif reste net dans les deux cas — preuve que displayScale est bien pris en compte.
