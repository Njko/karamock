Leçon 26 · Nettoyage architecture (3/N)

Deux bugs de concurrence bien réels : Task orpheline et identité instable

La Leçon 19 a posé actor, nonisolated et Sendable comme des règles imposées par le compilateur. Les Leçons 22 et 25 ont montré ce qui se passe quand on les ignore : ça ne compile pas. Cette leçon est différente — les trois problèmes qu'elle corrige compilent très bien. Ce sont de vrais bugs, silencieux, que le compilateur Swift 6 ne peut pas voir.

Pourquoi cette leçon : un Tech Lead qui sait discuter d'annotations d'isolation ne suffit pas — il doit savoir repérer un bug de concurrence qui compile sans se plaindre. C'est exactement le genre de question qu'on pose en entretien technique senior : "ce code compile, où est le bug ?"

Bug #1 — La Task orpheline dans DownloadSongUseCase

Point #1 de l'audit, marqué BUG PROD : repository.add(song) est appelé sans condition après la boucle, même si le téléchargement a été annulé entre-temps.

// Domain/Use Case/DownloadSongUseCase.swift — ACTUEL
func callAsFunction(_ song: Song) -> AsyncStream<Double> {
    AsyncStream { continuation in
        Task {
            for await progress in service.download(song) {
                continuation.yield(progress)
            }
            await repository.add(song)   // ← appelé même après annulation !
            continuation.finish()
        }
    }
}

Le point à comprendre : cette Task n'est référencée nulle part. Personne ne peut l'annuler explicitement, et surtout — c'est le piège — l'annulation ne se propage pas toute seule à travers un AsyncStream. Si le code qui consomme ce stream arrête d'itérer (l'écran de téléchargement disparaît, la Task appelante côté View est annulée), la structured concurrency de Swift ne fait pas le lien automatiquement avec la Task créée à l'intérieur de la closure AsyncStream { } : cette Task est une tâche indépendante, en dehors de toute hiérarchie parent-enfant. Elle continue de tourner jusqu'au bout, télécharge la chanson en entier, et l'ajoute au repository — alors que plus personne n'observe le résultat.

AsyncStream.Continuation expose justement un point d'accroche pour ce cas : onTermination, un callback appelé quand le stream se termine — que ce soit parce que le producteur a fini normalement, ou parce que le consommateur a arrêté d'itérer. C'est le seul signal fiable pour savoir "plus personne n'écoute" ; à charge pour le code producteur de réagir, en général en annulant sa propre Task interne.

// CORRECTION — Domain/Use Case/DownloadSongUseCase.swift
func callAsFunction(_ song: Song) -> AsyncStream<Double> {
    AsyncStream { continuation in
        let task = Task {
            for await progress in service.download(song) {
                guard !Task.isCancelled else { break }
                continuation.yield(progress)
            }
            if !Task.isCancelled {
                await repository.add(song)
            }
            continuation.finish()
        }
        continuation.onTermination = { _ in task.cancel() }
    }
}

Trois ajouts, chacun avec un rôle précis : let task = Task { ... } garde une référence annulable ; continuation.onTermination = { _ in task.cancel() } relie enfin l'arrêt du consommateur à l'annulation du producteur ; et guard !Task.isCancelled / if !Task.isCancelled font que repository.add(song) ne s'exécute plus jamais après une annulation. Les trois sont nécessaires — retirer l'un des trois laisse le bug intact ou en ouvre un autre.

Bug #2 — La Task non trackée dans SongDownloadViewModel

Corriger DownloadSongUseCase ne suffit pas : pour que onTermination se déclenche un jour, il faut que quelque chose, côté consommateur, arrête réellement d'itérer. Or SongDownloadViewModel.startDownload() a exactement le même défaut, à l'autre bout du fil :

// ViewModels/SongDownloadViewModel.swift — ACTUEL
func startDownload() {
    guard state == .notDownloaded || state == .failed else { return }
    state = .downloading(progress: 0)
    Task {
        for await progress in downloadSong(song) {
            state = .downloading(progress: progress)
        }
        state = .downloaded
    }
}

Cette Task non plus n'est stockée nulle part. Il n'existe aucun moyen d'interrompre un téléchargement en cours — ni bouton d'annulation, ni nettoyage automatique si la vue disparaît. Résultat concret : le Bug #1 vient d'être corrigé sur le papier, mais tant que rien n'annule jamais la Task du ViewModel, onTermination ne se déclenche jamais non plus — le correctif reste sans effet en pratique. C'est le même anti-pattern que le nouveau document de référence docs/swift6-isolation-bonnes-pratiques.md signale explicitement : "Task { } sans référence stockée → impossible à annuler, fuite mémoire potentielle → private var task: Task<Void, Never>? + deinit { task?.cancel() }".

// CORRECTION — ViewModels/SongDownloadViewModel.swift
private var downloadTask: Task<Void, Never>?

func startDownload() {
    guard state == .notDownloaded || state == .failed else { return }
    state = .downloading(progress: 0)
    downloadTask = Task {
        for await progress in downloadSong(song) {
            guard !Task.isCancelled else { return }
            state = .downloading(progress: progress)
        }
        guard !Task.isCancelled else { return }
        state = .downloaded
        downloadTask = nil
    }
}

func cancelDownload() {
    guard case .downloading = state else { return }
    downloadTask?.cancel()
    downloadTask = nil
    state = .notDownloaded
}

Avec les deux bugs corrigés ensemble, la chaîne d'annulation existe enfin de bout en bout : cancelDownload() annule downloadTask → l'itération for await du ViewModel s'arrête (le guard !Task.isCancelled à l'intérieur ET après la boucle empêche toute mise à jour de state une fois l'annulation demandée) → le stream se termine côté consommateur → onTermination se déclenche dans DownloadSongUseCase → la Task interne est annulée → repository.add(song) ne s'exécute jamais pour un téléchargement abandonné.

Un écart avec ce qui était enseigné plus haut : pas de deinit. Nicolas a câblé l'annulation directement sur le cycle de vie de la vue plutôt que sur celui du ViewModel :

// Views/Discovery/PlaylistDetail/SongOptionSheet/SongOptionsSheet.swift
.onDisappear {
    downloadViewModel?.cancelDownload()
}

C'est un meilleur choix que le deinit initialement suggéré. downloadViewModel est un @State porté par SongOptionsSheet — sa désallocation (et donc l'appel à un éventuel deinit) dépend de la gestion interne du stockage @State par SwiftUI, qui peut la retarder (une vue peut rester en mémoire un moment après avoir disparu de l'écran, par exemple dans une pile de navigation). .onDisappear, lui, est un signal explicite et immédiat du framework : "cette vue vient de quitter l'écran". Annuler le téléchargement à ce moment précis, plutôt que d'attendre un deinit dont le timing n'est pas garanti, correspond mieux à l'intention réelle : arrêter le téléchargement dès que l'utilisateur quitte l'écran, pas "un jour, quand ARC le décide".

Bug #3 — L'identité instable de Song.id

Point #2 de l'audit, également marqué BUG PROD :

// Domain/Models/Song.swift — ACTUEL
struct Song: Identifiable, Hashable {
    let id = UUID()   // ← un nouvel UUID à CHAQUE instanciation
    let title: String
    let artist: String
    let year: Int
    let duration: String
    let key: String
}

let id = UUID() comme valeur par défaut n'est pas figé une fois pour toutes : cette expression s'exécute à chaque appel de l'initialiseur. Deux Song construits séparément avec exactement le même titre et le même artiste obtiennent deux id différents — et comme Hashable/Equatable synthétisés comparent toutes les propriétés stockées, ces deux valeurs ne sont ni égales, ni interchangeables, alors qu'elles représentent la même chanson.

Ce n'est pas théorique : deux endroits du projet dépendent aujourd'hui de cette identité pour fonctionner correctement :

  • SimpleDownloadedSongsRepository.add(_:) fait guard !storage.contains(song) else { return } pour éviter les doublons — une vérification qui ne peut réussir que si song est exactement la même valeur (même id) que celle déjà stockée.
  • CachedLyricsRepository indexe son cache par Song.ID ([Song.ID: [LyricsLine]]) — deux Song représentant la même chanson mais construits séparément produiraient deux entrées de cache distinctes, jamais réutilisées entre elles.

Avec mockPlaylist, ce risque reste aujourd'hui latent : c'est une constante globale let, évaluée une seule fois au lancement, donc chaque Song qu'elle contient garde le même id pendant toute la durée de vie de l'app. Le bug ne se manifeste que si un Song représentant une chanson déjà connue est reconstruit ailleurs — un futur décodage JSON depuis une vraie API, un test unitaire qui recrée une valeur "attendue" pour la comparer, une recherche qui retourne un nouvel objet pour une chanson déjà en bibliothèque. Le #Preview de FullScreenPlayerView l'illustre d'ailleurs sans le vouloir : il construit un Song(title: "Year of the cat", ...) à chaque rafraîchissement du preview, avec un id neuf à chaque fois.

La correction proposée par l'audit remplace l'UUID aléatoire par une identité déterministe, dérivée des champs qui identifient réellement une chanson — exactement ceux utilisés pour interroger l'API lyrics.ovh (fetchLyrics(artist:title:), Leçon 22) :

// CORRECTION — Domain/Models/Song.swift
struct Song: Identifiable, Hashable {
    var id: String { "\(artist.lowercased())-\(title.lowercased())" }
    let title: String
    let artist: String
    let year: Int
    let duration: String
    let key: String
}

id devient une propriété calculée (plus stockée) : deux Song avec le même artiste et le même titre partagent désormais toujours le même id, quel que soit le nombre de fois où ils sont construits séparément. Identifiable n'impose aucune contrainte sur le type de ID au-delà de Hashable — String convient aussi bien que UUID.

Un quatrième ajustement, pas anticipé : song.id devient soudain isolé au Main Actor

Ce changement de id — de propriété stockée à propriété calculée — a cassé la compilation de CachedLyricsRepository (Leçon 25), qui indexe son cache par Song.ID :

// Repositories/CachedLyricsRepository.swift — avant le fix Song.id
if let cached = cache[song.id] { return cached }   // compilait
// ...
cache[song.id] = result                             // compilait

// après le fix Song.id (id devenu computed) — ne compile plus sans await
if let cached = await cache[song.id] { return cached }
// ...
await cache[song.id] = result

C'est le même mécanisme général que la Leçon 25 (isolation par défaut au Main Actor), mais sa cause précise est différente et mérite d'être nommée correctement : ce n'est pas SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor seul qui explique la différence entre l'ancien id (stocké) et le nouveau (calculé) — cette proposition (SE-0466) rend en principe toute déclaration non annotée @MainActor, stockée ou calculée. C'est une proposition distincte, SE-0434, qui ajoute l'exception précise : les propriétés stockées d'un type Sendable, dans le module qui les définit, sont automatiquement traitées comme nonisolated — parce qu'elles ne sont qu'une simple projection mémoire, sans code à exécuter, donc sans risque de data race à protéger. Les propriétés calculées sont explicitement exclues de cette exception : leur corps exécute du code, que le compilateur ne peut pas garantir statiquement inoffensif, donc elles restent isolées au Main Actor par défaut.

Résultat : let id = UUID() (stocké, UUID est Sendable) était couvert par SE-0434 et accessible sans await depuis n'importe quel acteur. var id: String { ... } (calculé) ne l'est plus — il retombe sous la règle générale de SE-0466 et devient implicitement @MainActor, exactement comme durationInSeconds l'était avant sa correction en Leçon 22. La preuve est dans le même fichier : quelques lignes plus loin, song.durationInSeconds — nonisolated depuis la Leçon 22 — s'utilise sans await, juste à côté de song.id qui, lui, en réclame un.

Le code de Nicolas fonctionne tel quel — les deux await sont corrects et suffisants. Mais par cohérence avec le précédent déjà posé pour durationInSeconds, la correction la plus alignée avec la convention du projet serait de marquer id lui-même nonisolated plutôt que de faire porter la traversée de frontière à chaque site d'appel :

// Domain/Models/Song.swift — alternative recommandée
nonisolated var id: String { "\(artist.lowercased())-\(title.lowercased())" }

id ne lit que artist/title (deux String, Sendable) et n'a aucune raison métier de dépendre du Main Actor — un calcul pur ne devrait jamais forcer un await chez ses appelants. Cette annotation n'entre en conflit avec rien : le requirement id d'Identifiable n'est lui-même pas isolé, et nonisolated sur une computed property est autorisé depuis bien avant Swift 6 strict concurrency.

Pourquoi ce type de bug est invisible pour le compilateur Swift 6

Tout ce que les Leçons 22, 24 et 25 ont enseigné jusqu'ici — nonisolated, actor, Sendable — protège contre les data races : deux bouts de code qui touchent la même mémoire mutable depuis deux threads en même temps. Le compilateur Swift 6 est excellent pour détecter ça. Mais les trois bugs de cette leçon ne sont pas des data races : DownloadSongUseCase et SongDownloadViewModel compilent et s'exécutent sans jamais violer l'isolation d'un acteur — ils lancent juste une Task que personne ne relie à la structured concurrency environnante, ce qui est parfaitement légal en Swift. Et Song.id = UUID() ne casse aucune règle de concurrence non plus — c'est un bug de logique métier (l'identité d'une valeur), pas un bug de thread-safety. Le compilateur ne peut vérifier que ce qu'il modélise ; la cohérence d'une identité entre deux instances, ou la propagation d'une annulation à travers un pont manuel comme AsyncStream, restent hors de sa portée.

Scénario de vérification, étape par étape :
  1. Build du projet (⌘B) : doit réussir sans erreur.
  2. Lance un téléchargement, quitte l'écran avant la fin (ou appelle cancelDownload()) : la chanson ne doit pas apparaître dans la bibliothèque téléchargée.
  3. Place un breakpoint (ou un print) dans onTermination de DownloadSongUseCase : vérifie qu'il se déclenche bien quand le téléchargement est annulé côté ViewModel.
  4. Écris un test rapide (ou vérifie à la main dans le debugger) : deux Song(title: "Kashmir", artist: "Led Zeppelin", ...) construits séparément doivent maintenant avoir le même id.
  5. Relance un téléchargement déjà terminé une deuxième fois : storage.contains(song) doit désormais fonctionner correctement même si le Song vient d'un endroit différent du code.
  6. Dans CachedLyricsRepository.swift, vérifie les deux await ajoutés devant cache[song.id] — nécessaires tant que Song.id reste une propriété calculée sans nonisolated.
  7. Quitte SongOptionsSheet pendant un téléchargement en cours (swipe pour fermer la sheet) : vérifie que .onDisappear déclenche bien cancelDownload().
