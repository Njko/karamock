Leçon 30 · Nettoyage architecture (7/N)

Preuve par test : les bugs de concurrence de la Leçon 26 ne reviendront pas

La Leçon 13 a posé Swift Testing et Factory comme outil de vérification. La Leçon 26 a corrigé trois bugs silencieux — une Task orpheline, un identifiant instable — que le compilateur Swift 6 ne pouvait pas voir. Cette leçon relie les deux : trois tests, chacun écrit pour qu'un futur refactor malheureux le fasse échouer immédiatement, plutôt que de laisser le bug revenir sans bruit.

Pourquoi cette leçon : "j'ai corrigé ce bug" est une phrase faible en entretien Tech Lead. "J'ai corrigé ce bug, et voici le test qui échoue si quelqu'un le réintroduit" en est une autre. Cette leçon referme le cycle Nettoyage architecture (Leçons 24 à 30) sur exactement cette distinction.

Test 1 — l'identité de Song reste stable

Bug #3 de la Leçon 26 : Song.id est passé d'un UUID() tiré au sort à chaque construction à une valeur calculée à partir de artist/title. Le test le plus direct : construire deux fois la même chanson, séparément, et vérifier que leurs identifiants concordent.

// KaramockTests/Domain/SongIdentityTests.swift
import Testing
@testable import Karamock

struct SongIdentityTests {

    @Test
    @MainActor
    func songsWithSameArtistAndTitleShareTheSameIdentity() {
        let first = Song(title: "Kashmir", artist: "Led Zeppelin", year: 1975, duration: "8:37", key: "Dm")
        let second = Song(title: "Kashmir", artist: "Led Zeppelin", year: 1975, duration: "8:37", key: "Dm")

        #expect(first.id == second.id)
        #expect(first == second)
    }
}

Aucun @Suite(.container), aucun import Factory ici : ce test ne touche à aucune dépendance, Song est une struct construite directement — rien à substituer dans le Container. Ce qui surprend davantage : ce test, purement synchrone et sans aucun appel réseau ou base de données, a quand même besoin de @MainActor. La raison est exactement celle documentée en Leçon 26 : id est une propriété calculée, et Song n'est pas marqué nonisolated — SE-0434 exempte les propriétés stockées Sendable de l'isolation par défaut, jamais les propriétés calculées. first.id retombe donc sous la règle générale de SE-0466 et reste implicitement isolé au Main Actor — un test qui le lit doit donc l'être aussi, sous peine d'erreur de compilation Swift 6. Nicolas n'a pour l'instant pas appliqué la correction nonisolated var id suggérée en Leçon 26 ; ce test compile quand même, simplement parce qu'il est @MainActor — la marque nonisolated resterait un geste de cohérence, pas une obligation.

Pourquoi first == second est vrai, indépendamment du fix de id

Une question naturelle : la deuxième assertion (first == second) teste-t-elle vraiment la correction de la Leçon 26 ? Vérification faite auprès de SE-0185 (Synthesizing Equatable and Hashable conformance) : "synthesis of Equatable's requirements is based on the conformances of only its stored instance properties. Neither static properties nor computed instance properties... are considered." Le Hashable/Equatable synthétisé de Song ignore donc totalement id depuis qu'il est devenu calculé — il compare uniquement title, artist, year, duration, key, tous stockés. C'est en réalité une conséquence indirecte, plus profonde que l'intention affichée du fix de la Leçon 26 : avant le fix (let id = UUID(), stocké), id faisait partie de la comparaison synthétisée, et c'est exactement pour ça que deux Song identiques par ailleurs n'étaient jamais égaux — le piège déjà documenté en Leçon 13. Après le fix, id n'entre même plus en jeu dans == : ce n'est plus une histoire d'identifiants qui concordent, mais d'identifiants complètement mis de côté par le compilateur. La première assertion (first.id == second.id) reste la plus importante pour ce bug précis : c'est id, pas ==, qu'utilisent réellement storage.contains(song) et cache[song.id].

Test 2 — annuler un téléchargement ne doit jamais persister la chanson

Bugs #1 et #2 de la Leçon 26, ensemble : la Task orpheline de DownloadSongUseCase et la Task non trackée de SongDownloadViewModel. Le test doit prouver qu'appeler cancelDownload() en cours de route empêche repository.add(song) de jamais s'exécuter.

// KaramockTests/ViewModels/SongDownloadCancellationTests.swift
import Testing
import FactoryKit
import FactoryTesting
@testable import Karamock

@Suite(.container)
struct SongDownloadCancellationTests {

    @Test
    @MainActor
    func cancellingMidDownloadNeverPersistsTheSong() async throws {
        let song = Song(title: "Kashmir", artist: "Led Zeppelin", year: 1975, duration: "8:37", key: "Dm")
        let repository = MockDownloadedSongsRepository()
        Container.shared.downloadedSongsRepository { repository }
        Container.shared.songDownloading { MockSongDownloading() }

        let viewModel = Container.shared.songDownloadViewModel(song)
        viewModel.startDownload()

        try await Task.sleep(for: .milliseconds(250))   // laisse partir une ou deux valeurs de progression
        viewModel.cancelDownload()

        // Attente volontairement bornée, plus longue que les 10 x 200 ms du mock :
        // si le bug de la Task orpheline revenait, l'ajout aurait déjà eu lieu.
        try await Task.sleep(for: .milliseconds(2500))

        #expect(await repository.songs().isEmpty)
    }
}

Le test suit la même construction qu'en production (Container.shared.songDownloadViewModel(song), comme en Leçon 13) plutôt que d'assembler SongDownloadViewModel à la main — downloadSong compose automatiquement songDownloading et downloadedSongsRepository, exactement la même chaîne d'appels qu'à l'exécution réelle.

Pourquoi ne pas utiliser confirmation() pour éviter l'attente bornée ?

Swift Testing propose confirmation(_:expectedCount:), avec expectedCount: 0 documenté explicitement pour "cet événement ne doit jamais se produire". Ça semblait la solution évidente pour remplacer un Task.sleep arbitraire — vérification faite, ce n'est pas le cas ici. confirmation vérifie le nombre d'appels reçus pendant l'exécution de sa closure, il n'attend rien de plus : si repository.add est censé être appelé (ou pas) par une Task détachée qui continue de tourner après la fin de cette closure, confirmation conclut prématurément. C'est précisément le scénario décrit dans l'issue #978 du dépôt swift-testing — fermée "not planned" par l'équipe Swift Testing, qui confirme qu'aucun mécanisme d'attente n'existe aujourd'hui pour ce cas précis. En clair : tant que DownloadSongUseCase et SongDownloadViewModel ne remontent aucun signal testable de "la Task interne a terminé son nettoyage", une attente bornée explicite reste la façon la plus honnête d'écrire ce test — pas une négligence, une limite documentée de l'écosystème actuel.

Précision sur onTermination : ce n'est pas la sortie de boucle qui déclenche tout

Un raccourci tentant serait de penser que sortir d'un for await par break ou return, où que ce soit dans la chaîne, déclenche onTermination. Ce n'est pas ce que documente le code source de AsyncThrowingStream : "If an onTermination callback is set, using task cancellation to terminate iteration of an AsyncThrowingStream results in a call to this callback." Le déclencheur documenté est précisément l'annulation de la Task consommatrice, pas la sortie de la boucle en elle-même. Dans la chaîne de la Leçon 26 : cancelDownload() annule downloadTask (la Task du ViewModel, consommatrice du stream de DownloadSongUseCase) → cette annulation déclenche onTermination sur ce stream → qui annule à son tour la Task interne de DownloadSongUseCase. Le guard !Task.isCancelled else { break } à l'intérieur de cette Task interne est une réaction à une annulation déjà propagée, pas ce qui la déclenche.

Test 3 — un téléchargement en échec bascule bien vers .failed

Promesse de la Leçon 28 : depuis que MockSongDownloading(shouldFail: true) a migré dans la cible de tests, il n'est plus possible de simuler un échec via un #Preview — la seule façon correcte de le vérifier devient un vrai test.

// KaramockTests/ViewModels/SongDownloadFailureTests.swift
import Testing
import FactoryKit
import FactoryTesting
@testable import Karamock

@Suite(.container)
struct SongDownloadFailureTests {

    @Test
    @MainActor
    func failedDownloadTransitionsToFailedState() async throws {
        let song = Song(title: "Kashmir", artist: "Led Zeppelin", year: 1975, duration: "8:37", key: "Dm")
        Container.shared.downloadedSongsRepository { MockDownloadedSongsRepository() }
        Container.shared.songDownloading { MockSongDownloading(shouldFail: true) }

        let viewModel = Container.shared.songDownloadViewModel(song)
        viewModel.startDownload()

        // MockSongDownloading(shouldFail: true) échoue à l'étape 5, soit 5 x 200 ms.
        try await Task.sleep(for: .milliseconds(1250))

        #expect(viewModel.state == .failed)
    }
}

Ce test aussi repose sur une attente bornée — mais d'une nature différente du Test 2 : ici on attend qu'un événement positif se produise (l'échec, à un instant connu et fixe du mock), pas qu'un événement négatif continue de ne pas se produire indéfiniment. La marge de 250 ms au-dessus des 1000 ms nécessaires suffit largement, sans avoir besoin de couvrir toute la durée du stream comme au Test 2.

Scénario de vérification, étape par étape :
  1. Build de la cible KaramockTests (⌘U) : les trois nouveaux tests doivent apparaître dans le Test Navigator.
  2. songsWithSameArtistAndTitleShareTheSameIdentity passe sans délai perceptible — aucune concurrence en jeu.
  3. cancellingMidDownloadNeverPersistsTheSong prend environ 2,75 secondes à s'exécuter — normal, c'est l'attente bornée assumée.
  4. failedDownloadTransitionsToFailedState prend environ 1,25 seconde.
  5. Commente temporairement le guard !Task.isCancelled else { return } après la boucle dans SongDownloadViewModel.startDownload() (réintroduis sciemment le Bug #2) : cancellingMidDownloadNeverPersistsTheSong doit désormais échouer.
  6. Reviens en arrière (annule ce changement) : les trois tests repassent au vert.
