De vraies paroles, récupérées avec URLSession

Jusqu'ici, tout Karamock tourne avec des données factices — c'est le périmètre confirmé de la mission. Mais mockLyrics a un défaut amusant : les chansons du catalogue (Queen, Guns N' Roses, Eagles…) sont de vraies chansons. On peut donc leur trouver de vraies paroles, sans inventer aucune nouvelle fonctionnalité — juste brancher FullScreenPlayerView sur un vrai service public au lieu du tableau figé.

Pourquoi cette leçon : un poste Swift/Apple Platforms senior suppose de savoir consommer une API REST proprement — construire une URL, décoder une réponse JSON, gérer l'asynchrone avec async/await — sans que ce soit noyé dans une fonctionnalité artificielle. Réutiliser le catalogue existant plutôt que d'inventer un écran de recherche garde cette première leçon réseau concentrée sur URLSession lui-même. Et comme le réseau introduit une vraie latence, c'est aussi l'occasion de réappliquer la distinction Service/Repository posée en Leçon 7 : le Service sait faire l'appel réseau, le Repository sait retenir ce qui a déjà été récupéré.

Le service public : api.lyrics.ovh

lyrics.ovh est une API gratuite, sans clé d'authentification, qui renvoie les paroles d'un titre à partir d'un artiste et d'un nom de chanson. Vérifié en direct pour cette leçon :

GET https://api.lyrics.ovh/v1/Queen/Bohemian%20Rhapsody

→ 200 OK
{"lyrics":"Is this the real life ?\nIs this just fantasy ?\n…"}
GET https://api.lyrics.ovh/v1/Queen/ThisSongDoesNotExist

→ 404 Not Found
{"error":"No lyrics found"}

Un seul champ lyrics en cas de succès : un texte brut avec des retours à la ligne (\n), sans aucun horodatage par ligne. C'est une différence importante avec mockLyrics, qui attache un time à chaque ligne pour piloter le surlignage dans LyricsView — il va falloir s'en accommoder.

Construire l'URL : le piège des espaces et apostrophes

"Sweet Child O' Mine", "Guns N' Roses" : les titres et artistes réels du catalogue contiennent des espaces et des apostrophes, invalides tels quels dans une URL. Il faut les encoder en pourcent-encodage avant de les insérer dans le chemin :

private func lyricsURL(artist: String, title: String) -> URL? {
    guard
        let encodedArtist = artist.addingPercentEncoding(withAllowedCharacters: .urlPathAllowed),
        let encodedTitle = title.addingPercentEncoding(withAllowedCharacters: .urlPathAllowed)
    else { return nil }
    return URL(string: "https://api.lyrics.ovh/v1/\(encodedArtist)/\(encodedTitle)")
}

CharacterSet.urlPathAllowed est l'ensemble de caractères que Foundation considère valides dans un segment de chemin d'URL — addingPercentEncoding(withAllowedCharacters:) remplace tout le reste par son équivalent %XX (un espace devient %20). Sans ça, une requête pour "Guns N' Roses" échouerait purement et simplement à se construire en URL valide.

Pour le moment, place lyricsURL en private dans le même fichier que le service qui l'utilise (LyricsFetching/URLSessionLyricsFetching, section suivante) — c'est un détail de construction d'URL propre à ce service, pas une API à exposer ailleurs dans le projet. Comme le rappelait déjà la Leçon 7 à propos de l'arborescence des dossiers : ce qui compte, c'est que seul le service parle de URLSession/URL — pas où exactement vit chaque fonction.

Le service : protocole + implémentation réelle

Même structure que SongDownloading/MockSongDownloading (Services/) — un protocole Sendable, une implémentation concrète :

protocol LyricsFetching: Sendable {
    func fetchLyrics(artist: String, title: String) async throws -> String
}

struct URLSessionLyricsFetching: LyricsFetching {
    func fetchLyrics(artist: String, title: String) async throws -> String {
        guard let url = lyricsURL(artist: artist, title: title) else {
            throw URLError(.badURL)
        }
        let (data, _) = try await URLSession.shared.data(from: url)
        let response = try JSONDecoder().decode(LyricsResponse.self, from: data)
        return response.lyrics
    }
}

private struct LyricsResponse: Decodable {
    let lyrics: String
}

URLSession.shared.data(from:) est la variante async de la méthode historique à callback — elle suspend la fonction appelante jusqu'à la réponse, sans bloquer de thread ni imbriquer de closures. JSONDecoder().decode(_:from:) retrouve le JSON {"lyrics": "…"} reçu et le transforme directement en LyricsResponse, à condition que ses propriétés correspondent aux clés du JSON — exactement ce qu'on a vérifié plus haut. LyricsFetching s'arrête volontairement là : il sait faire l'appel réseau, rien de plus — ni mise en forme, ni mémorisation.

Le repository : entre le UseCase et le service

La Leçon 7 posait déjà la distinction : un Service (SongDownloading, LyricsFetching) sait faire quelque chose d'externe ; un Repository (DownloadedSongsRepository) sait retenir une collection d'objets du domaine et y donner accès. Pour les paroles, ce rôle de rétention a une vraie utilité : lyrics.ovh n'a aucune raison d'être rappelé deux fois pour la même chanson dans une session. Le repository mémorise donc les [LyricsLine] déjà obtenues, et ne redemande au service que ce qu'il n'a pas encore :

nonisolated protocol LyricsRepository: Sendable {
    func lyrics(for song: Song) async throws -> [LyricsLine]
}

actor CachedLyricsRepository: LyricsRepository {
    private let service: LyricsFetching
    private var cache: [Song.ID: [LyricsLine]] = [:]

    init(service: LyricsFetching) {
        self.service = service
    }

    func lyrics(for song: Song) async throws -> [LyricsLine] {
        if let cached = cache[song.id] { return cached }

        let rawText = try await service.fetchLyrics(artist: song.artist, title: song.title)
        let lines = rawText.split(separator: "\n", omittingEmptySubsequences: false).map(String.init)
        guard !lines.isEmpty else { return [] }
        let interval = song.durationInSeconds / Double(lines.count)
        let result = lines.enumerated().map { index, text in
            LyricsLine(time: Double(index) * interval, text: text)
        }

        cache[song.id] = result
        return result
    }
}

Deux idées à retenir ici. D'abord, le service reste une simple propriété du repository — le UseCase ne le connaît plus du tout, exactement comme FetchDownloadedSongsUseCase (Leçon 7) ne connaît aucun Service, seulement son DownloadedSongsRepository. Ensuite, CachedLyricsRepository est un actor et non une struct : cache est un état mutable partagé, potentiellement lu et écrit par plusieurs appels concurrents (deux écrans ouvrant deux chansons en même temps) — même raisonnement que SimpleDownloadedSongsRepository. La transformation texte-brut-vers-[LyricsLine], elle, a simplement migré du UseCase vers le repository : c'est elle qui décide de la donnée qu'elle retient, donc c'est elle qui la façonne.

Correctif rencontré à l'implémentation : song.durationInSeconds devait devenir nonisolated

lyrics(for:) lit song.durationInSeconds à la ligne let interval = song.durationInSeconds / Double(lines.count) — une propriété calculée définie dans Views/Common/TimeUtilities.swift, sans await. Or CachedLyricsRepository est un actor, isolé à son propre exécuteur, pas au MainActor. Avec SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor (Leçon 19), durationInSeconds était implicitement @MainActor comme toute déclaration non annotée du projet — donc inaccessible sans await depuis l'acteur du repository. Le correctif, identique dans l'esprit à celui de la Leçon 19 : ajouter nonisolated devant var durationInSeconds. Cette propriété ne touche que ses propres paramètres (duration, une String) — elle n'a besoin d'appartenir à aucun acteur en particulier, donc rien ne justifiait qu'elle hérite du MainActor par défaut.

Le UseCase : une orchestration mince

struct FetchLyricsUseCase: Sendable {
    let repository: LyricsRepository

    nonisolated init(repository: LyricsRepository) {
        self.repository = repository
    }

    func callAsFunction(for song: Song) async throws -> [LyricsLine] {
        try await repository.lyrics(for: song)
    }
}

Le UseCase ne fait plus que déléguer — il ne sait ni comment les paroles sont récupérées (réseau ? cache ?), ni comment le texte brut devient des LyricsLine. C'est exactement la forme de FetchDownloadedSongsUseCase : un point d'entrée stable pour la vue, derrière lequel le repository est libre de changer de stratégie sans que personne d'autre n'ait à bouger.

Le surlignage synchronisé devient une approximation, pas une vraie fonctionnalité

lyrics.ovh ne fournit aucun horodatage par ligne — juste un bloc de texte. Pour rester compatible avec LyricsView (qui attend un [LyricsLine] avec un time par ligne, cf. Leçon 16), le repository répartit les lignes uniformément sur la durée totale de la chanson. C'est une approximation assumée, pas un vrai karaoké synchronisé — les vraies paroles ne défilent pas forcément au bon rythme. Une vraie synchronisation demanderait des données ligne-par-ligne avec horodatage (type LRC), que cette API ne fournit pas.

Brancher le repository et le UseCase dans le Container

// KaramockContainer.swift
var lyricsFetching: Factory {
    self { URLSessionLyricsFetching() }
}

var lyricsRepository: Factory {
    self { CachedLyricsRepository(service: self.lyricsFetching()) }
        .singleton
}

var fetchLyrics: Factory {
    self { FetchLyricsUseCase(repository: self.lyricsRepository()) }
}

lyricsRepository est enregistré .singleton, comme downloadedSongsRepository — sans ça, Factory recréerait un CachedLyricsRepository vide (donc un cache vide) à chaque résolution, et la mémorisation ne servirait jamais à rien.

Le ViewModel : la vue ne doit pas appeler le UseCase elle-même

FullScreenPlayerView n'a aujourd'hui aucun ViewModel dédié — elle lit directement @Injected(\.player) (un état d'app partagé) et gère progress en @State local. Injecter @Injected(\.fetchLyrics) directement dans la vue suivrait ce même raccourci, mais casserait la couche que le reste du projet respecte partout ailleurs : SongDownloadViewModel (Leçon 6-7) et LibraryViewModel (Leçon 12) sont les deux seuls points de contact autorisés entre une vue et un UseCase — jamais la vue directement. Une vue qui appelle elle-même un UseCase réseau perd la même chose qu'un ViewModel qui appellerait un Service directement (Leçon 8) : plus aucun endroit unique où tester la logique de chargement sans UIKit/SwiftUI.

@MainActor
@Observable
final class FullScreenPlayerViewModel {
    private(set) var lyrics: [LyricsLine] = mockLyrics

    private let song: Song
    private let fetchLyrics: FetchLyricsUseCase

    init(song: Song, fetchLyrics: FetchLyricsUseCase) {
        self.song = song
        self.fetchLyrics = fetchLyrics
    }

    func loadLyrics() async {
        do {
            lyrics = try await fetchLyrics(for: song)
        } catch {
            lyrics = [LyricsLine(time: 0, text: "Paroles indisponibles pour le moment.")]
        }
    }
}
// KaramockContainer.swift
@MainActor
var fullScreenPlayerViewModel: ParameterFactory {
    self { song in FullScreenPlayerViewModel(song: song, fetchLyrics: self.fetchLyrics()) }
}
// FullScreenPlayerView.swift
@State private var viewModel: FullScreenPlayerViewModel?
// … @Injected(\.player), progress, timer inchangés
// …
LyricsView(lyrics: viewModel?.lyrics ?? mockLyrics, currentTime: progress)
    .frame(height: 160)
// …
.task(id: song.id) {
    let viewModel = Container.shared.fullScreenPlayerViewModel(song)
    self.viewModel = viewModel
    await viewModel.loadLyrics()
}

ParameterFactory et l'appel Container.shared.fullScreenPlayerViewModel(song) dans .task reprennent exactement le schéma déjà en place pour songDownloadViewModel/SongOptionsSheet — un ViewModel qui a besoin d'un paramètre à la construction (ici, la chanson) n'est jamais résolu par simple @Injected. .task(id: song.id) reste nécessaire à cet endroit précis : RootTabView présente FullScreenPlayerView via .fullScreenCover(isPresented:) avec song lu depuis player.currentSong, pas .fullScreenCover(item:) — la même instance de vue peut donc recevoir une chanson différente sans être fermée puis rouverte, et il faut alors reconstruire le ViewModel (donc relancer loadLyrics()) pour la nouvelle chanson.

Le do/catch dans loadLyrics() est volontairement sommaire

Toute erreur — pas de réseau, chanson introuvable sur lyrics.ovh, JSON malformé — finit dans la même case catch, avec le même message générique. C'est honnête pour cette leçon centrée sur URLSession, mais ce n'est pas ce qu'on ferait dans une app industrielle : distinguer un 404 (chanson non trouvée) d'une vraie panne réseau, choisir quoi afficher à l'utilisateur dans chaque cas, décider quoi journaliser. C'est exactement le sujet de la prochaine leçon.

Scénario de vérification, étape par étape :
  1. Ouvre une chanson dont le titre existe vraiment — "Bohemian Rhapsody" de Queen, dans la playlist "Best Of Rock", est vérifiée fonctionner au moment de cette leçon. LyricsView doit afficher ses vraies paroles au lieu du texte simulé.
  2. Ressors de l'écran, coupe le Wi-Fi/les données, puis rouvre la même chanson : les paroles doivent réapparaître immédiatement, sans délai ni erreur — c'est le repository qui répond depuis son cache, sans repasser par URLSession.
  3. Ouvre une chanson dont l'association artiste/titre est peu probable sur lyrics.ovh (un titre du mock qui n'existe pas vraiment, ou un artiste mal orthographié pour tester). Le message de repli "Paroles indisponibles pour le moment." doit s'afficher, sans crash.
  4. Coupe le Wi-Fi/les données avant d'ouvrir une chanson jamais vue auparavant : même résultat attendu — repli propre, pas de blocage de l'interface.
