Leçon 40 · Moteur de paroles en C++ (4/N)

Une source de temps continue, sans interpolation

Depuis la Leçon 37, EngineProofView produit une seule image, figée à un instant choisi à la main (2.5 en Leçon 39). Cette leçon fait tourner le temps pour de vrai : TimelineView redessine l'image plusieurs fois par seconde, currentTime avance réellement, et la ligne active de LyricsPage change sous tes yeux entre les trois lignes de test. Elle saute encore net d'une position à l'autre, sans aucune transition lissée — ce lissage est le sujet de la leçon suivante, pas de celle-ci. Détail à noter : leçon inhabituelle dans cette série, aucun fichier C++ ne change. Le moteur sait déjà tout faire depuis la Leçon 39 ; il ne reste qu'à l'appeler en continu plutôt qu'une seule fois.

Le problème d'un rendu figé une seule fois

Rappel de ce que fait EngineProofView depuis la Leçon 37 :

// État avant cette leçon
.task (id: displayScale) {
    image = Self.render(pointSize: pointSize, scale: displayScale)
}

.task(id: displayScale) ne se redéclenche que si displayScale change (passage @2x → @3x, changement d'écran) — jamais parce que le temps avance. render() calcule une image, une fois, avec un currentTime constant codé en dur. Rien dans cette chaîne ne rappelle render() une seconde fois pour montrer une ligne différente.

TimelineView : une source de temps qui redessine

TimelineView résout exactement ce problème : il exécute sa closure de contenu à intervalles réguliers, chaque exécution recevant un context.date à jour.

// NOUVEAU — principe
TimelineView(.periodic(from: startDate, by: 0.1)) { context in
    // recalculé environ 10 fois par seconde, context.date avance à chaque fois
}

.periodic(from:by:) déclenche un nouveau context.date toutes les 0.1 seconde à partir de startDate. 0.1 seconde (10 Hz) suffit largement pour voir la ligne active changer sans à-coup perceptible dans ce rendu — un rendu à 60 images/seconde serait inutilement coûteux ici puisque chaque tick relance une rastérisation logicielle complète (Leçon 38), pas un simple changement de propriété SwiftUI. Le choix de la fréquence est justement le genre de compromis qu'une vraie boucle de lecture devra revisiter plus tard.

Pourquoi @State private var startDate = Date(), pas juste let

Piège facile à ne pas voir avant qu'il ne se manifeste : une View SwiftUI est une struct, une simple description reconstruite à chaque fois que son parent se redessine — ce qui arrive pour toutes sortes de raisons sans rapport avec EngineProofView elle-même. Une propriété stockée ordinaire (let startDate = Date()) serait donc réévaluée à chaque reconstruction, redonnant un "maintenant" différent à chaque fois — l'origine du temps ne cesserait de se réinitialiser, et currentTime semblerait redémarrer à zéro sans raison visible.

// CORRECTION
@State private var startDate = Date()

@State stocke la valeur en dehors de la struct elle-même, dans un espace de stockage géré par SwiftUI qui survit aux reconstructions successives — exactement le mécanisme qui permet déjà à @State private var image (Leçon 37) de garder son image entre deux passages de body. Rien de nouveau dans le mécanisme, seulement une nouvelle occasion de l'oublier : toute donnée qui doit "tenir" au-delà d'un seul passage de body a besoin de @State (ou d'un mécanisme équivalent), jamais d'une propriété stockée ordinaire.

Le vrai coût caché : recharger la police à chaque tick

À 10 exécutions par seconde, un détail qui ne posait aucun problème appelé une seule fois devient un vrai gâchis répété : Bundle.main.url(forResource:withExtension:) (recherche dans le bundle) puis Data(contentsOf:) (lecture disque) à chaque tick, pour un fichier qui ne change jamais après le premier chargement.

// CORRECTION — chargé une seule fois, mis en cache
@State private var fontData: Data?
// NOUVEAU — dans body, avant le TimelineView
.task {
    guard fontData == nil else { return }   // ne recharge jamais une deuxième fois
    guard let fontURL = Bundle.main.url(forResource: "NotoSans-Regular", withExtension: "ttf")
    else { return }
    fontData = try? Data(contentsOf: fontURL)
}

Data est un type Swift ordinaire, entièrement copiable — aucun obstacle à le garder dans @State. karamock.Font, en revanche, reste construit à neuf à chaque tick, à l'intérieur de render(), exactement comme depuis la Leçon 38 :

// Toujours dans render(), reconstruit à chaque appel
var font = karamock.Font()
guard loadFont(from: fontData, into: &font) else { return nil }

Pas un oubli : Font interdit explicitement sa copie depuis la Leçon 38 (Font(const Font&) = delete, pour empêcher deux Font de pointer vers les mêmes octets). Le stockage @State de SwiftUI doit pouvoir conserver et redonner sa valeur à chaque passage de body — un type C++ move-only s'y prête mal, et forcer la question sort du cadre de cette leçon. La solution retenue ici contourne le problème plutôt que de l'affronter : mettre en cache les octets (Data, triviallement copiable), et reconstruire le petit objet Font à partir de ces octets déjà en mémoire à chaque tick. Le résultat reste correct — stbtt_InitFont ne fait que lire des tables d'en-tête, aucune rastérisation de glyphe n'a lieu avant que drawText ne soit réellement appelée — seule la lecture disque, la vraie dépense évitable, est éliminée.

Le fichier complet

// CORRECTION — Views/Discovery/EngineProofView.swift (fichier complet)
import CoreGraphics
import Foundation
import SwiftUI

struct EngineProofView: View {
    @Environment(\.displayScale) private var displayScale
    @State private var startDate = Date()
    @State private var fontData: Data?

    private let pointSize = CGSize(width: 320, height: 200)

    var body: some View {
        TimelineView(.periodic(from: startDate, by: 0.1)) { context in
            content(at: context.date)
                .frame(width: pointSize.width, height: pointSize.height)
        }
        .task {
            guard fontData == nil else { return }
            guard let fontURL = Bundle.main.url(forResource: "NotoSans-Regular", withExtension: "ttf")
            else { return }
            fontData = try? Data(contentsOf: fontURL)
        }
    }

    @ViewBuilder
    private func content(at date: Date) -> some View {
        if let fontData,
           let image = Self.render(pointSize: pointSize, scale: displayScale,
                                    fontData: fontData, currentTime: date.timeIntervalSince(startDate)) {
            Image(decorative: image, scale: displayScale)
                .interpolation(.none)
        } else {
            ProgressView()
        }
    }

    private static func render(pointSize: CGSize, scale: CGFloat,
                                fontData: Data, currentTime: Double) -> CGImage? {
        let pixelWidth  = Int((pointSize.width  * scale).rounded())
        let pixelHeight = Int((pointSize.height * scale).rounded())

        var font = karamock.Font()
        guard loadFont(from: fontData, into: &font) else { return nil }

        var buffer = karamock.PixelBuffer()
        buffer.resize(Int32(pixelWidth), Int32(pixelHeight))
        buffer.fill(20, 20, 30)

        var lyricsStore = karamock.LyricsStore()
        let testLines: [(time: Double, text: String)] = [
            (0.0, "Premiere ligne, deja terminee"),
            (2.0, "Deuxieme ligne, celle qui joue maintenant"),
            (4.0, "Troisieme ligne, pas encore arrivee")
        ]
        lyricsStore.reserve(testLines.count)
        for line in testLines {
            lyricsStore.addLine(line.time, std.string(line.text))
        }

        var renderer = karamock.TextRenderer()
        let page = karamock.LyricsPage()
        page.render(&buffer, font, &renderer, lyricsStore, currentTime)

        guard let base = buffer.__dataUnsafe() else { return nil }
        let pixels = Data(bytes: base, count: buffer.sizeInBytes())

        guard let provider = CGDataProvider(data: pixels as CFData),
              let colorSpace = CGColorSpace(name: CGColorSpace.sRGB)
        else { return nil }

        let bitmapInfo = CGBitmapInfo(
            rawValue: CGImageAlphaInfo.premultipliedLast.rawValue
                    | CGImageByteOrderInfo.order32Big.rawValue
        )

        return CGImage(
            width: Int(buffer.width()), height: Int(buffer.height()),
            bitsPerComponent: 8, bitsPerPixel: 32, bytesPerRow: Int(buffer.bytesPerRow()),
            space: colorSpace, bitmapInfo: bitmapInfo, provider: provider,
            decode: nil, shouldInterpolate: false, intent: .defaultIntent
        )
    }

    private static func loadFont(from data: Data, into font: inout karamock.Font) -> Bool {
        data.withUnsafeBytes { rawBuffer in
            guard let baseAddress = rawBuffer.bindMemory(to: UInt8.self).baseAddress else {
                return false
            }
            return font.loadFromMemory(baseAddress, rawBuffer.count)
        }
    }
}

Bonus qui n'a rien coûté : content(at:) lit displayScale depuis l'environnement à chaque tick, comme n'importe quelle autre valeur utilisée dans body. Un changement d'échelle d'affichage (déplacer la fenêtre vers un autre écran, par exemple) est donc pris en compte automatiquement au tick suivant — le .task(id: displayScale) explicite des Leçons 37 à 39, qui ne servait qu'à ça, n'est plus nécessaire.

LyricsStore, PixelBuffer, TextRenderer et LyricsPage restent eux aussi reconstruits à chaque tick, sans mise en cache — délibérément laissé ainsi pour cette leçon. Leur construction ne coûte ni lecture disque ni rastération de glyphe tant que drawText n'est pas appelée ; le tout reste bon marché à l'échelle de trois lignes de test. Un vrai lecteur, avec de vraies paroles et un vrai flux audio, voudra probablement un objet "moteur" persistant réutilisé d'une frame à l'autre plutôt que tout reconstruire — une question qui se posera quand la lecture réelle, pas seulement cette vue de preuve, sera branchée.

État réel de l'implémentation (comparé le 8 août 2026) : conforme exactement à ce qu'enseigne cette leçon — TimelineView(.periodic(from: startDate, by: 0.1)), @State private var fontData: Data?, content(at:) et la signature de render(pointSize:scale:fontData:currentTime:) sont identiques, y compris le guard fontData == nil else { return } dans le .task. Aucun écart à corriger.
