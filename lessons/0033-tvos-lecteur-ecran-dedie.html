Leçon 33 · Multi-plateforme (3/N)

tvOS : le lecteur plein écran quitte la modale

Nicolas a observé un vrai bug visuel sur Apple TV : FullScreenPlayerView, présenté en .fullScreenCover depuis la Leçon 23, s'affiche sans fond et se superpose aux onglets de l'app — alors que sur iOS, la même modale couvre proprement tout l'écran. Cette leçon enquête sur la cause avant de corriger, teste le correctif le plus simple d'abord, et explique pourquoi on finit par en choisir un plus structurel : un vrai écran poussé dans une pile de navigation, pas une modale.

L'enquête : aucune cause tvOS documentée par Apple

Avant de corriger quoi que ce soit, vérification menée spécifiquement pour cette leçon, sur trois points :

  • La documentation officielle de fullScreenCover(isPresented:onDismiss:content:) liste tvOS 14.0+ comme plateforme supportée, sans aucune note de comportement spécifique à tvOS (opacité, couverture d'écran, composition graphique).
  • La page HIG "Modality" et la page HIG "Sheets" contiennent chacune la même phrase, mot pour mot : "No additional considerations for tvOS." Apple ne met en garde nulle part contre l'usage d'une modale plein écran sur tvOS, et ne recommande nulle part la navigation par pile comme substitut.
  • Recherche complémentaire (forums développeurs, non officielle, signalée comme telle) : un bug similaire de fullScreenCover perdant son fond opaque a été signalé sur iOS 26 — même symptôme, plateforme différente. Ce n'est pas une preuve que la cause est identique sur tvOS, mais ça affaiblit l'hypothèse d'une limitation tvOS spécifique et voulue : plus probablement un comportement non garanti par défaut, sur plusieurs plateformes.

Conclusion de l'enquête : rien dans la documentation Apple n'explique ni ne justifie ce que Nicolas observe. Le correctif ne peut donc pas s'appuyer sur "c'est documenté comme ça" — il faut choisir entre corriger le symptôme et changer de mécanisme, en connaissance de cause.

Option testée et écartée : forcer un fond opaque

La .presentationBackground(_:) est bien disponible sur tvOS (16.4+, confirmé), et l'exemple officiel de la page fullScreenCover applique lui-même .background(Color.blue) + .ignoresSafeArea(edges: .all) directement sur le contenu présenté. Les deux sont documentés, légitimes, et corrigeraient probablement le symptôme visible :

// Option écartée — juste un fond opaque forcé, RootTabView.swift
.fullScreenCover(isPresented: $player.isExpanded) {
    if let song = player.currentSong {
        FullScreenPlayerView(song: song)
    }
}
.presentationBackground(.black)   // tvOS 16.4+

Écartée quand même, pour une raison structurelle et pas seulement esthétique : une vue empilée dans une NavigationStack (comme PlaylistDetailView déjà aujourd'hui, sans aucun fond explicite) remplit son conteneur par construction — elle n'a jamais eu ce problème de translucidité, sur aucune plateforme, parce que ce n'est pas une présentation superposée mais un remplacement de contenu dans la pile. Corriger l'opacité d'une modale traite le symptôme sur CE cas précis ; changer de mécanisme élimine toute cette catégorie de bugs. Deuxième raison, tirée de la page HIG "Remotes" de tvOS : le bouton Back y est décrit comme devant "open the parent of the current screen" — un vocabulaire de hiérarchie parent/enfant, exactement le modèle d'une pile de navigation, pas celui d'une modale qu'on referme.

Le correctif adopté : NavigationStack + navigationDestination(isPresented:)

Fait vérifié avant d'écrire quoi que ce soit : imbriquer une NavigationStack directement autour d'un TabView dont chaque onglet a déjà sa propre NavigationStack (le cas de DiscoveryView et LibraryView dans Karamock) n'est ni recommandé ni déconseillé par la documentation officielle de NavigationStack — ce cas de figure précis n'y est simplement pas traité. Ce choix est donc une décision d'ingénierie assumée, pas une prescription Apple à citer. Fait confirmé en revanche : .navigationDestination(isPresented:destination:) est bien disponible tvOS 16.0+, aux côtés de NavigationStack lui-même.

// CORRECTION — RootTabView.swift
struct RootTabView: View {
    @Injected(\.player) private var player

    var body: some View {
        @Bindable var player = player

        #if os(iOS)
        tabs
            .fullScreenCover(isPresented: $player.isExpanded) {
                if let song = player.currentSong {
                    FullScreenPlayerView(song: song)
                }
            }
        #else
        NavigationStack {
            tabs
                .navigationDestination(isPresented: $player.isExpanded) {
                    if let song = player.currentSong {
                        FullScreenPlayerView(song: song)
                    }
                }
        }
        #endif
    }

    private var tabs: some View {
        TabView {
            DiscoveryView()
                .tabItem { Label("Découvrir", systemImage: "book.closed.fill") }
            LibraryView()
                .tabItem { Label("Bibliothèque", systemImage: "music.note.list") }
        }
        #if os(iOS)
        .tabBarMinimizeBehavior(.onScrollDown)
        .tabViewBottomAccessory(isEnabled: player.currentSong != nil && !player.isExpanded) {
            if let song = player.currentSong, !player.isExpanded {
                MiniPlayerBar(song: song)
            }
        }
        #else
        .overlay(alignment: .bottom) {
            if let song = player.currentSong, !player.isExpanded {
                MiniPlayerBarTV(song: song)
                    .padding(.horizontal, 60)
                    .padding(.bottom, 40)
            }
        }
        #endif
    }
}

Le TabView devient une propriété calculée tabs, réutilisée par les deux branches, pour ne pas dupliquer sa déclaration. Le comportement des onglets et du mini-lecteur (Leçon 32) ne change en rien : tabs reste la racine de la pile de navigation tvOS, donc MiniPlayerBarTV continue de s'afficher en .overlay exactement comme avant. Seul le mécanisme qui affiche FullScreenPlayerView change, de "présenté par-dessus" à "empilé dans la navigation".

Pourquoi FullScreenPlayerView.swift n'a besoin d'aucune modification

@Environment(\.dismiss) private var dismiss et le bouton chevron.down qui l'appelle restent identiques — DismissAction est indifférente au mode de présentation : le même appel ferme une modale (fullScreenCover/sheet) ou dépile une destination empilée (navigationDestination), sans distinction de code entre les deux. Même chose pour les deux autres points d'entrée qui déclenchent player.isExpanded = true — SongOptionsViewModel.playNow() et MiniPlayerBarTV — aucun des deux n'a besoin de savoir si le lecteur va être présenté ou poussé. SongOptionsSheet.swift appelle déjà explicitement dismiss() sur son propre bouton "Jouer maintenant" (indépendamment de player.isExpanded), donc la feuille se ferme normalement avant que la pile ne pousse le lecteur, sur les deux plateformes.

Pourquoi .navigationDestination(isPresented:) et pas la version par NavigationPath qu'Apple recommande en général ?

La documentation officielle de navigationDestination(isPresented:destination:) précise elle-même : "In general, favor binding a path to a navigation stack for programmatic navigation." (en résumé : Apple conseille en général de relier un path à la pile de navigation pour la navigation programmatique). Choix assumé de s'en écarter ici : player.isExpanded est un Bool déjà partagé dans toute l'app via PlayerState (Leçon 23), lu et écrit depuis trois endroits différents. Introduire un NavigationPath ou une valeur de destination dédiée juste pour cette seule destination ajouterait une couche sans bénéfice réel — la version booléenne reste la solution la plus simple, et elle exprime honnêtement l'intention, pour ce cas précis à une seule destination possible.

Ce qui reste à vérifier sur le vrai matériel : le bouton Menu

Recherche menée spécifiquement pour cette leçon : aucune page Apple ne confirme noir sur blanc que le bouton Menu de la télécommande dépile automatiquement une destination poussée par navigationDestination(isPresented:). Un élément qui plaide en faveur de ce comportement par défaut : isModalInPresentation (UIKit, tvOS 13+) existe spécifiquement pour désactiver la fermeture automatique d'un contrôleur présenté — son existence n'aurait pas de sens si rien ne se fermait automatiquement par défaut. Ce comportement est donc fortement suggéré, mais jamais affirmé explicitement par Apple. À vérifier en priorité une fois buildé : le bouton Menu doit fermer FullScreenPlayerView tout seul, sans code additionnel — sinon, .onExitCommand(perform:) (tvOS 13+ uniquement, absent d'iOS) est le mécanisme officiel pour l'intercepter manuellement, avec une limite connue mais non documentée officiellement : il peut cesser de fonctionner sur un écran sans aucun élément focusable.

Détail de pure forme laissé de côté : l'icône chevron.down

Le bouton de fermeture de FullScreenPlayerView utilise chevron.down, une métaphore visuelle de "glisser vers le bas pour réduire" — logique sur iOS, mais tvOS n'a pas de geste de balayage tactile équivalent, et le mécanisme est maintenant un vrai "retour" de pile. Remplacer l'icône (par exemple chevron.left) serait cohérent, mais reste un détail cosmétique hors périmètre de cette leçon — à faire si Nicolas le juge utile après avoir vu le rendu réel.

Scénario de vérification, étape par étape :
  1. Build (⌘B) sur le simulateur Apple TV et sur un simulateur iPhone : les deux doivent réussir. Sur iOS, aucun changement de comportement attendu — tabs est une extraction pure, la logique #if os(iOS) reste identique à la Leçon 32.
  2. Sur tvOS, lance "Jouer maintenant" (depuis une fiche chanson ou la Bibliothèque) : FullScreenPlayerView doit maintenant couvrir tout l'écran avec un fond opaque, sans que la barre d'onglets ne reste visible dessous ou autour.
  3. Depuis le lecteur, appuie sur le bouton de fermeture (focus + select) : retour normal à l'écran précédent (Découvrir ou Bibliothèque, celui d'où on est parti).
  4. Sans toucher au bouton de fermeture, appuie sur le bouton Menu de la télécommande (ou son équivalent simulateur) : vérifie si ça ferme aussi le lecteur tout seul. Note le résultat — c'est le point non confirmé officiellement signalé plus haut.
  5. Ouvre le mini-lecteur (MiniPlayerBarTV) pendant qu'une chanson joue en arrière-plan : toujours affiché en bas de Découvrir/Bibliothèque, comportement inchangé depuis la Leçon 32.
  6. Alterne entre l'onglet Découvrir et Bibliothèque après avoir fermé le lecteur plusieurs fois de suite : vérifie qu'aucun état de navigation ne reste "coincé" (pas de pile qui grandit anormalement, pas d'écran qui refuse de s'ouvrir une seconde fois).
