Le mini-lecteur compact, quand la barre d'onglets se réduit

La Leçon 20 a corrigé la position, la visibilité et le fond de MiniPlayerBar. Une question restait ouverte en aside : que se passe-t-il quand la barre d'onglets se réduit pendant le scroll ? L'accessoire se compresse avec elle — et le contenu actuel de MiniPlayerBar (pochette + titre + artiste + bouton) n'a pas été pensé pour tenir dans cet espace réduit.

Pourquoi cette leçon : c'est la suite directe de ce que tu as identifié toi-même à la fin de la Leçon 20 — un vrai comportement d'iOS 26 à anticiper, pas un cas limite théorique. Les captures de référence KaraFun montrent un mini-lecteur qui reste lisible en toute circonstance ; s'assurer qu'il ne casse pas visuellement dès que l'utilisateur scrolle fait partie de la fidélité à l'original que la mission demande.

Ce qui déclenche le changement d'état

Le passage d'un accessoire "étendu" (au-dessus de la barre d'onglets) à "en ligne" (fondu dans la barre d'onglets réduite) est piloté par .tabBarMinimizeBehavior, un modificateur qu'on peut poser sur le TabView :

.tabBarMinimizeBehavior(.automatic)  // valeur par défaut
.tabBarMinimizeBehavior(.never)      // la barre ne se réduit jamais
.tabBarMinimizeBehavior(.onScrollDown)
.tabBarMinimizeBehavior(.onScrollUp)

RootTabView ne posait initialement aucun de ces modificateurs, donc c'était .automatic qui s'appliquait par défaut — le système décide seul, selon des critères non documentés précisément, quand réduire la barre. C'est justement ce qui rend le résultat difficile à vérifier : sans savoir quand .automatic décide de déclencher la réduction, il n'y a pas de geste fiable à reproduire pour observer compactContent à l'écran. La correction : fixer le comportement explicitement, pour le rendre prévisible.

TabView {
    DiscoveryView()
        .tabItem { Label("Découvrir", systemImage: "book.closed.fill") }
    LibraryView()
        .tabItem { Label("Bibliothèque", systemImage: "music.note.list") }
}
.tabBarMinimizeBehavior(.onScrollDown)
.tabViewBottomAccessory(isEnabled: player.currentSong != nil && !player.isExpanded) {
    if let song = player.currentSong {
        MiniPlayerBar(song: song)
    }
}

Avec .onScrollDown, la règle devient simple et reproductible : scroller vers le bas dans le contenu de l'onglet actif réduit la barre (et l'accessoire avec elle) ; scroller vers le haut la fait réapparaître. Plus besoin de deviner ce que .automatic aurait décidé.

Scénario de vérification, étape par étape :
  1. Lance une lecture (par exemple depuis une chanson de la playlist "Best Of Rock", qui contient une trentaine de titres — largement de quoi remplir l'écran).
  2. Retourne sur l'onglet Découvrir, puis ouvre cette même playlist pour ouvrir PlaylistDetailView : le mini-lecteur complet (pochette + titre + artiste + bouton) doit être visible au-dessus de la barre d'onglets.
  3. Scrolle vers le bas dans la liste des chansons. La barre d'onglets doit se réduire, et le mini-lecteur ne doit plus afficher que le bouton play/pause, fondu dans la barre réduite.
  4. Scrolle vers le haut : la barre d'onglets et le mini-lecteur complet doivent réapparaître tels quels.

Lire l'état de l'accessoire depuis son contenu

SwiftUI expose cet état via l'environnement, directement lisible depuis MiniPlayerBar :

@Environment(\.tabViewBottomAccessoryPlacement) private var placement

placement est de type TabViewBottomAccessoryPlacement?, avec trois valeurs possibles : .expanded (accessoire affiché en entier au-dessus de la barre), .inline (fondu dans la barre réduite), ou nil (placement non défini — on le traite comme .expanded par prudence).

Deux présentations pour un seul composant

struct MiniPlayerBar: View {
    @Injected(\.player) private var player
    @Environment(\.tabViewBottomAccessoryPlacement) private var placement

    let song: Song

    var body: some View {
        Group {
            if placement == .inline {
                compactContent
            } else {
                expandedContent
            }
        }
        .contentShape(Rectangle())
        .onTapGesture {
            player.isExpanded = true
        }
    }

    private var compactContent: some View {
        Button {
            player.isPlaying.toggle()
        } label: {
            Image(systemName: player.isPlaying ? "pause.fill" : "play.fill")
                .font(.title3)
        }
        .buttonStyle(.plain)
        .accessibilityLabel(player.isPlaying ? "Mettre en pause" : "Lire")
    }

    private var expandedContent: some View {
        HStack(spacing: 12) {
            RoundedRectangle(cornerRadius: 6)
                .fill(.quaternary)
                .frame(width: 40, height: 40)
                .accessibilityHidden(true)

            VStack(alignment: .leading, spacing: 2) {
                Text(song.title).font(.subheadline.bold())
                Text(song.artist).font(.caption).foregroundStyle(.secondary)
            }
            .accessibilityElement(children: .combine)
            .accessibilityAddTraits(.isButton)
            .accessibilityAction { player.isExpanded = true }

            Spacer()

            Button {
                player.isPlaying.toggle()
            } label: {
                Image(systemName: player.isPlaying ? "pause.fill" : "play.fill")
                    .font(.title3)
            }
            .buttonStyle(.plain)
            .accessibilityLabel(player.isPlaying ? "Mettre en pause" : "Lire")
        }
        .padding(.horizontal, 16)
    }
}

expandedContent reprend exactement le contenu de la Leçon 20, inchangé. compactContent ne garde que le strict nécessaire : le bouton play/pause, seul élément qui a une chance de rester lisible et cliquable dans l'espace réduit de la barre d'onglets minimisée.

Où est passé le .onTapGesture de expandedContent ?

Il n'a pas disparu : il est monté d'un niveau, posé une seule fois sur le Group dans body, plutôt que dupliqué séparément dans compactContent et expandedContent. Pour expandedContent, le comportement est identique à la Leçon 20. Ça soulève une question légitime pour compactContent : le bouton play/pause s'y trouve directement enveloppé par ce .onTapGesture ambiant, sans HStack intermédiaire comme dans expandedContent — est-ce que le tap sur le bouton risque de déclencher aussi l'expansion ? Non : dans SwiftUI, quand deux vues imbriquées portent chacune un geste de tap, c'est toujours celui de la vue la plus interne qui se déclenche en premier, qu'il y ait ou non un conteneur entre les deux. Le Button garde donc la priorité, dans les deux présentations.

Pourquoi ne pas essayer de faire tenir la pochette et le titre en plus petit ?

C'est tentant, mais ça déplacerait le problème sans le résoudre : réduire une pochette de 40×40 ou un texte déjà en .caption les rendrait illisibles plutôt que simplement absents. Le choix fait ici est le même que celui d'Apple Music dans son propre accessoire compact — afficher moins d'éléments, mais tous parfaitement lisibles, plutôt que tout garder en miniature.

Ce que ça change pour VoiceOver

En compactContent, il n'y a plus de VStack titre/artiste avec son .accessibilityAction pour ouvrir le lecteur plein écran (le sujet de la Leçon 15) — puisqu'il n'y a plus de titre ni d'artiste affichés à cet endroit. Ce n'est pas une régression : il n'existe simplement plus rien à annoncer ou à activer à cet endroit tant que l'utilisateur reste dans l'état compact. L'action d'expansion reste disponible dès que l'accessoire repasse en .expanded (par exemple en remontant en haut de la liste).

Vérifie ta compréhension

1. Qu'est-ce qui déclenche le passage de l'accessoire en état .inline ?

2. Pourquoi fixer .tabBarMinimizeBehavior(.onScrollDown) explicitement plutôt que de garder .automatic ?

3. Pourquoi compactContent ne garde-t-il que le bouton play/pause, sans réduire la pochette et le texte en plus petit ?

4. Que devient l'action VoiceOver d'expansion (ouvrir le lecteur plein écran depuis le titre) en état compact ?

Le scénario de vérification ci-dessus s'appuie sur "Best Of Rock", qui a toujours assez de chansons pour remplir l'écran. Mais LibraryView affiche les chansons téléchargées par l'utilisateur, un nombre qui dépend de ce que tu as réellement téléchargé en testant l'app — demande à ton agent comment vérifier si cet onglet contient assez de contenu pour reproduire le même scénario, ou s'il faut d'abord télécharger plusieurs chansons.
