Le mini-lecteur qui cache le dernier élément de la liste

Tu as repéré un vrai bug en testant : quand une chanson joue en arrière-plan, le mini-lecteur flotte au-dessus de l'onglet actif — y compris au-dessus de PlaylistDetailView. Le dernier SongRow de la liste se retrouve masqué derrière lui, sans pouvoir être vu ni touché en entier. Ce n'est pas un problème propre à cet écran : c'est la façon dont le mini-lecteur est positionné aujourd'hui qui est en cause.

Pourquoi cette leçon : encore une fois, ce n'est pas un sujet planifié — tu l'as trouvé en utilisant l'app comme le ferait un vrai utilisateur qui reprend une lecture en cours. C'est exactement le genre de détail qu'un test superficiel (regarder l'écran une fois, sans scroller jusqu'au bout) laisse passer, et que la mission demande de traiter avec le même sérieux qu'un vrai correctif produit.

La cause : un overlay ne réserve pas de place

RootTabView affiche le mini-lecteur avec .overlay(alignment: .bottom), posé sur l'ensemble du TabView :

TabView {
    DiscoveryView()
        .tabItem { Label("Découvrir", systemImage: "book.closed.fill") }
    LibraryView()
        .tabItem { Label("Bibliothèque", systemImage: "music.note.list") }
}
.overlay(alignment: .bottom) {
    if let song = player.currentSong, !player.isExpanded {
        MiniPlayerBar(song: song)
            .padding(.bottom, 49)
    }
}

.overlay dessine simplement une vue par-dessus une autre, sans toucher à la mise en page de ce qu'il y a dessous. Le 49 en dur dans .padding(.bottom, 49) est une estimation de la hauteur de la barre d'onglets, ajoutée à la main pour que le mini-lecteur flotte juste au-dessus d'elle plutôt que par-dessus. Mais le ScrollView de PlaylistDetailView (ou n'importe quel écran contenu dans un onglet) n'a aucune idée que ce mini-lecteur existe : il continue de calculer sa zone de défilement comme si toute la hauteur de l'écran lui était disponible, jusqu'à la barre d'onglets. Le dernier élément se retrouve donc physiquement sous le mini-lecteur.

Le correctif : l'accessoire natif du TabView

Depuis iOS 26, SwiftUI propose un modificateur pensé précisément pour ce cas — un mini-lecteur audio flottant au-dessus de la barre d'onglets, exactement comme celui d'Apple Music : .tabViewBottomAccessory.

TabView {
    DiscoveryView()
        .tabItem { Label("Découvrir", systemImage: "book.closed.fill") }
    LibraryView()
        .tabItem { Label("Bibliothèque", systemImage: "music.note.list") }
}
.tabViewBottomAccessory(isEnabled: player.currentSong != nil && !player.isExpanded) {
    if let song = player.currentSong {
        MiniPlayerBar(song: song)
    }
}
.fullScreenCover(isPresented: $player.isExpanded) {
    if let song = player.currentSong {
        FullScreenPlayerView(song: song)
    }
}

La différence n'est pas cosmétique : l'accessoire n'est pas une vue dessinée par-dessus le contenu, c'est une zone à part entière du TabView, gérée nativement à côté de la barre d'onglets. Le contenu de chaque onglet — y compris un écran poussé par navigationDestination comme PlaylistDetailView — voit automatiquement sa zone sûre réduite en conséquence, sans qu'aucun écran individuel n'ait besoin de connaître la hauteur du mini-lecteur. Le .padding(.bottom, 49) disparaît : ce n'est plus une estimation à maintenir à la main.

Le piège : masquer le contenu ne suffit pas

Une première version de cette leçon utilisait .tabViewBottomAccessory { if let song = … { MiniPlayerBar(…) } } sans le paramètre isEnabled — en ne conditionnant que le contenu, pas l'accessoire lui-même. C'est exactement le piège que tu as repéré en testant : quand currentSong devient nil, le contenu disparaît, mais l'accessoire continue d'exister comme zone vide au-dessus de la barre d'onglets, puisque le TabView ne sait pas qu'il doit arrêter de lui réserver de la place.

Le paramètre isEnabled de tabViewBottomAccessory(isEnabled:content:) résout précisément ce cas : il dit explicitement au TabView de retirer l'accessoire de la mise en page, pas seulement de vider son contenu. C'est un paramètre récent (ajouté en iOS 26.2, après que ce problème a été signalé comme comportement non voulu sur les forums développeurs Apple) — comme le projet cible iOS 26.5, il est disponible sans condition de compatibilité à gérer.

Le mini-lecteur a changé de contenant : le fond gris tronqué

Ce que l'aside précédente laissait en suspens, tu l'as vu à l'écran : un fond gris, partiellement coupé sur les bords. La cause est exactement celle annoncée — MiniPlayerBar pose son propre fond, pensé pour l'ancien .overlay flottant :

HStack(spacing: 12) {
    // pochette, titre/artiste, bouton play/pause
}
.padding(10)
.background(.regularMaterial)
.clipShape(RoundedRectangle(cornerRadius: 10))
.padding(.horizontal, 8)
.contentShape(Rectangle())
.onTapGesture { player.isExpanded = true }

L'accessoire du TabView applique déjà, de son côté, son propre fond "Liquid Glass" en forme de capsule autour de tout ce que tu lui donnes. Les deux fonds se superposent désormais : le rectangle arrondi de MiniPlayerBar (dimensionné pour flotter seul) dépasse ou se fait couper par le masque en capsule de l'accessoire, d'où le bord gris tronqué que tu observes. La documentation officielle est explicite sur ce point — dans la session WWDC25 Build a SwiftUI app with the new design : le contenu placé dans l'accessoire "obtient automatiquement un fond Liquid Glass en capsule", et si l'app a "des fonds ou effets d'assombrissement supplémentaires derrière les éléments de la barre", il faut les retirer, car ils interfèrent avec cet effet.

Le restylage : ne garder que la mise en page du contenu, laisser l'accessoire fournir le fond.

var body: some View {
    HStack(spacing: 12) {
        RoundedRectangle(cornerRadius: 6)
            .fill(.quaternary)
            .frame(width: 40, height: 40)
            .accessibilityHidden(true)

        VStack(alignment: .leading, spacing: 2) {
            Text(song.title).font(.subheadline.bold())
            Text(song.artist).font(.caption).foregroundStyle(.secondary)
        }
        .accessibilityElement(children: .combine)
        .accessibilityAddTraits(.isButton)
        .accessibilityAction { player.isExpanded = true }

        Spacer()

        Button {
            player.isPlaying.toggle()
        } label: {
            Image(systemName: player.isPlaying ? "pause.fill" : "play.fill")
                .font(.title3)
        }
        .buttonStyle(.plain)
        .accessibilityLabel(player.isPlaying ? "Mettre en pause" : "Lire")
    }
    .padding(.horizontal, 16)
    .contentShape(Rectangle())
    .onTapGesture { player.isExpanded = true }
}

.background(.regularMaterial), .clipShape(RoundedRectangle(cornerRadius: 10)) et le .padding(10)/.padding(.horizontal, 8) pensés pour un fond propre disparaissent : c'est l'accessoire qui dessine désormais la capsule, ses marges internes, et son matériau translucide. Il ne reste qu'un .padding(.horizontal, 16) pour éviter que la pochette et le bouton touchent le bord de la capsule — une valeur de départ à ajuster à l'œil une fois testée sur ton appareil.

Pour aller plus loin : le mini-lecteur en version compacte

Quand la barre d'onglets se réduit pendant un scroll, l'accessoire passe lui aussi dans un état compact ("inline"), fusionné dans la barre au lieu de flotter au-dessus. SwiftUI expose cet état via l'environnement : @Environment(\.tabViewBottomAccessoryPlacement) private var placement, avec les valeurs .inline, .expanded, ou nil. Le contenu actuel de MiniPlayerBar (pochette + titre + artiste + bouton) est pensé pour l'état .expanded — dans l'état .inline, plus étroit, il vaudrait la peine de basculer vers un contenu réduit (par exemple juste le bouton play/pause). Volontairement laissé de côté ici : la correction du fond tronqué ne dépend pas de ce raffinement.
