Leçon 28 · Nettoyage architecture (5/N)

Le Repository range, le Mapper transforme — et deux noms qui mentaient

Cette leçon regroupe quatre corrections plus petites que les précédentes, mais toutes du même ordre : un nom ou un emplacement qui ne dit pas la vérité sur ce que fait vraiment le code. Une leçon nécessite aussi de contredire l'audit sur un point précis — pas parce qu'il avait tort en général, mais parce que les Leçons 26 et 27 ont changé la réalité qu'il décrivait.

1. Extraire LyricsMapper : le Repository range, il ne transforme pas

Point #8 de l'audit : "Le calcul des timestamps (Double(index) * (duration / lines.count)) est de la logique métier dans un Repository. Un Repository récupère/stocke ; un Mapper transforme."

// Repositories/CachedLyricsRepository.swift — ACTUEL
func lyrics(for song: Song) async throws(LyricsError) -> [LyricsLine] {
    if let cached = await cache[song.id] {
        return cached
    }

    let rawText = try await service.fetchLyrics(artist: song.artist, title: song.title)
    let lines = rawText.split(separator: "\n", omittingEmptySubsequences: false).map(String.init)

    guard !lines.isEmpty else { return [] }

    let interval = song.durationInSeconds / Double(lines.count)

    let result = lines.enumerated().map { index, text in
        LyricsLine(time: Double(index) * interval, text: text)
    }

    await cache[song.id] = result
    return result
}

Cinq lignes sur neuf ne concernent ni la récupération ni le cache — elles transforment un texte brut en [LyricsLine] horodatées. C'est une règle métier autonome (comment répartir des lignes de paroles sur la durée d'une chanson), testable indépendamment de tout réseau ou cache, qui n'a pas sa place dans un Repository :

// NOUVEAU — Domain/Mappers/LyricsMapper.swift
nonisolated enum LyricsMapper {
    static func map(rawText: String, duration: TimeInterval) -> [LyricsLine] {
        let lines = rawText.split(separator: "\n", omittingEmptySubsequences: false).map(String.init)
        guard !lines.isEmpty else { return [] }

        let interval = duration / Double(lines.count)
        return lines.enumerated().map { index, text in
            LyricsLine(time: Double(index) * interval, text: text)
        }
    }
}
// Repositories/CachedLyricsRepository.swift — CORRECTION
func lyrics(for song: Song) async throws(LyricsError) -> [LyricsLine] {
    if let cached = await cache[song.id] {
        return cached
    }

    let rawText = try await service.fetchLyrics(artist: song.artist, title: song.title)
    let result = LyricsMapper.map(rawText: rawText, duration: song.durationInSeconds)

    await cache[song.id] = result
    return result
}

enum sans cas plutôt que struct : LyricsMapper n'a aucun état et ne sera jamais instancié, seulement utilisé comme espace de noms pour une fonction statique — un enum vide rend cette intention explicite et empêche techniquement d'écrire LyricsMapper() par erreur, contrairement à une struct.

nonisolated devant l'enum n'est pas une précaution superflue : LyricsMapper.map(...) est une fonction statique non annotée, donc implicitement @MainActor sous SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor — exactement comme une computed property (Leçon 26). Ni la pureté de la fonction, ni l'absence d'état dans l'enum n'exemptent quoi que ce soit : la règle par défaut de Swift 6 est syntaxique (la déclaration est-elle annotée ?), pas sémantique (le corps a-t-il des effets de bord ?). Sans nonisolated, l'appel depuis CachedLyricsRepository (un actor, donc un domaine d'isolation différent du Main Actor) exigerait await LyricsMapper.map(...) pour un simple calcul synchrone — un aller-retour vers le thread principal sans aucune raison métier.

2. Encapsuler lyricsURL — et simplifier au passage le correctif de la Leçon 25

Point 2.10 de l'audit : lyricsURL est aujourd'hui une fonction libre, en dehors de URLSessionLyricsFetching, alors qu'elle ne sert qu'à lui :

// Services/URLSessionLyricsFetching.swift — ACTUEL
struct URLSessionLyricsFetching: LyricsFetching {
    func fetchLyrics(artist: String, title: String) async throws(LyricsError) -> String {
        guard let url = await lyricsURL(artist: artist, title: title) else {
            throw .invalidURL
        }
        // ...
    }
}

private func lyricsURL(artist: String, title: String) -> URL? { /* ... */ }

La rendre private à l'intérieur du type est le premier réflexe (elle n'a aucune raison d'exister en dehors) :

struct URLSessionLyricsFetching: LyricsFetching {
    func fetchLyrics(artist: String, title: String) async throws(LyricsError) -> String {
        guard let url = lyricsURL(artist: artist, title: title) else { /* ... */ }
        // ...
    }

    private func lyricsURL(artist: String, title: String) -> URL? { /* ... */ }   // NE COMPILE PAS SANS AJOUT
}

Mais ce déplacement seul ne suffit pas à retirer le await. fetchLyrics compile aujourd'hui sans annotation nonisolated explicite parce qu'elle hérite automatiquement de l'isolation du protocole qu'elle satisfait (nonisolated protocol LyricsFetching) — un mécanisme d'inférence explicitement listé par SE-0466 ("declarations with inferred actor isolation from ... protocol conformance"). Mais cette inférence ne s'étend qu'aux membres qui satisfont réellement un requirement du protocole. lyricsURL, une méthode privée qui ne fait partie d'aucun contrat, n'en bénéficie pas — elle reste, comme n'importe quelle déclaration non annotée du module, implicitement @MainActor, même voisine d'une méthode nonisolated par inférence. Le await resterait donc nécessaire tel quel.

Deux façons de le retirer : annoter lyricsURL individuellement (private nonisolated func lyricsURL(...)), ou — plus propre ici, parce que tout ce type est censé être nonisolated de bout en bout — annoter le type entier, une syntaxe introduite par SE-0449 (Swift 6.1) :

// CORRECTION — Services/URLSessionLyricsFetching.swift
nonisolated struct URLSessionLyricsFetching: LyricsFetching {
    func fetchLyrics(artist: String, title: String) async throws(LyricsError) -> String {
        guard let url = lyricsURL(artist: artist, title: title) else {
            throw .invalidURL
        }
        // ... reste du corps inchangé, voir aside ci-dessous pour lyricsFetcherLogger
    }

    private func lyricsURL(artist: String, title: String) -> URL? {
        guard let encodedArtist = artist.addingPercentEncoding(withAllowedCharacters: .urlPathAllowed),
              let encodedTitle = title.addingPercentEncoding(withAllowedCharacters: .urlPathAllowed)
        else {
            return nil
        }
        return URL(string: "https://api.lyrics.ovh/v1/\(encodedArtist)/\(encodedTitle)")
    }
}

nonisolated struct applique l'annotation à tous les membres du type — méthodes, computed properties, stored properties, initialiseurs — sans avoir à les annoter un par un. Deux simplifications immédiates : lyricsURL n'a plus besoin de sa propre annotation, et l'appel depuis fetchLyrics n'a plus besoin d'await. Cette même syntaxe, si elle avait été connue en Leçon 25, aurait aussi évité d'avoir à annoter fetchLyrics individuellement — bien que ça ne change rien ici, puisque l'inférence par conformance au protocole s'en chargeait déjà.

Pourquoi les await devant lyricsFetcherLogger.error(...) restent, eux, nécessaires

Un piège à ne pas manquer : nonisolated struct URLSessionLyricsFetching ne change rien à lyricsFetcherLogger. Cette constante est déclarée en dehors du type, au niveau du fichier (private let lyricsFetcherLogger = Logger(...)) — l'annotation portée par le struct ne s'applique qu'à ses propres membres, pas aux déclarations globales voisines dans le même fichier. lyricsFetcherLogger reste donc implicitement @MainActor, et les deux await lyricsFetcherLogger.error(...) introduits en Leçon 25 restent inchangés. Cette leçon ne les retire pas — elle ne visait que lyricsURL, précisément parce que c'est la seule tâche listée par l'audit (point 2.10). Rendre le logger lui-même nonisolated serait un choix légitime, mais un sujet différent, hors périmètre ici.

3. Renommer SimpleDownloadedSongsRepository → InMemoryDownloadedSongsRepository

Point 1.7 de l'audit, un renommage Xcode simple mais qui change quelque chose de réel : "Simple" ne dit rien sur la stratégie de stockage — n'importe quel Repository pourrait revendiquer d'être "simple". "InMemory" dit précisément ce que quiconque lisant ce nom a besoin de savoir avant de l'utiliser : le stockage est un tableau en mémoire, perdu à chaque relance de l'app. Une information qu'un futur "InMemory" vs "Persistent" rendrait immédiatement visible dans le nom du type, sans avoir à ouvrir le fichier.

// AVANT : Repositories/SimpleDownloadedSongsRepository.swift
actor SimpleDownloadedSongsRepository: DownloadedSongsRepository { /* ... */ }

// APRÈS : Repositories/InMemoryDownloadedSongsRepository.swift
actor InMemoryDownloadedSongsRepository: DownloadedSongsRepository { /* ... */ }

Le corps ne change pas d'une ligne — seul le nom du type (et donc du fichier, et la référence dans KaramockContainer.swift, self { InMemoryDownloadedSongsRepository() }) change.

4. mockLyrics et MockSongDownloading — pourquoi l'audit ne peut plus être suivi tel quel

Point #9 de l'audit, écrit le 2026-07-28 : "Des données de test polluent le bundle de production", avec pour correctif suggéré de déplacer MockSongDownloading et mockLyrics vers KaramockTests/Mocks/. Vérification faite sur le code actuel : les deux sont bien utilisés en production, pas seulement dans des tests.

// ViewModels/FullScreenPlayerViewModel.swift
private(set) var lyrics: [LyricsLine] = mockLyrics   // état initial, avant le premier chargement réel

// Views/Player/FullScreenPlayer/FullScreenPlayerView.swift
LyricsView(lyrics: viewModel?.lyrics ?? mockLyrics, currentTime: progress)   // filet avant que le ViewModel existe

// KaramockContainer.swift
var songDownloading: Factory<SongDownloading> {
    self { MockSongDownloading() }   // LA seule implémentation de production, depuis la Leçon 27
}

Déplacer purement et simplement ces deux déclarations vers KaramockTests/, comme le suggère l'audit, casserait la compilation : une cible de test n'est pas visible depuis la cible d'app. L'audit avait raison sur le principe (du code au nom trompeur ne devrait pas se balader en production) mais sa recommandation date d'avant les Leçons 26-27, qui ont transformé MockSongDownloading en implémentation de production assumée — faute de vrai backend de téléchargement à appeler (Leçon 27). Suivre la lettre de l'audit ici serait suivre une checklist plutôt que comprendre le problème qu'elle décrit.

Le vrai problème n'est pas l'emplacement de ce code, c'est son nom : il prétend être un mock (donc jetable, réservé aux tests) alors qu'il s'agit d'un comportement de production assumé (paroles de secours pendant le chargement, simulation de téléchargement en l'absence de backend réel). Le correctif est de dire la vérité sur ce que c'est :

// RENOMMÉ — Domain/Models/LyricsLine.swift
let placeholderLyrics: [LyricsLine] = [ /* ... contenu inchangé ... */ ]
// RENOMMÉ — Services/SimulatedSongDownloading.swift (était MockSongDownloading.swift)
struct SimulatedSongDownloading: SongDownloading {
    func download(_ song: Song) -> AsyncThrowingStream<Double, Error> {
        AsyncThrowingStream { continuation in
            Task {
                do {
                    for step in 1...10 {
                        try await Task.sleep(for: .milliseconds(200))
                        continuation.yield(Double(step) / 10)
                    }
                    continuation.finish()
                } catch is CancellationError {
                    continuation.finish()
                } catch {
                    continuation.finish(throwing: error)
                }
            }
        }
    }
}

shouldFail disparaît de cette version : c'était un crochet de test (forcer un échec pour vérifier .failed, Leçon 27) qui n'avait aucune raison d'être configurable dans du code livré à un utilisateur réel. Cette capacité ne disparaît pas pour autant — elle migre là où elle appartenait depuis le début, dans un vrai mock, réservé à la cible de tests :

// NOUVEAU — KaramockTests/Services/MockSongDownloading.swift
@testable import Karamock

struct MockSongDownloading: SongDownloading {
    var shouldFail = false

    func download(_ song: Song) -> AsyncThrowingStream<Double, Error> {
        AsyncThrowingStream { continuation in
            Task {
                do {
                    for step in 1...10 {
                        try await Task.sleep(for: .milliseconds(200))
                        if shouldFail, step == 5 {
                            throw SimulatedDownloadFailure()
                        }
                        continuation.yield(Double(step) / 10)
                    }
                    continuation.finish()
                } catch is CancellationError {
                    continuation.finish()
                } catch {
                    continuation.finish(throwing: error)
                }
            }
        }
    }
}

private struct SimulatedDownloadFailure: Error {}

Le nom MockSongDownloading se libère du même coup pour ce à quoi il correspond réellement — un vrai mock, dans KaramockTests/Services/, à côté de KaramockTests/Repositories/MockDownloadedSongsRepository.swift (convention déjà en place, dossier par dossier miroir de la cible d'app). Dernier ajustement, dans KaramockContainer.swift :

var songDownloading: Factory<SongDownloading> {
    self { SimulatedSongDownloading() }
}

Conséquence à anticiper : le contournement manuel évoqué en Leçon 27 pour vérifier .failed (surcharger Container.shared.songDownloading depuis un #Preview avec MockSongDownloading(shouldFail: true)) ne fonctionne plus — ce type n'existe désormais que dans la cible de tests, invisible depuis l'app. C'est voulu : la bonne façon de vérifier .failed devient un vrai test, exactement le sujet de la Leçon 30.

Pourquoi ce n'est pas un désaveu de l'audit, juste son application correcte

L'audit est un instantané du 2026-07-28 — une photo du code à un instant donné, pas une spécification figée à appliquer aveuglément des semaines plus tard. Les Leçons 26 et 27 ont changé un fait sur lequel reposait sa recommandation #9 (l'existence, ou non, d'une vraie implémentation réseau à venir). Continuer à suivre la lettre d'une recommandation devenue incompatible avec des décisions prises entre-temps serait le signe qu'on exécute une checklist sans la comprendre — l'audit lui-même, dans son esprit ("des données de test ne devraient pas polluer le bundle de production"), reste totalement valide ; c'est seulement son plan d'action précis qui ne tient plus tel quel.

Scénario de vérification, étape par étape :
  1. Build du projet (⌘B) : doit réussir sans erreur.
  2. Affiche les paroles d'une chanson : comportement identique à avant (fetch, cache, fallback en cas d'erreur) — seul le code interne a changé.
  3. Dans Xcode, vérifie que LyricsMapper.map(...) compile sans await depuis CachedLyricsRepository.
  4. Vérifie que URLSessionLyricsFetching est nonisolated struct, que lyricsURL est privée à l'intérieur, et que les deux await lyricsFetcherLogger.error(...) sont toujours là (ils n'ont pas à disparaître).
  5. Vérifie que plus aucun fichier ne référence SimpleDownloadedSongsRepository ni MockSongDownloading dans la cible d'app — seulement InMemoryDownloadedSongsRepository et SimulatedSongDownloading.
  6. Lance un téléchargement normal : doit toujours réussir (0% à 100%, .downloaded) — SimulatedSongDownloading n'a plus de shouldFail, il réussit toujours.
  7. Vérifie que KaramockTests/Services/MockSongDownloading.swift existe et compile dans la cible de tests uniquement.
