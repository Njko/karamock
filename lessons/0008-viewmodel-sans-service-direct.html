Leçon 8 · Architecture en couches (3/N) — nettoyage

Le ViewModel ne doit pas connaître le Service

Un rattrapage avant d'aller plus loin : SongDownloadViewModel dépend encore directement de SongDownloading, en plus du DownloadSongUseCase de la Leçon 7. Ce sont deux façons différentes d'accéder à de la donnée externe dans la même classe — la règle de dépendance de la Clean Architecture dit que ça ne devrait pas être le cas.

Pourquoi cette leçon : depuis la Leçon 6, SongDownloadViewModel tient à la fois service: SongDownloading (Leçon 6) et markSongAsDownloaded: DownloadSongUseCase (Leçon 7). Le second respecte la règle "présentation → domaine" ; le premier la contourne. Avant d'ajouter la Leçon 9 (injection de dépendance) par-dessus cette incohérence, on la corrige : plus aucune dépendance du ViewModel ne pointera directement vers un Service.

La règle de dépendance, et où elle est violée ici

Le texte fondateur de la Clean Architecture (Robert C. Martin) pose une seule règle structurante : les dépendances de code source ne peuvent pointer que vers l'intérieur — une couche externe (UI, réseau, disque) ne doit jamais être visible directement par une couche plus interne qu'elle ne devrait connaître. Appliquée ici : le ViewModel (couche présentation) ne devrait parler qu'au Domain (UseCase), jamais directement à un Service (couche externe, même mockée).

// État actuel (Leçons 6-7) — deux chemins d'accès à de la donnée externe
@MainActor
@Observable
final class SongDownloadViewModel {
    private let service: SongDownloading              // ← accès direct au Service
    private let markSongAsDownloaded: DownloadSongUseCase  // ← accès via le Domain

    func startDownload() {
        Task {
            for await progress in service.download(song) {  // ← Service appelé directement
                state = .downloading(progress: progress)
            }
            await markSongAsDownloaded(song)
            state = .downloaded
        }
    }
}

service et markSongAsDownloaded sont deux frontières différentes dans la même classe : l'une respecte la règle de dépendance, l'autre non. Un lecteur qui découvre ce code est en droit de demander pourquoi ce n'est pas cohérent.

Absorber le Service dans le UseCase

DownloadSongUseCase représente déjà "télécharger une chanson" comme intention métier — il lui manquait juste la partie "obtenir la progression". Un UseCase peut légitimement orchestrer plusieurs dépendances (ici Service et Repository) tant qu'elles servent une seule intention utilisateur :

struct DownloadSongUseCase: Sendable {
    let service: SongDownloading
    let repository: DownloadedSongsRepository

    init(
        service: SongDownloading = MockSongDownloading(),
        repository: DownloadedSongsRepository
    ) {
        self.service = service
        self.repository = repository
    }

    func callAsFunction(_ song: Song) -> AsyncStream<Double> {
        AsyncStream { continuation in
            Task {
                for await progress in service.download(song) {
                    continuation.yield(progress)
                }
                await repository.add(song)
                continuation.finish()
            }
        }
    }
}

service retrouve sa valeur par défaut (interchangeable, sans état — la règle de la Leçon 7). repository reste obligatoire, toujours pour la même raison : il doit pointer vers l'instance partagée. Le UseCase absorbe le flux de progression et l'enregistrement dans la Bibliothèque — une seule sortie (AsyncStream<Double>), un seul point d'entrée pour le ViewModel.

continuation.yield depuis un Task non isolé — pourquoi c'est sûr

Le Task créé dans AsyncStream { continuation in Task { … } } n'hérite d'aucun acteur particulier (DownloadSongUseCase est une struct ordinaire). Ça ne pose pas de problème : AsyncStream.Continuation est explicitement conçu pour être appelé depuis n'importe quel contexte de concurrence, y compris concurremment — c'est tout l'intérêt du type. Le seul endroit qui a besoin d'un await explicite reste repository.add(song), puisque lui est isolé à son propre acteur.

Le ViewModel : une seule dépendance externe

@MainActor
@Observable
final class SongDownloadViewModel {
    private(set) var state: DownloadState = .notDownloaded

    private let song: Song
    private let downloadSong: DownloadSongUseCase

    init(song: Song, downloadSong: DownloadSongUseCase) {
        self.song = song
        self.downloadSong = downloadSong
    }

    func startDownload() {
        guard state == .notDownloaded || state == .failed else { return }
        state = .downloading(progress: 0)
        Task {
            for await progress in downloadSong(song) {
                state = .downloading(progress: progress)
            }
            state = .downloaded
        }
    }
}

service a disparu de la liste des propriétés du ViewModel — il ne connaît plus que DownloadSongUseCase. La forme du startDownload() ne change presque pas (toujours un Task, toujours un for await), mais le nom de ce qu'il consomme change de sens : avant, un flux technique venu du Service ; maintenant, une intention métier complète.

Le seul appelant à mettre à jour : SongOptionsSheet

.task {
    if downloadViewModel == nil {
        downloadViewModel = SongDownloadViewModel(
            song: song,
            downloadSong: DownloadSongUseCase(repository: downloadedSongsRepository)
        )
    }
}

DownloadSongUseCase(repository:) — service retombe sur sa valeur par défaut, comme avant. C'est le seul endroit de tout le projet qui a besoin d'être modifié pour ce refactoring : la preuve concrète que cacher le Service derrière le UseCase a réduit, pas augmenté, le nombre d'endroits à connaître.
