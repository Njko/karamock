Leçon 12 · Architecture en couches (8/N)

Les ViewModels dans le Container : la Vue n'injecte plus que ce dont elle a besoin

La Leçon 11 a fait migrer player, downloadedSongsRepository et les deux UseCases vers Container. Mais SongOptionsSheet et LibraryView injectent encore un UseCase et construisent elles-mêmes leur ViewModel dans .task. Cette leçon pousse le graphe un cran plus loin : les ViewModels rejoignent aussi le Container, et chaque Vue n'injecte plus que le ViewModel dont elle a besoin.

Pourquoi cette leçon : tu l'as repéré toi-même en relisant la Leçon 11 — SongOptionsSheet injecte downloadSong: DownloadSongUseCase puis l'assemble elle-même dans SongDownloadViewModel(song:downloadSong:). C'est une fuite de couche : une Vue n'a normalement pas besoin de connaître les UseCases, seulement le ViewModel qui les orchestre pour elle. Faire porter cet assemblage par Container referme cette fuite, et complète la Dependency Rule appliquée à la construction (Leçon 10) jusqu'à la couche ViewModel.

Ce qui reste à corriger

État actuel de SongOptionsSheet, tel que tu l'as poussé sur ta machine après la Leçon 11 :

struct SongOptionsSheet: View {
    @Injected(\.player) private var player
    @Environment(\.dismiss) private var dismiss
    @Injected(\.downloadSong) private var downloadSong

    let song: Song
    @State private var downloadViewModel: SongDownloadViewModel?
    // …

    var body: some View {
        // …
        .task {
            if downloadViewModel == nil {
                downloadViewModel = SongDownloadViewModel(song: song, downloadSong: downloadSong)
            }
        }
    }
}

Container a bien fini de cacher DownloadedSongsRepository à la Vue depuis la Leçon 11. Mais SongOptionsSheet connaît encore DownloadSongUseCase — elle l'injecte, puis sait comment l'assembler avec song pour produire un SongDownloadViewModel. Deux responsabilités qui n'ont rien à voir avec l'affichage d'une feuille d'options. L'objectif : que SongOptionsSheet ne connaisse plus que SongDownloadViewModel.

ParameterFactory : une fabrique qui prend un paramètre

LibraryViewModel ne dépend que d'un UseCase — rien de spécifique à une instance. Mais SongDownloadViewModel a besoin d'un song: Song précis à chaque résolution, un paramètre que Container ne peut pas deviner. Factory a un type dédié à ce cas, ParameterFactory<P, T>, défini directement dans le code source de la librairie :

extension Container {
    var parameterService: ParameterFactory<Int, MyServiceType> {
        self { ParameterService(value: $0) }
    }
}

let myService = Container.shared.parameterService(16)

Le principe : le type du paramètre devient le premier paramètre générique, et la closure de fabrication le reçoit en argument. On résout en appelant la fabrique comme une fonction, avec la valeur en argument.

Container : les ViewModels s'ajoutent aux UseCases

import FactoryKit

extension Container {
    // player, downloadedSongsRepository, downloadSong, fetchDownloadedSongs : inchangés

    @MainActor
    var libraryViewModel: Factory<LibraryViewModel> {
        self { LibraryViewModel(fetchDownloadedSongs: self.fetchDownloadedSongs()) }
    }

    @MainActor
    var songDownloadViewModel: ParameterFactory<Song, SongDownloadViewModel> {
        self { song in SongDownloadViewModel(song: song, downloadSong: self.downloadSong()) }
    }
}

L'annotation @MainActor est nécessaire : LibraryViewModel et SongDownloadViewModel sont tous les deux @MainActor @Observable final class (Leçon 9), et Factory demande que la fabrique porte la même isolation que le type qu'elle construit.

LibraryView : @InjectedObservable

LibraryViewModel ne prend pas de paramètre à la résolution, donc on peut l'injecter directement avec @InjectedObservable, le pendant observable de @Injected :

import FactoryKit

struct LibraryView: View {
    @InjectedObservable(\.libraryViewModel) private var viewModel
    @State private var selectedSong: Song?

    var body: some View {
        NavigationStack {
            Group {
                if !viewModel.songs.isEmpty {
                    List(viewModel.songs) { song in
                        Button {
                            selectedSong = song
                        } label: {
                            SongRow(song: song)
                        }
                        .buttonStyle(.plain)
                    }
                    .listStyle(.plain)
                } else {
                    ContentUnavailableView(
                        "Aucune chanson téléchargée",
                        systemImage: "arrow.down.circle",
                        description: Text("Télécharge une chanson depuis sa fiche pour la retrouver ici.")
                    )
                }
            }
            .navigationTitle("Bibliothèque")
        }
        .task { await viewModel.refresh() }
        .refreshable { await viewModel.refresh() }
        .sheet(item: $selectedSong) { song in
            SongOptionsSheet(song: song)
        }
    }
}

Deux choses disparaissent en même temps : @Injected(\.fetchDownloadedSongs) — la Vue ne sait plus que ce UseCase existe — et tout le couple @State private var viewModel: LibraryViewModel? / if viewModel == nil { viewModel = … }. viewModel n'est plus optionnel : @InjectedObservable le résout une seule fois, à la première utilisation, comme le documente Factory lui-même.

SongOptionsSheet : la limite du compile-time safe

Ici, @Injected/@InjectedObservable ne suffisent pas. Le code source de Factory est explicite sur ce point : une ParameterFactory ne peut pas être injectée par un property wrapper, faute de moyen de lui transmettre le paramètre avant l'initialisation de ce wrapper. Il faut donc appeler le Container directement — mais seulement pour résoudre le ViewModel, plus le UseCase :

import FactoryKit

struct SongOptionsSheet: View {
    @Injected(\.player) private var player
    @Environment(\.dismiss) private var dismiss

    let song: Song
    @State private var downloadViewModel: SongDownloadViewModel?
    // … le reste de l'état du formulaire, inchangé

    var body: some View {
        // … inchangé
        .task {
            if downloadViewModel == nil {
                downloadViewModel = Container.shared.songDownloadViewModel(song)
            }
        }
    }
}

SongOptionsSheet ne référence plus ni DownloadedSongsRepository ni DownloadSongUseCase — seulement SongDownloadViewModel, le seul type dont elle a réellement besoin pour s'afficher.

Avant (Leçon 11)Après (Leçon 12)
La Vue injecte un UseCase (@Injected(\.downloadSong))La Vue résout directement son ViewModel
La Vue assemble elle-même le ViewModel dans .taskContainer assemble le ViewModel, UseCase compris
LibraryView gère un viewModel optionnel à initialiser@InjectedObservable résout une fois, type non optionnel
La Vue doit connaître la signature du ViewModel pour l'appelerLa Vue ne connaît que le keyPath ou la fabrique à appeler
Pourquoi SongOptionsSheet appelle encore Container.shared directement

Ce n'est pas une régression par rapport à @Injected — c'est une limite documentée de ParameterFactory elle-même : un property wrapper est initialisé avant que la vue n'ait la moindre chance de lui fournir un paramètre à l'exécution, donc il ne peut tout simplement pas exister d'@Injected paramétré. Factory documente lui-même ce contournement — appeler le Container directement reste la seule solution pour ce cas précis, y compris dans les exemples officiels de la librairie. Le gain reste réel : ce que la Vue connaît s'arrête au ViewModel, elle n'a plus besoin de savoir qu'un UseCase ou un Repository existent derrière.

.singleton sur un ViewModel : une fausse bonne idée

libraryViewModel et songDownloadViewModel restent volontairement au scope par défaut (.unique), sans .singleton. Un ViewModel porte un état propre à un écran affiché à un instant donné (songs, state) — le passer en singleton ferait fuiter cet état d'une apparition de la Vue à la suivante, exactement le problème inverse de celui que .singleton résout pour player (Leçon 11), qui lui doit rester partagé entre tous les écrans.

Source primaire recommandée
Factory.swift et Injections.swift sur le dépôt officiel — les commentaires de documentation au-dessus de ParameterFactory et InjectedObservable couvrent exactement les deux mécanismes de cette leçon, avec leurs limites.
