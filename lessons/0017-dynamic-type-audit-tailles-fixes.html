Leçon 17 · Accessibilité (4/N)

Dynamic Type : l'audit des autres tailles fixes

La Leçon 16 a laissé une question ouverte : PlaylistCard (150×150), SongRow (50×50) et PlaylistCoverHeader (220 de hauteur) ont tous une taille fixe quelque part — est-ce un problème ? La Leçon 16 avait déjà montré avec LyricsView qu'une taille fixe n'est pas automatiquement un bug. Cette leçon termine l'audit, et une seule des trois vues a un vrai problème.

Pourquoi cette leçon : le réflexe utile à transmettre à toute l'équipe n'est pas "chercher les tailles fixes et les éliminer" — c'est savoir distinguer une taille fixe inoffensive d'une taille fixe qui va silencieusement couper du texte à un réglage d'accessibilité élevé. C'est un jugement de revue de code, pas une règle automatique, et c'est justement ce qui le rend difficile à faire appliquer sans exemples concrets comme celui-ci.

SongRow : rien à corriger

struct SongRow: View {
    let song: Song

    var body: some View {
        HStack(spacing: 12) {
            RoundedRectangle(cornerRadius: 8)
                .fill(.quaternary)
                .frame(width: 50, height: 50)

            VStack(alignment: .leading, spacing: 2) {
                Text(song.title)
                Text(song.artist)
                    .font(.subheadline)
                    .foregroundStyle(.secondary)
            }
            Spacer()
        }
        .padding(.vertical, 4)
    }
}

Le rectangle 50×50 est une simple pochette factice — comme dans MiniPlayerBar (Leçon 15), une taille fixe pour un élément décoratif n'a pas besoin de suivre le texte. Le titre et l'artiste utilisent des styles par défaut/sémantiques (.body implicite, .subheadline), donc ils grossissent normalement. Et surtout : rien ici ne limite la hauteur de la rangée. Si le texte s'étale sur deux lignes à un réglage de texte plus grand, le HStack grandit avec lui — aucune information n'est perdue, la rangée devient juste un peu plus haute. Rien à corriger.

PlaylistCard : la vraie régression

struct PlaylistCard: View {
    let playlist: Playlist

    var body: some View {
        LinearGradient(colors: playlist.gradientColors, startPoint: .topLeading, endPoint: .bottomTrailing)
            .frame(width: 150, height: 150)
            .overlay(alignment: .bottomLeading) {
                Text(playlist.title)
                    .font(.headline)
                    .foregroundStyle(.white)
                    .padding(10)
            }
            .clipShape(RoundedRectangle(cornerRadius: 16))
    }
}

La différence critique avec SongRow : ce .clipShape(RoundedRectangle(cornerRadius: 16)) à la fin. La carte entière — dégradé et superposition de texte — est découpée au gabarit fixe de 150×150. .font(.headline) grossit bien avec Dynamic Type, mais rien ne limite le texte à tenir dans la carte : à un réglage de texte élevé, le titre s'étale sur plus de lignes, dépasse les 150×150, et se fait couper net par le masque — sans les trois petits points d'une troncature classique, juste une coupe brutale au milieu d'un mot. C'est une vraie perte d'information, pas juste un défaut esthétique.

La correction

struct PlaylistCard: View {
    let playlist: Playlist

    var body: some View {
        LinearGradient(colors: playlist.gradientColors, startPoint: .topLeading, endPoint: .bottomTrailing)
            .frame(width: 150, height: 150)
            .overlay(alignment: .bottomLeading) {
                Text(playlist.title)
                    .font(.headline)
                    .foregroundStyle(.white)
                    .padding(10)
                    .lineLimit(2)
                    .dynamicTypeSize(...DynamicTypeSize.accessibility1)
            }
            .clipShape(RoundedRectangle(cornerRadius: 16))
            .accessibilityShowsLargeContentViewer {
                Text(playlist.title)
            }
    }
}

Trois ajustements, chacun avec un rôle précis :

  • .lineLimit(2) plafonne le nombre de lignes, quel que soit le réglage de texte — le titre ne peut plus s'étaler indéfiniment dans la carte.
  • .dynamicTypeSize(...DynamicTypeSize.accessibility1) plafonne la taille de police à laquelle ce texte précis peut grossir — même à 2 lignes, un texte à la taille d'accessibilité maximale serait encore trop grand pour 150×150.
  • .accessibilityShowsLargeContentViewer { Text(playlist.title) } rend au texte plafonné ce que les deux lignes précédentes lui ont retiré : un appui long sur la carte affiche le titre complet, en grand, dans une bulle temporaire — sans les limites de .lineLimit ni de .dynamicTypeSize.
Est-ce que ça contredit la Leçon 16 ?

La Leçon 16 disait : laisse le bouton play/pause grossir avec le texte, ne le plafonne pas. Ici on plafonne délibérément. Pas de contradiction : le bouton de la Leçon 16 n'avait aucune contrainte d'espace autour de lui — le laisser grossir ne cassait rien. PlaylistCard, elle, doit tenir dans une grille de cartes de taille fixe (PlaylistSection) : la laisser grossir sans limite casserait la mise en page de toute la grille, pas juste cette carte. La documentation Apple sur dynamicTypeSize est explicite sur ce point : plafonner est acceptable pour des éléments déjà volumineux dans une mise en page contrainte, jamais comme solution de facilité pour éviter de gérer une mise en page qui devrait s'adapter. Et c'est précisément pour ne pas perdre l'information au passage qu'on ajoute accessibilityShowsLargeContentViewer juste après.

PlaylistCoverHeader : un problème différent, une solution différente

struct PlaylistCoverHeader: View {
    let playlist: Playlist

    var body: some View {
        LinearGradient(colors: playlist.gradientColors, startPoint: .topLeading, endPoint: .bottomTrailing)
            .frame(height: 220)
            .overlay {
                Text(playlist.title)
                    .font(.title2.bold())
                    .foregroundStyle(.white)
                    .multilineTextAlignment(.center)
                    .padding()
            }
    }
}

Remarque ce qui manque ici par rapport à PlaylistCard : pas de .clipShape. Un .overlay ne redimensionne jamais la vue de base et n'est pas non plus automatiquement découpé à ses bords — sans masque, un titre trop long ne serait pas coupé, il déborderait simplement des 220pt et viendrait chevaucher visuellement ce qui suit dans le ScrollView (la liste des chansons). Ce n'est pas de la perte d'information comme PlaylistCard, mais un vrai chevauchement visuel — un problème différent, pas le même bug avec un habillage différent.

Et surtout, contrairement à PlaylistCard, rien ici n'oblige la bannière à rester à 220pt : c'est un élément unique en haut d'un écran qui défile, pas une carte dans une grille de cartes toutes identiques. Plafonner le texte comme pour PlaylistCard serait donc la mauvaise réponse ici — la bonne réponse est de laisser la bannière grandir pour accueillir le texte, plutôt que de contraindre le texte à tenir dans la bannière.

Le blocage technique : un .overlay ne fait jamais grandir sa vue de base, quelle que soit la taille de son contenu — la taille rapportée d'un .overlay est toujours celle de la vue principale seule. Un ZStack, lui, rapporte l'union (le maximum) des tailles de tous ses enfants. En remplaçant l'un par l'autre, et .frame(height:) par .frame(minHeight:), le dégradé peut s'étirer pour couvrir toute la hauteur que le titre réclame :

struct PlaylistCoverHeader: View {
    let playlist: Playlist

    var body: some View {
        ZStack {
            LinearGradient(colors: playlist.gradientColors, startPoint: .topLeading, endPoint: .bottomTrailing)
                .frame(minHeight: 220)

            Text(playlist.title)
                .font(.title2.bold())
                .foregroundStyle(.white)
                .multilineTextAlignment(.center)
                .padding()
        }
    }
}

À un réglage de texte par défaut, rien ne change visuellement : le dégradé fait toujours 220pt. À un réglage plus élevé, le ZStack grandit pour loger le titre en entier, et pousse le reste du contenu du ScrollView vers le bas en conséquence — aucune découpe, aucun chevauchement, et pas besoin de plafonner ni de restituer quoi que ce soit via le Large Content Viewer, puisque rien n'est jamais tronqué.

Restricting Dynamic Type Sizes (useyourloaf.com) — l'usage de .dynamicTypeSize(...) pour plafonner un élément à mise en page contrainte, avec l'avertissement explicite de ne jamais s'en servir pour contourner un vrai problème de mise en page. Vérifie ta compréhension

1. Pourquoi SongRow ne nécessite-t-elle aucune correction, malgré son rectangle fixe 50×50 ?

2. Quelle est la différence critique entre PlaylistCard (buguée) et SongRow (correcte) ?

3. Pourquoi ajouter .accessibilityShowsLargeContentViewer après avoir plafonné .dynamicTypeSize sur le titre de PlaylistCard ?
