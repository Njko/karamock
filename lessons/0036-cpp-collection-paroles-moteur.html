Leçon 36 · Interop Swift/C++ (2/N)

Envoyer les paroles horodatées au moteur C++

La Leçon 35 a prouvé le mécanisme avec un entier bidon. Cette leçon fait traverser la frontière à quelque chose de réel : la collection de paroles horodatées que LyricsMapper calcule déjà côté Swift (découpage des lignes, calcul des intervalles — inchangé, cette logique reste en Swift). Objectif unique : que cette collection arrive intacte côté C++, stockée dans une structure que le futur moteur graphique pourra consulter. Toujours aucun rendu — la surface Metal et le premier pixel affiché viendront dans une leçon dédiée.

Ce qui existe déjà, ce qui change

LyricsMapper.map(rawText:duration:) -> [LyricsLine] (Leçon 28) produit un tableau de LyricsLine — id: UUID, time: TimeInterval, text: String. FullScreenPlayerViewModel.loadLyrics() l'obtient déjà, via CachedLyricsRepository, et l'affiche avec LyricsView (SwiftUI pur). Cette leçon ne touche à aucun de ces deux comportements : LyricsView continue d'afficher les paroles exactement comme avant. Elle ajoute un second chemin, en parallèle — la même collection part aussi vers un objet C++ qui la garde en mémoire, préparant le terrain pour la leçon où ce chemin C++ remplacera LyricsView.

Le piège : une String Swift ne devient pas un std::string toute seule

Point vérifié précisément avant d'écrire quoi que ce soit, parce que la documentation officielle prête à confusion sur ce point exact. Elle montre ceci comme fonctionnant "normalement" :

// Doc officielle swift.org — fonctionne, mais pas pour la raison qu'on croit
void printWelcomeMessage(const std::string &name);
printWelcomeMessage("Thomas")   // ✅ compile

Ça compile — mais pas parce que Swift convertit une String en std::string automatiquement. C'est parce que "Thomas" est un littéral, et que std::string est rendu conforme à ExpressibleByStringLiteral côté Swift. Dès qu'on remplace le littéral par une variable, ça ne compile plus :

let songTitle = song.title
printWelcomeMessage(songTitle)   // ❌ ne compile pas
"cannot convert value of type 'String' to expected argument type 'std.__1.string'"

Confirmé dans le code source de la bibliothèque standard Swift : le seul chemin d'une String vers un std::string est un initialiseur explicite, std.string(_:) — "Swift does not convert C++ std::string type to Swift's String type automatically." Le cast est obligatoire, partout, y compris pour construire un champ std::string d'un struct C++ depuis Swift :

printWelcomeMessage(std.string(songTitle))   // ✅ compile

La structure côté C++ : LyricsStore, un objet qui accumule

Question posée avant d'écrire le header : comment faire arriver plusieurs lignes côté C++ ? Deux approches existent techniquement — Swift construit lui-même un std::vector et le passe en un seul appel, ou Swift appelle une fonction C++ une fois par ligne et laisse le std::vector entièrement du côté C++. La seconde est retenue ici, pour une raison précise : c'est la seule dont chaque mécanisme est documenté noir sur blanc par swift.org (constructeurs → initialiseurs Swift, fonctions membres non-const → méthodes mutating, std.string(_:)) — construire un std::vector depuis Swift fonctionne aussi (`push_back(_:)`, testé dans la suite de tests officielle de Swift), mais ne fait l'objet d'aucune section du guide officiel, et la documentation prévient explicitement que Swift recopie profondément un conteneur C++ à chaque usage. Éviter cette zone grise pour l'instant.

// NOUVEAU — Engine/LyricsStore.hpp
#pragma once
#include <string>
#include <vector>
#include <cstddef>

namespace karamock {

struct LyricLine {
    double time;
    std::string text;
};

class LyricsStore {
public:
    LyricsStore() = default;

    void reserve(std::size_t count);
    void addLine(double time, const std::string& text);
    void clear();

    std::size_t lineCount() const;
    double timeAt(std::size_t index) const;

private:
    std::vector<LyricLine> lines_;
};

} // namespace karamock
// NOUVEAU — Engine/LyricsStore.cpp
#include "LyricsStore.hpp"

namespace karamock {

void LyricsStore::reserve(std::size_t count) {
    lines_.reserve(count);
}

void LyricsStore::addLine(double time, const std::string& text) {
    lines_.push_back(LyricLine{time, text});
}

void LyricsStore::clear() {
    lines_.clear();
}

std::size_t LyricsStore::lineCount() const {
    return lines_.size();
}

double LyricsStore::timeAt(std::size_t index) const {
    return lines_[index].time;
}

} // namespace karamock

namespace karamock : premher type C++ un peu conséquent du projet — la Leçon 35 n'avait qu'une fonction globale. Ce n'est pas indispensable techniquement, mais évite une renomination plus tard quand un deuxième type C++ (le moteur de rendu) arrivera. const std::string& plutôt que std::string en paramètre d'addLine : évite une copie superflue à l'appel — le push_back interne en fera une de toute façon pour peupler le vector.

Dans Xcode : clic droit sur le groupe Engine → Add Files to "Karamock"... → sélectionne les deux nouveaux fichiers. Le bridging header pointe maintenant vers LyricsStore.hpp à la place de l'ancien fichier de preuve :

// Karamock-Bridging-Header.h
#include "Engine/LyricsStore.hpp"

L'appel depuis Swift : var, pas let

import CxxStdlib est nécessaire pour obtenir std.string côté Swift. Le type C++ LyricsStore est importé comme une value type (un struct Swift) — ses méthodes non-const (reserve, addLine, clear) deviennent des méthodes mutating, donc la propriété qui le porte doit être var :

// CORRECTION — ViewModels/FullScreenPlayerViewModel.swift
import Foundation
import CxxStdlib

@MainActor
@Observable
final class FullScreenPlayerViewModel {
    private(set) var lyrics: [LyricsLine] = placeholderLyrics
    private var lyricsStore = karamock.LyricsStore()

    private let song: Song
    private let fetchLyrics: FetchLyricsUseCase

    init(song: Song, fetchLyrics: FetchLyricsUseCase) {
        self.song = song
        self.fetchLyrics = fetchLyrics
    }

    func loadLyrics() async {
        do throws(LyricsError) {
            lyrics = try await fetchLyrics(for: song)
        } catch {
            switch error {
            case .notFound:
                lyrics = [LyricsLine(time: 0, text: "Paroles indisponibles pour cette chanson.")]
            case .network:
                lyrics = [LyricsLine(time: 0, text: "Connexion impossible. Réessayez")]
            case .invalidURL, .malformedResponse:
                lyrics = [LyricsLine(time: 0, text: "Paroles indisponibles pour le moment.")]
            }
        }
        sendLyricsToEngine()
    }

    private func sendLyricsToEngine() {
        lyricsStore.clear()
        lyricsStore.reserve(lyrics.count)
        for line in lyrics {
            lyricsStore.addLine(line.time, std.string(line.text))
        }
        assert(lyricsStore.lineCount() == lyrics.count)
    }
}

sendLyricsToEngine() est appelée après le do/catch, pas seulement dans la branche réussie : même les messages de repli à une seule ligne ("Paroles indisponibles...") doivent atteindre le moteur, pour rester cohérent avec ce que LyricsView affiche déjà. L'assert ne coûte rien en release (retiré à la compilation) et confirme, en debug, que rien n'a été perdu dans la traversée.

Un piège pour plus tard : std::string compte des octets, pas des caractères

Vérifié dans la suite de tests officielle de Swift : l'encodage est garanti UTF-8 et l'aller-retour String → std::string → String ne perd rien. Mais size() compte des octets, pas des caractères — "Éloignés" fait 9 caractères mais 10 octets en UTF-8, à cause du "É". Sans conséquence pour cette leçon, qui ne fait que stocker et compter des lignes entières. Ça deviendra un vrai piège le jour où le moteur de rendu devra découper une ligne caractère par caractère pour l'effet de surlignage karaoké (s.substr(...) couperait au milieu d'un caractère accentué) — à garder en tête pour cette leçon-là, pas à résoudre maintenant.

Sendable et Swift 6 : non documenté par Apple pour l'interop C++

Recherche menée avant d'écrire cette leçon : ni le guide officiel swift.org sur l'interop C++, ni la session WWDC25 "Safely mix C, C++, and Swift" ne mentionnent Sendable, la concurrence ou l'isolation d'acteur. Un type C++ importé n'est pas Sendable par défaut. Tant que lyricsStore reste une propriété privée d'un ViewModel @MainActor, utilisée uniquement de façon synchrone comme ici, aucune erreur Swift 6 ne se déclenche. Le jour où le moteur de rendu (Metal) devra être touché depuis un autre contexte, il existe une macro non documentée sur swift.org mais livrée dans la toolchain depuis Swift 6.0 (SWIFT_UNCHECKED_SENDABLE, dans <swift/bridging>) — à vérifier empiriquement à ce moment-là, pas une garantie à enseigner aujourd'hui.

Pourquoi LyricsStore reste une value type, pour l'instant

Sans annotation particulière côté C++, une classe C++ importée devient un struct Swift — copiée, pas partagée par référence. C'est sans conséquence ici : lyricsStore reste toujours la même propriété du même ViewModel, jamais copiée ailleurs. Ça cessera d'être vrai le jour où le moteur devra être partagé entre le ViewModel et une vue Metal qui le pilote en parallèle — swift.org documente une annotation dédiée pour ce cas (SWIFT_SHARED_REFERENCE, "Mapping C++ Types to Swift Reference Types"). Changement d'architecture à assumer explicitement dans une leçon future, pas un défaut à corriger aujourd'hui.
