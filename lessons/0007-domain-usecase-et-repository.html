Leçon 7 · Architecture en couches (2/N)

Domain/UseCase : donner un rôle à DownloadSongUseCase

La Leçon 6 a délibérément laissé de côté la couche Domain/UseCase, faute de règle métier pour la justifier. On en a une maintenant : une chanson téléchargée doit apparaître dans la Bibliothèque.

Pourquoi cette leçon : LibraryView affiche "Bibliothèque à venir" depuis la Leçon 1 — un stub jamais rempli. La Leçon 8 va le remplir, mais il faut d'abord décider qui se souvient qu'une chanson a été téléchargée. Ce n'est ni le rôle du Service (qui sait seulement comment télécharger), ni celui du ViewModel (qui gère l'état d'un seul écran) : c'est une règle métier transverse, donc un UseCase.
Sur l'arborescence des dossiers dans cette leçon

Le code ci-dessous ne précise volontairement aucun chemin de fichier. Ton projet a déjà réorganisé Views/ par écran (Discovery/, Player/, Library/, Common/) plutôt que par type de fichier — un choix tout à fait valide, que cette leçon ne remet pas en cause. Ce qui compte ici, c'est qui a le droit de faire quoi (une vue ne parle jamais directement à un Repository, un Service ne connaît jamais le Repository, etc.) — pas l'emplacement exact des fichiers sur disque. Range DownloadedSongsRepository et DownloadSongUseCase où ça a du sens pour toi — à côté de DownloadState, dans un dossier dédié, peu importe.

Repository ≠ Service : deux rôles distincts

Le vocabulaire de MISSION.md distinguait "repository" et "service" — voici la différence concrète appliquée ici :

  • Service (SongDownloading, Leçon 6) : sait faire quelque chose — déclencher un téléchargement, appeler un système externe (ici mocké).
  • Repository (nouveau) : sait retenir une collection d'objets du domaine et y donner accès — ici, les chansons déjà téléchargées.
Correction : un Repository ne doit pas être @MainActor

Une première version de cette leçon isolait DownloadedSongsRepository à @MainActor, pour éviter d'introduire un deuxième mécanisme de concurrence dans l'exercice. C'est une mauvaise pratique dans un vrai projet : le rôle du main actor est de protéger l'UI, pas la couche donnée. Un vrai repository fait potentiellement de l'I/O (disque, réseau, base de données) — le forcer sur le thread principal sérialiserait ce travail derrière l'UI et bloquerait l'app dès que cette I/O devient un peu lente. "Si les utilisateurs le voient, @MainActor ; si seul ton code le voit, un acteur dédié" est la règle de base couramment citée par la communauté Swift (Swift Crafted — "Swift Actors: Concurrency Guide"). Apple va dans le même sens dans sa session sur les acteurs : le main actor sert le travail lié à l'UI, et tout ce qui n'en a pas besoin peut rester nonisolated ou vivre sur son propre acteur (WWDC21 — "Protect mutable state with Swift actors"). La version ci-dessous utilise donc un actor Swift ordinaire plutôt que @MainActor.

protocol DownloadedSongsRepository: Sendable {
    func songs() async -> [Song]
    func add(_ song: Song) async
}

actor InMemoryDownloadedSongsRepository: DownloadedSongsRepository {
    private var storage: [Song] = []

    func songs() async -> [Song] {
        storage
    }

    func add(_ song: Song) async {
        guard !storage.contains(song) else { return }
        storage.append(song)
    }
}

actor protège storage exactement comme @MainActor protégeait songs — un seul accès à la fois, jamais deux threads en même temps — mais avec son propre exécuteur, indépendant du thread principal. Le protocole devient Sendable et ses méthodes async : il ne présuppose plus quel acteur protège les données, seulement qu'un appel peut avoir besoin d'attendre. N'importe quelle future implémentation (UserDefaults…, CoreData…, Remote…) reste libre de choisir sa propre stratégie d'isolation sans changer le protocole.

Le nom de la classe concrète, InMemoryDownloadedSongsRepository, suit une convention courante quand une interface (DownloadedSongsRepository) peut avoir plusieurs implémentations : préfixer par la façon dont les données sont stockées. Rien qu'au nom, sans lire le code, on sait que storage vit uniquement en RAM (un simple tableau) : fermer l'app fait tout oublier. Choix délibéré, cohérent avec le périmètre 100% mocké de la mission — pas une limitation qu'on découvre par accident.

Le UseCase : coordonner Service et Repository

struct DownloadSongUseCase: Sendable {
    let repository: DownloadedSongsRepository

    func callAsFunction(_ song: Song) async {
        await repository.add(song)
    }
}

callAsFunction permet d'appeler une instance comme une fonction — markSongAsDownloaded(song) plutôt que markSongAsDownloaded.execute(song). C'est purement stylistique (tu peux préférer une méthode nommée), mais c'est une convention fréquente pour les UseCase à une seule responsabilité, qui rend l'intention très lisible à l'appel.

await repository.add(song) : DownloadSongUseCase n'est isolé à aucun acteur (une struct ordinaire), alors que repository.add l'est — à l'acteur propre de InMemoryDownloadedSongsRepository cette fois, plus à @MainActor. Swift exige donc await pour franchir cette frontière. C'est le compilateur qui te protège ici : sans ce garde-fou, deux threads pourraient modifier storage en même temps — et contrairement à la version précédente, ce garde-fou ne coûte plus rien au thread principal.

Brancher le UseCase dans le ViewModel existant

Le ViewModel de la Leçon 6 gagne un second paramètre injecté, au même titre que service — mais sans valeur par défaut :

@MainActor
@Observable
final class SongDownloadViewModel {
    private(set) var state: DownloadState = .notDownloaded

    private let song: Song
    private let service: SongDownloading
    private let markSongAsDownloaded: DownloadSongUseCase

    init(
        song: Song,
        service: SongDownloading = MockSongDownloading(),
        markSongAsDownloaded: DownloadSongUseCase
    ) {
        self.song = song
        self.service = service
        self.markSongAsDownloaded = markSongAsDownloaded
    }

    func startDownload() {
        guard state == .notDownloaded || state == .failed else { return }
        state = .downloading(progress: 0)
        Task {
            for await progress in service.download(song) {
                state = .downloading(progress: progress)
            }
            await markSongAsDownloaded(song)
            state = .downloaded
        }
    }
}
Pourquoi service a une valeur par défaut mais pas markSongAsDownloaded ?

MockSongDownloading() est sans état et interchangeable : peu importe l'instance, le comportement est identique. DownloadSongUseCase, lui, doit obligatoirement pointer vers la même instance partagée de DownloadedSongsRepository que celle que LibraryView lira (Leçon 8) — une valeur par défaut créerait silencieusement un repository isolé, et la chanson téléchargée n'apparaîtrait jamais dans la Bibliothèque, sans la moindre erreur pour te le signaler. Un paramètre obligatoire force l'appelant à réfléchir à la bonne instance. On reviendra sur ce genre de risque en Leçon 9.

Où vit l'instance partagée, pour l'instant

En attendant la Leçon 9, on suit exactement le même schéma déjà en place pour player — un @State dans RootTabView, exposé via @Entry :

extension EnvironmentValues {
    @Entry var player = PlayerState()
    @Entry var downloadedSongsRepository: DownloadedSongsRepository = InMemoryDownloadedSongsRepository()
}

struct RootTabView: View {
    @State var player = PlayerState()
    @State var downloadedSongsRepository = InMemoryDownloadedSongsRepository()

    var body: some View {
        TabView {
            DiscoveryView()
                .tabItem { Label("Découvrir", systemImage: "book.closed.fill") }
            LibraryView()
                .tabItem { Label("Bibliothèque", systemImage: "music.note.list") }
        }
        .environment(\.player, player)
        .environment(\.downloadedSongsRepository, downloadedSongsRepository)
        // ... .overlay et .fullScreenCover inchangés
    }
}

Et SongOptionsSheet lit ce repository pour construire le UseCase, au même endroit où il construisait déjà le ViewModel :

struct SongOptionsSheet: View {
    @Environment(\.player) private var player
    @Environment(\.dismiss) private var dismiss
    @Environment(\.downloadedSongsRepository) private var downloadedSongsRepository

    let song: Song
    @State private var downloadViewModel: SongDownloadViewModel?
    // ... @State existants inchangés (mode, singerName, adjustVolumes, pitch, tempo)

    var body: some View {
        ScrollView {
            VStack(alignment: .leading, spacing: 20) {
                SongHeader(song: song)

                if let downloadViewModel {
                    DownloadButton(state: downloadViewModel.state, startDownload: downloadViewModel.startDownload)
                }

                // ... ModeCard, TextField, Toggle, Sliders, boutons inchangés
            }
            .padding()
        }
        .task {
            if downloadViewModel == nil {
                downloadViewModel = SongDownloadViewModel(
                    song: song,
                    markSongAsDownloaded: DownloadSongUseCase(repository: downloadedSongsRepository)
                )
            }
        }
    }
}

Rien à changer dans DownloadButton lui-même : il ne connaît que DownloadState et une closure, jamais le ViewModel ni le UseCase — cette séparation, déjà en place dans ton code, est exactement le genre de découplage que cette leçon généralise à la couche du dessous.

Deux @Entry à la main, ça commence à sentir le problème

RootTabView accumule maintenant un @State + une ligne .environment(\.xxx, xxx) par dépendance partagée. Ça fonctionne, mais ça ne passera pas à l'échelle indéfiniment : chaque nouvelle dépendance (un futur repository de playlists, un service d'authentification…) répète le même geste manuel, et rien n'empêche d'oublier une injection dans une Preview ou un test. C'est exactement le problème que la Leçon 9 (stratégies d'injection de dépendance) va résoudre avec un composition root unique.

Conséquence pour la Leçon 8 : lire un repository-acteur n'est plus synchrone

DownloadedSongsRepository.songs() est maintenant async — LibraryView ne pourra plus lire repository.songs comme une simple propriété stockée. Elle devra l'await, typiquement dans un .task, comme SongOptionsSheet le fait déjà pour construire son ViewModel. C'est le prix normal d'un repository correctement isolé — on verra en Leçon 8 comment la Bibliothèque se tient à jour proprement.
