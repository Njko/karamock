Leçon 25 · Nettoyage architecture (2/N)

Inverser la dépendance : les protocoles vivent dans Domain, pas dans Data

La Leçon 24 a sorti les entités métier des dossiers Views/. L'audit signale un problème voisin, plus subtil : les contrats (LyricsRepository, DownloadedSongsRepository, SongDownloading, LyricsFetching) sont eux aussi déclarés hors du Domain — dans les fichiers mêmes de leurs implémentations. Cette leçon les en sort, sans changer un seul comportement.

Pourquoi cette leçon : la mission voulait une architecture en couches "pour être capable de discuter de structuration d'app à un niveau Tech Lead". Le sujet ici a un nom précis en ingénierie logicielle — le Dependency Inversion Principle (le "D" de SOLID) — et c'est le genre de vocabulaire qu'on doit pouvoir relier à du code concret en entretien, pas seulement réciter.

Ce que l'audit a trouvé

Point #4 de l'audit : "LyricsRepository, DownloadedSongsRepository, SongDownloading sont définis dans les couches Data/Services. La couche Domain dépend d'eux sans les 'posséder' — violation directe du Dependency Inversion Principle."

// ACTUEL (incorrect)
Domain (UseCase) ──dépend de──▶ Data (protocole déclaré dans CachedLyricsRepository.swift)

// CORRECT (Clean Architecture)
Data (implémentation) ──implémente──▶ Domain/Interfaces (protocole)
Domain (UseCase) ──dépend de──▶ Domain/Interfaces (protocole)

Concrètement aujourd'hui : FetchLyricsUseCase (Domain) déclare let repository: LyricsRepository — mais pour savoir ce qu'est LyricsRepository, il faut aller lire Repositories/CachedLyricsRepository.swift (Data), qui contient le protocole et son unique implémentation dans le même fichier. Domain dépend d'un détail d'organisation de Data. Si Data réorganise ses fichiers, ou si une deuxième implémentation apparaît un jour (un RemoteDownloadedSongsRepository, par exemple), le contrat que Domain utilise reste accroché au hasard à l'une des deux — sans raison de principe pour ça.

Le Dependency Inversion Principle dit l'inverse : ni Domain ni Data ne devraient dépendre l'un de l'autre directement — les deux devraient dépendre d'une abstraction partagée. Ici, cette abstraction, c'est le protocole — et c'est Domain qui doit le posséder, parce que c'est Domain qui exprime le besoin métier ("j'ai besoin de récupérer des paroles"), pas Data qui décide comment le satisfaire.

Quatre protocoles, un seul geste répété

Un sous-dossier Repositories/ et un sous-dossier Services/ à l'intérieur de Domain/Interfaces/ — même découpage que celui déjà utilisé côté implémentation, appliqué cette fois aux contrats. Pour chacun, la déclaration du protocole quitte son fichier d'origine ; l'implémentation concrète y reste seule, et peut au passage prendre le nom du type concret plutôt que celui du protocole disparu (Services/SongDownloading.swift devient Services/MockSongDownloading.swift, par exemple — le fichier ne contient plus que ça). Exemple complet sur LyricsRepository :

// NOUVEAU — Domain/Interfaces/Repositories/LyricsRepository.swift
nonisolated protocol LyricsRepository: Sendable {
    func lyrics(for song: Song) async throws(LyricsError) -> [LyricsLine]
}
// Repositories/CachedLyricsRepository.swift — ne garde que l'implémentation
import Foundation

actor CachedLyricsRepository: LyricsRepository {
    private let service: LyricsFetching
    private var cache: [Song.ID: [LyricsLine]] = [:]

    init(service: LyricsFetching) {
        self.service = service
    }

    func lyrics(for song: Song) async throws(LyricsError) -> [LyricsLine] {
        // ... corps inchangé (Leçons 22-23)
    }
}

Les trois autres suivent exactement le même geste : le protocole (avec son Sendable, son éventuel nonisolated, ses signatures) part tel quel dans Domain/Interfaces/ ; la struct ou l'actor qui le concrétise reste dans Repositories/ ou Services/, en gardant seulement les imports dont elle a vraiment besoin (URLSessionLyricsFetching garde import os pour son Logger, par exemple — le protocole LyricsFetching, lui, n'en a besoin d'aucun).

Une incohérence de nommage à corriger avant de continuer

En construisant cette extraction, une question se pose naturellement : les protocoles Services/ devraient-ils, eux aussi, porter un nom qui rappelle leur couche — SongDownloadingService, LyricsFetchingService — pour rester lisibles à côté de LyricsRepository/DownloadedSongsRepository ? La tentation est réelle : ranger les quatre protocoles dans deux sous-dossiers symétriques (Repositories/, Services/) donne envie de leur donner des noms symétriques aussi.

Mais les Swift API Design Guidelines officielles répondent précisément à ce cas, avec deux règles distinctes selon ce qu'un protocole décrit :

  • "Protocols that describe what something is should read as nouns" (exemple cité : Collection) — c'est le cas de LyricsRepository/DownloadedSongsRepository : un repository est une chose, un nom suffit.
  • "Protocols that describe a capability should be named using the suffixes able, ible, or ing" (exemple cité : ProgressReporting) — c'est le cas de SongDownloading/LyricsFetching : ils décrivent une capacité ("sait télécharger", "sait récupérer des paroles"), pas une identité. Le suffixe -ing qu'ils portent déjà remplit exactement ce rôle.

Ajouter Service par-dessus un nom déjà en -ing double le signal (la capacité est indiquée deux fois : une fois par -ing, une fois par Service) sans rien clarifier de plus — et casse la symétrie avec les deux protocoles Repository, qui eux n'ont jamais eu besoin d'un suffixe de couche pour être clairs. Le nom du dossier peut légitimement s'appeler Services/ (c'est une étiquette d'organisation, pas un identifiant Swift) sans que le type ait besoin de répéter ce mot. Nicolas a suivi cette recommandation : SongDownloading et LyricsFetching ont retrouvé leur nom d'origine (renommage Xcode, répercuté partout où SongDownloadingService/LyricsFetchingService étaient utilisés — KaramockContainer.swift, DownloadSongUseCase, CachedLyricsRepository, les deux structs concrètes).

nonisolated sur les deux protocoles Service : un changement qui s'est propagé

En même temps que le renommage, Nicolas a ajouté nonisolated aux deux protocoles Service — pas seulement LyricsFetching (visé par l'audit, point 3.7) mais aussi SongDownloading, pour une cohérence totale entre les 4 protocoles :

// Domain/Interfaces/Services/LyricsFetching.swift
nonisolated protocol LyricsFetching: Sendable {
    func fetchLyrics(artist: String, title: String) async throws(LyricsError) -> String
}

// Domain/Interfaces/Services/SongDownloading.swift
nonisolated protocol SongDownloading: Sendable {
    func download(_ song: Song) -> AsyncStream
}

Pour SongDownloading, ce changement n'a rien cassé ailleurs : MockSongDownloading.download n'appelle que Task, Task.sleep et son AsyncStream.Continuation — des primitives de concurrence qui ne dépendent d'aucun réglage d'isolation par défaut du module. Pour LyricsFetching, en revanche, ce même changement a exigé trois corrections dans URLSessionLyricsFetching.swift pour continuer à compiler — la vraie raison d'être de cette section.

Pourquoi rendre LyricsFetching nonisolated a cassé la compilation ailleurs

SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor rend toute déclaration non annotée du module implicitement @MainActor — pas seulement les protocoles, mais aussi les fonctions libres et les constantes globales. Tant que LyricsFetching était lui-même implicitement @MainActor (faute de nonisolated), URLSessionLyricsFetching.fetchLyrics l'était aussi pour le satisfaire — et tout ce qu'il appelait à l'intérieur (une fonction libre, une constante globale, également @MainActor par défaut) était sur le même acteur : aucune frontière, aucun await nécessaire. Rendre le protocole nonisolated retire ce filet : fetchLyrics devient nonisolated à son tour pour continuer à satisfaire le contrat, mais tout ce qu'il appelait reste, lui, implicitement @MainActor — et une frontière apparaît là où il n'y en avait pas avant. Trois croisements sont devenus visibles d'un coup :

// AVANT — tout tournait silencieusement sur le Main Actor, aucun await nécessaire
guard let url = lyricsURL(artist: artist, title: title) else { throw .invalidURL }
// ...
lyricsFetcherLogger.error("Echec reseau lyrics.ovh : \(error)")
// APRÈS — nonisolated protocol : chaque appel à une déclaration restée @MainActor doit franchir la frontière
guard let url = await lyricsURL(artist: artist, title: title) else { throw .invalidURL }
// ...
await lyricsFetcherLogger.error("Echec reseau lyrics.ovh : \(error)")

lyricsURL (fonction libre privée) et lyricsFetcherLogger (constante globale) sont toutes les deux non annotées, donc @MainActor par défaut, exactement comme durationInSeconds l'était avant sa correction en Leçon 22 — le même mécanisme, révélé cette fois à trois endroits différents plutôt qu'un seul. Un troisième cas, plus strict, a demandé une solution différente :

nonisolated private struct LyricsResponse: Decodable {
    let lyrics: String
}

JSONDecoder().decode(LyricsResponse.self, from: data) est un appel synchrone, pas async — impossible d'y ajouter await. Si l'initialiseur synthétisé de LyricsResponse était resté implicitement @MainActor, le décoder depuis fetchLyrics (devenu nonisolated) aurait été un blocage réel, pas juste un await manquant — un appel synchrone ne peut pas franchir une frontière d'acteur en cours de route. LyricsResponse a donc dû devenir nonisolated directement, plutôt que d'ajouter un await impossible à écrire.

La leçon à retenir dépasse ce seul fichier : rendre un protocole nonisolated ne change rien en soi — mais ça retire l'appartenance implicite au Main Actor qui, jusque-là, mettait tout le monde d'accord par défaut. Chaque déclaration que la nouvelle isolation "nonisolated" touche et qui était restée @MainActor par défaut devient une frontière à traiter, une par une, révélée par le compilateur.

Pourquoi ce déplacement ne change rien à l'exécution

Swift ne donne aucune signification particulière à l'emplacement d'un fichier dans le projet — contrairement à d'autres langages où le chemin du fichier fait partie de l'identité du type (un package Java, par exemple). Tout le code de Karamock compile dans une seule cible ; Domain/Interfaces/LyricsRepository.swift et Repositories/CachedLyricsRepository.swift se voient l'un l'autre exactement comme avant. Cette leçon ne change donc que l'organisation visuelle du projet dans Xcode, pas une seule ligne de logique exécutée.

Scénario de vérification, étape par étape :
  1. Build du projet (⌘B) : doit réussir sans erreur — comme la Leçon 24, c'est un pur déplacement.
  2. N'importe quel écran déjà fonctionnel (téléchargement d'une chanson, affichage de paroles, bibliothèque) doit se comporter exactement comme avant — aucune régression attendue, puisque rien n'a changé au runtime.
  3. Dans Xcode, vérifie que Domain/Interfaces/ contient bien les 4 protocoles (répartis en Repositories/ et Services/) et que Repositories//Services/ côté Data ne contiennent plus que des implémentations concrètes.
  4. Vérifie que SongDownloading et LyricsFetching ne portent pas de suffixe Service, et que les 4 protocoles sont nonisolated.
  5. Dans URLSessionLyricsFetching.swift, vérifie les 3 await ajoutés (appel à lyricsURL, deux appels à lyricsFetcherLogger.error) et le nonisolated sur LyricsResponse — sans eux, le fichier ne compile plus une fois LyricsFetching devenu nonisolated.
