Dynamic Type : un bouton qui ne grossit pas avec le texte

Après les étiquettes VoiceOver (Leçon 14) et le bouton imbriqué (Leçon 15), un axe différent : le Dynamic Type, le réglage système qui agrandit tout le texte de l'app pour les utilisateurs qui en ont besoin. Sur l'écran FullScreenPlayerView, deux boutons voisins réagissent différemment à ce réglage — et ce n'est pas un hasard.

Pourquoi cette leçon : le Dynamic Type n'est pas qu'un sujet de basse vision. Dans une app de karaoké, il est probable qu'un utilisateur pose son téléphone à distance en chantant, ou augmente la taille du texte pour lire les paroles sans ses lunettes — un cas d'usage central pour Karamock, pas un cas limite. Un bouton play/pause qui reste minuscule pendant que tout le reste de l'écran grossit devient un vrai problème d'usage, pas juste un détail de conformité.

Ce qui grossit déjà, sans rien faire

Dans FullScreenPlayerView, le titre (.title2.bold()), l'artiste, et les boutons piste précédente/suivante (.font(.title)) réagissent tous correctement au réglage de taille de texte : ce sont des styles de texte sémantiques. Une SF Symbol affichée via Image(systemName:) suit automatiquement la taille de la police qu'on lui applique — tant que cette police est un style sémantique comme .title, elle grossit avec le reste de l'app, sans configuration supplémentaire.

Ce qui ne grossit pas : .font(.system(size: 64))

Button {
    player.isPlaying.toggle()
} label: {
    Image(systemName: player.isPlaying ? "pause.circle.fill" : "play.circle.fill")
        .font(.system(size: 64))
}

.system(size: 64) est une taille fixe, en points — pas un style sémantique. Ce bouton ne bouge pas d'un pixel quel que soit le réglage de Dynamic Type, alors que les boutons précédent/suivant juste à côté, eux, grossissent normalement. Résultat concret à un réglage de texte élevé : le plus gros bouton de l'écran visuellement au réglage par défaut devient le plus petit, proportionnellement, à côté d'un texte et de boutons voisins bien plus grands.

La correction : @ScaledMetric

struct FullScreenPlayerView: View {
    @Environment(\.player) private var player
    @Environment(\.dismiss) private var dismiss

    let song: Song

    @State private var progress: TimeInterval = 0
    @ScaledMetric(relativeTo: .largeTitle) private var playButtonSize: CGFloat = 64
    private let timer = Timer.publish(every: 0.5, on: .main, in: .common).autoconnect()

    var body: some View {
        // …
        Button {
            player.isPlaying.toggle()
        } label: {
            Image(systemName: player.isPlaying ? "pause.circle.fill" : "play.circle.fill")
                .font(.system(size: playButtonSize))
        }
        .accessibilityLabel(player.isPlaying ? "Mettre en pause" : "Lire")
        // …
    }
}

@ScaledMetric garde 64 comme valeur de référence à la taille de texte par défaut, mais recalcule cette valeur proportionnellement dès que l'utilisateur change son réglage — exactement le même comportement que les styles sémantiques, mais applicable à une taille numérique quelconque (ici un point de police, mais ça marche aussi pour un espacement ou une largeur de cadre). relativeTo: .largeTitle aligne l'échelle du bouton sur le plus gros texte visible de l'écran, cohérent avec son rôle de contrôle principal.

Vérifier : changer la taille de texte sans quitter le Simulateur

Dans Xcode, la barre de debug du Simulateur en cours d'exécution propose un raccourci Environment Overrides (icône de curseurs) avec un réglage "Text Size" — changer sa valeur applique le Dynamic Type immédiatement, sans relancer l'app ni changer les Réglages système. Alternative complète : Réglages → Accessibilité → Affichage et taille du texte → Texte plus grand, jusqu'aux tailles d'accessibilité (au-delà de la simple taille de texte).

Le cadre fixe des paroles (160pt) n'est pas le même problème

LyricsView, affichée dans un .frame(height: 160), pourrait sembler souffrir du même défaut. Mais LyricsView encapsule déjà un ScrollView : à une taille de texte plus grande, les paroles ne sont ni coupées ni perdues, il faut simplement défiler un peu plus pour voir la ligne courante — un compromis d'espace acceptable, pas une perte d'information. C'est la différence entre un cadre fixe qui contient du contenu défilant (correct) et une taille de police fixe qui ignore le réglage utilisateur (le bug de cette leçon).
