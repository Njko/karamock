Leçon 29 · Nettoyage architecture (6/N)

SongOptionsSheet gagne enfin son ViewModel

Depuis la Leçon 22, chaque écran avec une vraie logique passe par un ViewModel. SongOptionsSheet est le dernier à y échapper : cinq @State locaux et une mutation directe de PlayerState subsistent encore dans la View. Cette leçon refait la même transformation qu'en Leçon 22 — et explique pourquoi elle ne l'applique pas à DiscoveryView, contrairement à ce que suggère l'audit.

Ce que l'audit a trouvé — et où il faut le nuancer

Section 3.3 de l'audit, "Views manquant un ViewModel" : "DiscoveryView → données mockées hardcodées, aucun VM" et "SongOptionsSheet → 5 @State locaux + logique métier inline". Deux cas présentés côte à côte, avec la même gravité — mais qui ne se ressemblent pas une fois qu'on regarde le code réel de chacun.

DiscoveryView aujourd'hui :

struct DiscoveryView: View {
    var body: some View {
        NavigationStack {
            ScrollView {
                VStack(alignment: .leading, spacing: 24) {
                    PlaylistSection(playlists: mockPlaylist)
                }
                .padding(.top)
            }
            .navigationTitle("Découvrir")
            .navigationDestination(for: Playlist.self) { playlist in
                PlaylistDetailView(playlist: playlist)
            }
        }
    }
}

Il n'y a rien à extraire : aucun état mutable, aucun appel réseau, aucune branche conditionnelle — juste une constante affichée telle quelle. Un DiscoveryViewModel aujourd'hui contiendrait exactement une ligne (let playlists = mockPlaylist) et ne ferait rien d'autre que renommer mockPlaylist en viewModel.playlists. Ce serait une couche d'abstraction qui ne ferait rien du tout, ajoutée pour cocher une case plutôt que pour répondre à un besoin réel — le jour où DiscoveryView devra vraiment charger des playlists (une source de données réelle, un état de chargement, une erreur réseau), ce sera le bon moment pour lui donner un ViewModel, pas avant. Cette leçon laisse donc DiscoveryView tel quel, et se concentre sur le cas qui a une vraie justification.

SongOptionsSheet : le cas qui, lui, justifie un ViewModel

// Views/Discovery/PlaylistDetail/SongOptionSheet/SongOptionsSheet.swift — ACTUEL (extrait)
struct SongOptionsSheet: View {
    @Injected(\.player) private var player
    @Environment(\.dismiss) private var dismiss

    let song: Song

    @State private var downloadViewModel: SongDownloadViewModel?

    @State private var mode: KaraokeMode = .karaoke
    @State private var singerName: String = ""
    @State private var adjustVolumes = false
    @State private var pitch: Double = 0
    @State private var tempo: Double = 0

    var body: some View {
        // ...
        Button("Jouer maintenant") {
            player.currentSong = song
            player.isPlaying = true
            player.isExpanded = true
            dismiss()
        }
        // ...
    }
}

Ici, contrairement à DiscoveryView, il y a une vraie logique : cinq valeurs de configuration mutables, et une action ("Jouer maintenant") qui modifie directement PlayerState — un objet partagé, injecté via @Injected(\.player). Le modifier depuis une View est exactement le genre de logique métier qu'un ViewModel doit porter : ça doit pouvoir se tester sans instancier de View.

// NOUVEAU — ViewModels/SongOptionsViewModel.swift
@MainActor
@Observable
final class SongOptionsViewModel {
    private let song: Song
    private let player: PlayerState

    let downloadViewModel: SongDownloadViewModel

    var mode: KaraokeMode = .karaoke
    var singerName: String = ""
    var adjustVolumes = false
    var pitch: Double = 0
    var tempo: Double = 0

    init(song: Song, player: PlayerState, downloadViewModel: SongDownloadViewModel) {
        self.song = song
        self.player = player
        self.downloadViewModel = downloadViewModel
    }

    func playNow() {
        player.currentSong = song
        player.isPlaying = true
        player.isExpanded = true
    }
}

downloadViewModel n'est pas recréé — il devient une propriété de SongOptionsViewModel, composée à la construction plutôt que récupérée séparément par la View (voir Container ci-dessous). dismiss(), lui, reste dans la View : @Environment(\.dismiss) est un mécanisme de navigation propre à SwiftUI, sans équivalent côté ViewModel — fermer un écran est une responsabilité de la View, changer l'état de lecture est une responsabilité métier. La différence n'est pas cosmétique : l'un se teste avec @Test et un PlayerState factice, l'autre ne se teste qu'avec un framework d'UI.

Un optionnel qui n'a pas de raison d'être

Vérification faite sur l'implémentation réelle : downloadViewModel a été déclaré Optional, avec une valeur par défaut nil :

// ViewModels/SongOptionsViewModel.swift — IMPLÉMENTATION RÉELLE
var downloadViewModel: SongDownloadViewModel?

init(song: Song, player: PlayerState, downloadViewModel: SongDownloadViewModel? = nil) {
    self.song = song
    self.player = player
    self.downloadViewModel = downloadViewModel
}

Or songOptionsViewModel, la seule Factory qui construit ce type en production, fournit toujours un vrai SongDownloadViewModel — jamais nil. Rien dans le code de production ne peut jamais faire exister un SongOptionsViewModel sans son downloadViewModel. Ce paramètre par défaut n'existe donc que pour un usage : simplifier la construction d'un SongOptionsViewModel dans un test qui ne s'intéresse pas au téléchargement (SongOptionsViewModel(song: ..., player: ...), sans troisième argument).

C'est exactement la même catégorie de problème que la Leçon 28 a corrigée ailleurs (shouldFail sur MockSongDownloading, un besoin de test qui s'était glissé dans un type de production) : une facilité de test qui contamine la signature du type livré en production, obligeant tout le monde à gérer un cas qui ne se produit jamais, y compris la View en usage normal :

// Conséquence dans SongOptionsSheet : deux extractions d'optionnel qui ne protègent jamais contre rien en production
.onDisappear {
    viewModel?.downloadViewModel?.cancelDownload()   // le deuxième ? ne protège contre rien de réel
}
// ...
if let downloadViewModel = viewModel.downloadViewModel {   // toujours vrai en pratique
    DownloadButton(state: downloadViewModel.state, startDownload: downloadViewModel.startDownload)
}

Aucun des autres ViewModels du projet (SongDownloadViewModel, FullScreenPlayerViewModel, LibraryViewModel) ne recourt à ce genre de paramètre rendu optionnel par simple confort — leurs tests construisent l'objet complet (réel ou mock), sans jamais relâcher les exigences du type lui-même. La correction recommandée est celle montrée plus haut : let downloadViewModel: SongDownloadViewModel non optionnel, sans valeur par défaut. Un test qui ne s'intéresse pas au téléchargement passe simplement un SongDownloadViewModel construit avec un MockSongDownloading minimal — un peu plus de code au site d'appel du test, mais un type de production incapable, par construction, de représenter un état invalide.

Enregistrement dans le container — un seul appel à Container.shared, pas deux

// KaramockContainer.swift — AJOUT
@MainActor
var songOptionsViewModel: ParameterFactory<Song, SongOptionsViewModel> {
    self { song in
        SongOptionsViewModel(
            song: song,
            player: self.player(),
            downloadViewModel: self.songDownloadViewModel(song)
        )
    }
}

Composer self.songDownloadViewModel(song) à l'intérieur de cette Factory (même geste que lyricsRepository composant self.lyricsFetching(), Leçon 11) évite à SongOptionsSheet de devoir construire deux ViewModels séparément. La View garde exactement un seul @State optionnel et un seul appel à Container.shared dans son .task — ni plus, ni moins qu'avant :

// CORRECTION — Views/Discovery/PlaylistDetail/SongOptionSheet/SongOptionsSheet.swift
struct SongOptionsSheet: View {
    @Environment(\.dismiss) private var dismiss

    let song: Song

    @State private var viewModel: SongOptionsViewModel?

    var body: some View {
        ScrollView {
            VStack(alignment: .leading, spacing: 20) {
                SongHeader(song: song)

                if let viewModel {
                    DownloadButton(state: viewModel.downloadViewModel.state, startDownload: viewModel.downloadViewModel.startDownload)
                    SongOptionsForm(viewModel: viewModel)
                }

                Button("Ajouter à la file d'attente") { }
                    .buttonStyle(.borderedProminent)
                    .tint(.pink)
                    .frame(maxWidth: .infinity)

                Button("Jouer maintenant") {
                    viewModel?.playNow()
                    dismiss()
                }
                    .buttonStyle(.bordered)
                    .frame(maxWidth: .infinity)
            }
            .padding()
        }
        .onDisappear {
            viewModel?.downloadViewModel.cancelDownload()
        }
        .task {
            if viewModel == nil {
                viewModel = Container.shared.songOptionsViewModel(song)
            }
        }
    }
}

Le fait que SongOptionsSheet appelle encore Container.shared une fois, depuis .task, n'est pas un oubli : c'est la limite déjà admise en Leçon 12 et reconfirmée en Leçon 22 — une View a besoin d'un point d'entrée pour obtenir son ViewModel, et SwiftUI n'offre aucun point d'injection équivalent au moment de la création de la vue (là où Android, par exemple, dispose de SavedStateHandle) pour éviter ça proprement. Cette leçon ne cherche pas à faire disparaître cet appel, seulement à s'assurer qu'il n'y en ait qu'un, et que tout ce qui peut être délégué au ViewModel le soit.

SongOptionsForm : où vivent les @Bindable

Les @State devenus des var sur SongOptionsViewModel ont besoin de Binding pour TextField/Toggle/Slider. La Leçon 10 a établi @Bindable var x = x pour ce genre de cas — mais toujours en toute première ligne de body, une contrainte empirique observée avec @Injected, jamais documentée officiellement comme règle générale. Plutôt que de risquer ce placement dans le corps déjà long de SongOptionsSheet (et surtout, viewModel y est Optional — @Bindable n'accepte pas Optional<T>, seulement un T: Observable non optionnel), la démarche la plus sûre est d'extraire une sous-vue qui reçoit le ViewModel déjà extrait de son optionnel, en propriété stockée plutôt qu'en variable locale de body :

// NOUVEAU — Views/Discovery/PlaylistDetail/SongOptionSheet/SongOptionsForm.swift
struct SongOptionsForm: View {
    @Bindable var viewModel: SongOptionsViewModel

    var body: some View {
        VStack(spacing: 12) {
            ForEach(KaraokeMode.allCases) { option in
                ModeCard(option: option, isSelected: viewModel.mode == option) {
                    viewModel.mode = option
                }
            }
        }

        VStack(alignment: .leading, spacing: 8) {
            Text("Chanté par").font(.headline)
            TextField("Chanteur", text: $viewModel.singerName)
                .textFieldStyle(.roundedBorder)
        }

        Toggle("Régler les volumes", isOn: $viewModel.adjustVolumes)

        VStack(alignment: .leading) {
            HStack {
                Text("Tonalité")
                Spacer()
                Text("\(Int(viewModel.pitch))")
            }
            Slider(value: $viewModel.pitch, in: -12...12, step: 1)
        }

        VStack(alignment: .leading) {
            HStack {
                Text("Tempo")
                Spacer()
                Text("\(Int(viewModel.tempo))")
            }
            Slider(value: $viewModel.tempo, in: -50...50, step: 5)
        }
    }
}

mode n'a besoin d'aucun Binding — ModeCard prend un booléen et une closure, pas une projection $ ; l'assignation directe (viewModel.mode = option) suffit, exactement comme avant avec le @State. @Bindable en propriété stockée d'une struct View — plutôt qu'en variable locale de body — est son usage le plus courant et le mieux documenté : aucune ambiguïté de placement, puisqu'il n'y a pas de "première ligne de body" à respecter pour une propriété de la struct elle-même.

Pourquoi ne pas simplement essayer @Bindable var viewModel = viewModel dans un if let ?

Ça aurait été la solution la plus proche de celle déjà enseignée en Leçon 10 — mais deux raisons l'écartent. D'abord, SongOptionsSheet.viewModel est Optional (SongOptionsViewModel?) tant que le .task n'a pas fini de s'exécuter ; @Bindable exige un type conforme directement à Observable, et Optional<T> ne l'est jamais, même quand T l'est — le compilateur refuse @Bindable sur une valeur optionnelle, avec une erreur explicite ("The wrapped value must be an object that conforms to Observable"). Ensuite, même après un if let viewModel pour obtenir une constante non optionnelle, déclarer une variable à property wrapper directement dans le corps de la vue, à l'intérieur d'un VStack/ScrollView, repose sur un comportement que rien ne garantit — contrairement à la même déclaration en propriété stockée d'une sous-vue. La contrainte "première ligne de body" observée en Leçon 10 n'a jamais été confirmée comme une règle Swift générale, seulement comme un comportement empirique avec @Injected. Extraire SongOptionsForm avec @Bindable en propriété stockée évite complètement ces deux questions plutôt que de parier sur l'une ou l'autre.

Scénario de vérification, étape par étape :
  1. Build du projet (⌘B) : doit réussir sans erreur.
  2. Ouvre la feuille d'options d'une chanson : mode, chanteur, volumes, tonalité, tempo se comportent exactement comme avant.
  3. Appuie sur "Jouer maintenant" : le lecteur s'ouvre avec la bonne chanson, exactement comme avant.
  4. Lance un téléchargement puis ferme la feuille avant la fin : vérifie que l'annulation du téléchargement se déclenche toujours (comportement de la Leçon 26/27, inchangé).
  5. Dans Xcode, vérifie que DiscoveryView.swift n'a pas changé — aucun DiscoveryViewModel n'a été créé.
  6. Vérifie que SongOptionsSheet ne contient plus aucun @State métier (seulement viewModel) et n'appelle plus @Injected(\.player) directement.
  7. Vérifie que SongOptionsForm n'est pas déclaré private — utilisé depuis SongOptionsSheet.swift, un fichier différent, un private au niveau fichier l'aurait rendu invisible et aurait empêché la compilation.
  8. Vérifie si SongOptionsViewModel.downloadViewModel a été rendu non optionnel (let downloadViewModel: SongDownloadViewModel, sans valeur par défaut) — sinon, c'est le correctif qui reste à appliquer, voir la section dédiée ci-dessus.
