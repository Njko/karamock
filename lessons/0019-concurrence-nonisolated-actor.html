Un correctif Swift 6 : nonisolated, actor, et l'isolation par défaut

Avant de commencer la Leçon 18 sur ton Mac, tu as ajusté ton projet pour respecter proprement le mode de concurrence stricte de Swift 6. Le dépôt des chansons téléchargées était déjà un actor depuis les leçons précédentes — ce n'est pas lui qui a changé de nature. Le vrai sujet : un protocole et deux init qui avaient besoin d'un mot-clé qu'ils n'avaient pas encore, et un @MainActor ajouté par clarté sur un type qui l'était déjà implicitement. En cours de route, une tentative explorée pour faire compiler le tout — remplacer temporairement l'acteur par une classe protégée par une échappatoire non sûre — illustre bien le réflexe à éviter.

Pourquoi cette leçon : ce n'est pas une leçon planifiée à l'avance — comme les leçons d'accessibilité, elle existe parce que tu as toi-même repéré et corrigé un vrai problème dans ton projet. Un poste Swift/Apple Platforms senior suppose de savoir lire un diagnostic de concurrence Swift 6 et comprendre pourquoi un correctif marche, pas seulement copier la solution qui fait taire le compilateur.

Le réglage qui change tout : l'isolation par défaut du module

Le projet Karamock a deux réglages de build actifs (visibles dans project.pbxproj) :

SWIFT_APPROACHABLE_CONCURRENCY = YES;
SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor;

Ce deuxième réglage correspond à la proposition d'évolution SE-0466 : sans lui, une déclaration Swift est non isolée par défaut, et on ajoute @MainActor à la main partout où c'est nécessaire (exactement ce que faisait KaramockContainer.swift jusqu'à présent, avec un @MainActor explicite sur libraryViewModel et songDownloadViewModel). Avec ce réglage activé, c'est l'inverse : toute déclaration non annotée devient implicitement @MainActor, et c'est nonisolated qui permet d'en sortir explicitement. L'exemple de la proposition elle-même, compilé avec cette option :

func f() { }              // implicitement @MainActor

nonisolated func g() { }   // explicitement non isolée

class C {
    init() { }             // implicitement @MainActor
    static var value = 10  // implicitement @MainActor
}

C'est un mode pensé pour les apps à dominante UI, où la plupart du code tourne de toute façon sur le thread principal — Xcode 26 l'active par défaut pour tout nouveau projet.

Une tentation explorée, puis écartée : l'échappatoire non sûre

En cherchant à faire compiler les changements de cette leçon, tu es passé un temps par une version différente du dépôt — pas celle avec laquelle tu étais parti, et pas celle que tu as gardée :

final class SimpleDownloadedSongsRepository: DownloadedSongsRepository {
    nonisolated(unsafe) private var storage: [Song] = []

    func songs() async -> [Song] { storage }
    func add(_ song: Song) async {
        guard !storage.contains(song) else { return }
        storage.append(song)
    }
}

nonisolated(unsafe) est une échappatoire : elle dit au compilateur "arrête de vérifier les accès concurrents à cette propriété, je te promets que c'est sûr" — sans qu'aucun mécanisme ne garantisse réellement cette promesse. Rien n'empêcherait deux appels concurrents à add(_:) de modifier storage en même temps. Ce n'était pas la bonne piste, et tu ne l'as pas gardée : le dépôt est resté un actor, exactement comme dans les leçons précédentes :

actor SimpleDownloadedSongsRepository: DownloadedSongsRepository {
    private var storage: [Song] = []

    init() {}

    func songs() async -> [Song] { storage }
    func add(_ song: Song) async {
        guard !storage.contains(song) else { return }
        storage.append(song)
    }
}

Un actor garantit qu'un seul accès à storage s'exécute à la fois, appliqué par le compilateur — pas une promesse manuelle, une vraie exclusion mutuelle. C'est exactement le rôle que MockDownloadedSongsRepository joue déjà côté tests depuis la Leçon 13 : le vrai dépôt suit la même discipline que son double de test, et n'a jamais eu besoin d'en changer.

nonisolated(unsafe) n'est pas toujours une erreur

Ce n'est pas un anti-pattern en soi : c'est une échappatoire de migration légitime quand on sait, par construction du code, qu'une propriété n'est en réalité accédée que depuis un seul contexte à la fois, sans vouloir l'encoder dans le type. Le réflexe à éviter, c'est de s'en servir pour faire taire une erreur de compilation sans avoir compris sa cause réelle — ce qui était tentant ici, puisque l'erreur venait en fait du protocole et des init, pas du dépôt lui-même.

Pourquoi le protocole et les init ont besoin de nonisolated

DownloadedSongsRepository et les deux UseCase qui l'utilisent ont aussi changé :

nonisolated protocol DownloadedSongsRepository: Sendable {
    func songs() async -> [Song]
    func add(_ song: Song) async
}

struct DownloadSongUseCase: Sendable {
    nonisolated init(service: SongDownloading, repository: DownloadedSongsRepository) { … }
}

struct FetchDownloadedSongsUseCase: Sendable {
    nonisolated init(repository: DownloadedSongsRepository) { … }
}

Ces trois types sont Sendable : par construction, un type Sendable est conçu pour être partagé en sécurité entre acteurs différents — c'est tout l'intérêt du protocole Sendable. Mais sous isolation par défaut MainActor, un protocole ou un init non annoté devient implicitement @MainActor, ce qui les enfermerait sur un seul acteur et contredirait leur propre nature Sendable. nonisolated lève cette contradiction : ces déclarations restent utilisables depuis n'importe quel contexte, y compris depuis l'intérieur de l'acteur SimpleDownloadedSongsRepository lui-même.

Conséquence directe visible dans KaramockContainer.swift : les Factory downloadSong et fetchDownloadedSongs portaient un @MainActor explicite avant la correction — nécessaire tant que les init qu'elles appellent étaient implicitement MainActor. Une fois ces init rendus nonisolated, ce @MainActor devient inutile et a été retiré : les deux Factory redeviennent utilisables depuis n'importe quel contexte d'isolation, cohérent avec le fait qu'elles ne construisent que des structs Sendable.

Et PlayerState, pourquoi ajouter @MainActor alors qu'il l'était déjà implicitement ?

PlayerState est un @Observable final class qui porte l'état de lecture affiché à l'écran — il n'a de sens que sur le fil principal, et le sera de toute façon tant que le réglage de build actuel reste actif. Le rendre @MainActor explicite documente cette contrainte dans le type lui-même plutôt que de la laisser dépendre silencieusement d'un réglage de projet invisible en lisant le fichier seul — utile si ce fichier est un jour partagé dans un module avec un réglage d'isolation différent.
